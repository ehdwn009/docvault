# 문서 교차 검토 (doc-crosscheck, skillVersion 1)

목적: 문서의 **정확성**(코드와 같은가)과 **정합성**(다른 문서와 같은 말을 하는가)을 쓴 사람이 아닌 눈으로 확인한다. 매번 같은 역할·같은 지시문으로 한다 — 그때그때 고쳐 쓰지 않는다. 고칠 일이 생기면 이 파일을 고치고 skillVersion을 올린다.

용어: **리더** = 문서를 쓴 이 세션. **검토자** = 리더가 띄우는 에이전트(쓴 과정을 모른다).

## 언제

이번 작업에서 아래 중 하나라도 새로 쓰거나 고쳤으면, **작업을 마치기 전(커밋 전)**에 한 번. 여러 문서를 고쳤으면 한 조가 전부를 함께 본다(문서마다 따로 띄우지 않는다).

| 대상 | 예 |
|---|---|
| 설계 문서 | `docs/design/*.md` — ERD, API명세서, IA, 시스템아키텍처, 기능 설계(뉴스브리핑·배움카드·수출입동향 …) |
| 보고서·가이드 | `docs/` 아래의 글 문서(하위 폴더 포함, `.md`·`.html`) — 배포 가이드, 토론 보고서, 시장조사, 저장소에 넣은 시안 HTML |
| 업데이트 기록 | `CHANGELOG.md` (맨 위 버전이 루트 `package.json`의 version과 같은가까지) |
| 학습자료 | `docs/data_ignored/학습자료/**` (이 폴더가 있는 환경에서만 — git에 올리지 않는 개인 자료다) |
| 지시 문서 | `CLAUDE.md`, `.claude/skills/` 아래 전부(`SKILL.md`·`references/`·`assets/`의 예시 파일) |

대상이 아닌 것: 코드 주석, 저장소에 넣지 않고 claude.ai에만 올린 시안 페이지, 뷰어 시험용 견본(`docs/samples/*.html`).

## 몇 명을

| 바뀐 크기 | 검토자 |
|---|---|
| 오타·문구 한두 줄 (사실이 바뀌지 않음) | B |
| 사실이 바뀌는 수정(숫자·이름·경로 하나라도), 문단·절 수정 | A + B |
| `CHANGELOG.md` 항목 추가만 | A + C (설계 문서도 함께 고쳤으면 아래 줄) |
| 새 문서, 새 절, 스키마·API·화면 구조가 바뀌는 수정, 학습자료의 새 장 | A + B + C |

크기가 다른 문서를 함께 고쳤으면 **가장 큰 쪽**에 맞춘다. 검토자는 한 번에 띄운다(서로 기다리지 않는다). 범용(general-purpose) 에이전트로 — 지시문이 "고치지 말고 찾기만"을 말한다.

## 검토자에게 주는 것

검토자 한 명에게 **공통 머리 + 자기 역할 문단 하나**를 넘긴다. 아래 글을 그대로 쓰고 중괄호 자리 셋만 채운다.

- `{FILES}`: 문서마다 한 줄 — 경로와 **어디가 바뀌었나**(새 파일 / 새 절의 제목 / 고친 절의 제목). 무엇을 왜 바꿨는지, 어떤 결론이 맞는지는 적지 않는다 — 가설을 받은 검토자는 그 가설을 확인해 준다.
- `{DIFF}`: 바뀐 것을 보는 법. 커밋 전이면 `git status --short`와 `git diff`(작업 트리), 이미 커밋했으면 리더가 기준 커밋을 넣어 `git diff <기준 커밋>..HEAD`.
- `{EXCLUDE}`: 작업 트리에 이번 문서와 **무관한 진행 중 변경**이 섞여 있으면 그 경로 묶음(예: "`server/src/lib/trade/` 아래와 `client/src/screens/TradePage.tsx`"), 없으면 "없음". 경로만 적는다 — 그 변경이 무엇인지, 옳은지는 적지 않는다. 범위를 좁힐 일이 있으면 이 자리로만 한다(지시문 뒤에 글을 덧붙이지 않는다).

알아 둘 것(지시문에 이미 들어 있다): **새로 만든 파일은 `git diff`에 나오지 않는다** — `git status --short`의 `??` 줄로 찾아 파일 전체를 읽어야 한다. 학습자료는 git 밖이라 diff가 없다 — `{FILES}`에 적힌 절을 직접 읽는다.

공통 머리:

> docvault(앱 이름 Loft) 저장소(지금 작업 폴더가 그 루트다)에서 방금 고친 문서를 검토한다.
> 대상: {FILES}
> 바뀐 것을 보는 법: {DIFF}. 새로 만든 파일은 `git diff`에 나오지 않으니 `git status --short`의 `??` 줄을 보고 그 파일은 전체를 읽는다(문서든 코드든). git에 올리지 않는 문서(`docs/data_ignored/` 아래)는 diff가 없으니 대상에 적힌 절을 직접 읽는다.
> 작업 트리에 함께 있지만 이번 검토와 무관한 변경(보지 않는다): {EXCLUDE}
> **고치지 말고 찾기만 한다.** 지적마다 ① 문서 파일과 줄(또는 인용) ② 무엇이 틀렸나 ③ 근거(코드 파일:줄, 다른 문서 파일:줄, 계산식) ④ 확신 정도(확인함 / 추정)를 적는다. 근거를 직접 열어 본 것만 "확인함"이라고 쓴다. 틀린 것이 없으면 무엇을 대조했는지 목록으로 적고 "없음"이라고 쓴다 — 억지로 만들지 않는다. 문체·취향은 지적하지 않는다.

### A — 코드 대조

> 문서가 말하는 **사실**을 실제 코드와 하나씩 맞춰 본다.
> - 파일 경로와 줄 번호, 함수·상수 이름과 값 — 서버 `server/src/constants.ts`, 화면 `client/src/lib/constants.ts`
> - DB 표·칸 이름과 타입·제약 — `server/src/db/schema.ts`, `server/drizzle/*.sql`
> - API 경로·메서드·요청/응답 모양 — 라우트 파일(`server/src/routes/`)에는 뒷부분만 있고 앞머리(`/api/v1/…`)는 `server/src/index.ts`에서 붙는다
> - 에러 코드 — 라우트뿐 아니라 `server/src/middleware/`·`server/src/lib/`에서도 낸다
> - 화면 ID(SCR-…)와 화면 구성 — `client/src/screens/`·`components/`·`lib/`·`renderers/`
> - 명령어 — 루트 `package.json`과 `server/package.json`·`client/package.json`의 scripts
> - 버전 — **루트** `package.json`의 version ↔ `CHANGELOG.md` 맨 위(server·client의 version 칸은 쓰지 않는 값이다). 기능 설계 문서(`docs/design/`의 뉴스브리핑·수출입동향 등) 머리표의 "상태" 칸에 버전이 적혀 있으면 그것도 `CHANGELOG.md`와 맞는지
>
> 찾을 것: 문서에는 있는데 코드에 없는 것, 코드와 다른 값, "구현됨"이라 적혔는데 없는 것, 반대로 이번 작업의 코드 변경(새 파일 포함)이 문서에 안 적힌 것. 숫자(개수·시간·크기·비율)는 다시 세거나 계산한다.

### B — 문서 사이 정합

> 같은 사실이 적힌 **다른 문서**와 어긋나는 곳을 찾는다. 반드시 맞춰 볼 짝:
> - ERD(`docs/design/ERD_*.md`)의 엔티티 다이어그램 블록 ↔ 엔티티 설명 표 ↔ 관계 설명 — 같은 사실이 세 군데 적혀 있다(칸 이름이 바뀌었으면 "비고" 절의 인덱스·뷰 설명에 나열된 칸 이름도)
> - API명세서의 에러 코드 표 ↔ API 목록 표 ↔ 상세 절
> - 기능 설계 문서(뉴스브리핑·배움카드·수출입동향) ↔ ERD·API명세서·IA
> - IA의 Depth 표(화면 ID) ↔ 메뉴 구조 트리 ↔ 날짜별 개정 절
> - `CHANGELOG.md` ↔ 기능 설계 문서 머리표의 "상태" 칸(어느 단계가 어느 버전인가)
> - `CLAUDE.md` ↔ 스킬 문서, 스킬의 `SKILL.md` ↔ 그 `references/`
>
> 문서 안에서도 앞뒤가 다른 곳(위에서는 3번, 아래에서는 2번), 지워진 것을 아직 가리키는 링크·파일 경로·절 이름, 날짜·버전이 서로 다른 곳을 찾는다. `docs/data_ignored/학습자료/`가 있으면 그 안의 인용(파일 경로·줄 번호)이 이번 변경으로 낡지 않았는지도 본다.

### C — 읽는 사람

> 이 문서를 처음 읽는 사람(사용자는 코딩 입문자다)의 눈으로 읽는다: 설명 없이 처음 나오는 용어, 앞에서 정하지 않고 쓰는 약어·ID, 순서대로 따라 하면 막히는 단계, 본문과 표·예시가 다른 곳, 계산이 안 맞는 숫자, "나중에"·"별도" 처럼 어디인지 알 수 없는 참조, 한 문장이 두 가지로 읽히는 곳. `CHANGELOG.md`라면 비개발자가 체감하는 변화로 쓰였는지(코드 용어가 아닌지, `CLAUDE.md`의 "업데이트 기록" 규칙). 사실의 진위는 A·B가 본다 — 여기서는 읽히는가와 빠진 것만.

## 받은 뒤 (리더)

1. 지적을 **그대로 믿지 않는다.** "확인함"도 근거 줄을 직접 열어 맞는지 본다. 검토자가 틀린 경우(낡은 줄 번호를 본 것 등)는 버린다.
2. 맞는 지적은 문서를 고친다. **문서가 맞고 코드가 틀린 것**으로 드러나면, 코드를 고치기 전에 사용자에게 알린다 — 틀린 코드에 맞춰 문서를 고쳐 쓰지 않는다.
3. 고친 양이 절 하나 이상이면, 그 문서만 대상으로 B를 한 번 더 띄운다(`{FILES}`에 고친 절의 제목). 그 이상 되풀이하지 않는다.
4. 사용자에게 알린다 — 요약 한 줄, 그 아래에 필요하면 목록:
   `문서 교차 검토: 검토자 n명 · 지적 n개 중 n개 반영 · 버린 것 n개 · 남은 것 n개`
   (지적 수 = 반영 + 버린 것 + 남은 것.) 버린 것은 이유를 한 줄씩, 남은 것(판단이 필요해 고치지 않은 것)은 무엇인지 목록으로.

## 하지 않는 것

- 검토자에게 고치게 하지 않는다(여러 에이전트가 같은 문서를 고치면 어긋난다).
- 검토 결과를 문서에 "검토 완료" 같은 표시로 남기지 않는다 — 문서는 내용만 담는다.
- 사용자가 "검토 없이"라고 하면 그 작업에서는 건너뛴다.
