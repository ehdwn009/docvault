수집부터 다시 — 더 좋으면서 싸게 만드는 길

사용자 질문: "RSS를 긁어 AI가 정리하는 지금 방식은 비용이 많이 드는 것 같다. 애초에 Claude 웹 검색으로 '오늘 무슨 일이 있었나'를 묻고 찾는 식은 어떤가. 근본부터 다시 의논해 달라." 울타리는 세 가지 — 파이프라인 전체, 품질 우선에 비용 절감은 곁들임, 무료 티어 키 허용. 이전 토론과 무관한 새 에이전트 4명(뉴스 출처·수집 전문가 · AI 호출 구조·비용 전문가 · 품질 담당 · 회의론자)이 두 라운드로 다퉜다. 외부 API 조건과 Anthropic 단가는 각자 웹에서 확인했다.

결론 — 수집 방식은 바꾸지 않는다. 돈은 모델에서, 품질은 재료에서 나온다 (4/4)
  • 웹 검색으로 사건부터 묻는 하향식은 4/4 반대. 계산하면 수집~선별이 $0.9~1.5로 지금($0.35~0.8)보다 비싸거나 같고, 나오는 건 사건 25~30개뿐이다. 발행 시각(24시간 범위)·재현성·국내 커버리지·참고 층을 잃고 "무엇이 오늘의 사건인가"를 검색 엔진이 정하게 된다. 다만 "오늘의 핵심 6건을 빠뜨리지 않았나" 교차검증(검색 3회, 약 $0.06)에는 쓸 가치가 있다.
  • 비용의 몸통은 수집이 아니라 Sonnet 요약(55%)이다. 후보 600건 중 버려지는 450건의 분류·선별 비용은 $0.3 남짓. 수집을 어떻게 바꿔도 아낄 돈은 $0.3~0.5가 상한이고, 수집 재설계의 진짜 목적은 핵심·주요가 본문 2곳 이상을 재료로 갖는 비율(지금 스크린샷 4건 중 3건이 1곳)이다.
  • 가장 큰 지렛대는 Haiku 4.5 → Haiku 5.5(단가 1/10, 분류·선별·합치기·참고·요약 보기·웹 보강 전부). 품질 손해 없이 회차당 약 −$0.64. 4/4 찬성.
  • "지금 월 $75"는 실측이 아니라 종이 계산이다. v0.45 파이프라인은 오늘 배포됐고 실측 0회. 유일한 실측(10/1, v0.42)은 추정보다 22% 낮았다. 그래서 먼저 10회차(2주) 실측 — 1~5회차 기준선, 6회차부터 Haiku 5.5만 바꿔 단일 변수로 잰다. 단계별 토큰 칸(30줄)과 품질 지표 5개를 지금 넣는다.
  • 비용 0인 수집 개선 4개는 지금 한다: 수집 단계 사건 묶기(언론사 수 신호) · 선별 입력 자르기를 "언론사 수 우선"으로 · Google 검색 40개를 실패율 분모에서 분리(단일 장애점 제거) · 웹 검색 allowed_domains 20곳으로 제한. 그리고 서버에서 briefing:check를 돌려 통과한 후보 출처만 켠다.
  • 하지 않는다: 네이버 검색 API(개정 약관이 AI 입력·요약을 금지), NewsAPI·GNews·Mediastack 등 무료 뉴스 API(12~24시간 지연·월 100회), 프롬프트 캐시(Haiku 4.5는 최소 4,096토큰이라 한 바이트도 안 잡힘, 효과 2~3%), 단계 병합·분류 폐지, 후보·분야 축소, 주요 요약을 Haiku로 강등(A/B 전), 배치 API(사용자가 "새벽 자동 생성"으로 바꾸지 않는 한).
  • 예상 비용: 지금 약 $2.2/회차(월 $66) → 2단계(Haiku 5.5 + 출력 다이어트) 약 $1.5(월 $45) → 3단계(실측 뒤 웹 보강 조정, 선택에 따라 핵심 Opus) $1.3~1.7(월 $39~51). 품질은 그대로거나 핵심이 더 좋아진 채로.

## 1. 지금 수집의 진단 (코드 기준)
돈의 낭비는 생각보다 작고, 품질의 누수는 생각보다 크다. 24시간판 약 $2.5의 내역을 역산하면 수집·분류·선별(Haiku) 약 $0.43, 웹 검색 보강 약 $0.4, 요약 보기 $0.27, Sonnet 요약 약 $1.1~1.3. 후보 600건 중 버려지는 450건이 먹는 분류·선별 비용은 약 $0.3. 수집을 아무리 잘 재설계해도 아낄 수 있는 돈은 $0.3~0.5가 상한. 비용의 몸통은 "핵심·주요 85건을 언론사 2~3곳 본문으로 Sonnet이 쓴다"는 뒷단 결정이다.

## 3. 사용자 제안(웹 검색 하향식)의 정직한 평가
- 1단계 "오늘 주요 사건 찾기": 분야 8개 × 검색 2회 = $0.16 + Sonnet ≈ $0.19 → $0.35
- 2단계 사건 25개 × 보도 찾기 2회 = $0.50 + Haiku 토큰 ≈ $0.04~0.43 → $0.5~0.9
- 수집~선별 합 $0.9~1.3: 지금($0.83)보다 비싸거나 같은데, 나오는 건 사건 25~30개뿐. 지금은 핵심·주요 85 + 참고 60.
얻는 것: 코드 단순화, 통신사 기사 직접 접근, 처음부터 사건 단위 묶음. 잃는 것: ① 편집 주체가 검색 엔진 랭킹과 모델의 사전지식으로 바뀜 ② 재현성 없음 ③ 24시간 범위 붕괴(발행 시각 없음) ④ 국내 커버리지 미지 ⑤ 참고 층 소멸.
결론: 전면 하향식은 품질 우선 원칙에 맞지 않는다. "오늘의 핵심 6건"에 한해 검색 2회로 반대 시각·후속 보도 보강(≈ $0.12+토큰)은 가치 있음 — S8 구조 그대로 대상만 바꾸면 된다.

## 4. 추천: E = 네이버 검색 API(국내 신호+재료) + Google 편집 피드(세계 신호) + 직접 RSS(재료) + 수집 단계 사건 묶기(비용 0)
1. 국내: DEFAULT_QUERIES 국내 20개를 Google 대신 네이버 뉴스 검색 API로(분야당 display=100, sort=date, 20~60회/일). originallink로 원문 바로, pubDate로 범위 정확. 제목만 핵심·주요가 줄어 S8 비용 $0.4 → ~$0.1.
2. 세계: Google 영어판 Top stories + WORLD/BUSINESS/TECHNOLOGY/SCIENCE 주제 피드로 검색 20개를 5~6개로. 피드 순서를 편집 신호로.
3. 직접 RSS는 재료 공급원으로 유지, briefing:check 통과분만.
4. 수집 단계 사건 묶기(비용 0): bigramSimilarity를 dedupe()에도 적용(같은 분야·6시간 안·유사도 0.6+)해 기사 600건 → 사건 ~250묶음, 묶음의 언론사 수를 선별 프롬프트에 준다. 분류·선별 입력 절반, 중요도 판정의 근거가 생김.
5. MAX_INPUT_PER_SUB·MAX_PER_SOURCE를 시간대 균등이 아니라 "언론사 수 → 최신" 순으로.
예상 비용: Haiku 수집~선별 $0.43 → ~$0.25, 웹 보강 $0.4 → ~$0.1 → 약 $2.0. Haiku 5.5 전환까지 합치면 $1.6~1.8.
품질이 나아지는 지점: 국내 핵심·주요의 재료 있는 비율, 발행 시각 정확도, 국내 언론 다양성, "다룬 언론사 수" 정량 신호, 영어 기사 핵심 누락 완화.
선행 확인(서버에서): 네이버 개발자 약관의 검색 결과 저장·가공 조항(우리는 제목·주소·시각만 저장), 한국판 Google Top stories 피드 실존, GDELT 한국어 포함 여부.

# 출처·수집 전문가 — 2라운드

## 1. 질문에 대한 답
비용 담당에게 — bodiesRead·webFilled 실측. 이 환경의 DB는 비어 있고 v0.45는 실측 0회. briefing_runs에는 그 칸이 없다. 실측은 회차 JSON의 stats(attached·bodiesRead·fromFeed·extractRejected·webFilled·demoted·basis)에 있다. 서버에서: sqlite3 data/docvault.db "select json_extract(content_text,'$.stats') from files where kind='briefing' order by id desc limit 10". 웹 보강이 10회차 평균 15건 중 3건 이하면 $0.30을 "핵심 6건 교차검증"으로 돌리는 데 동의 — 단 allowedDomainsOf()가 피드 호스트를 전부 넣는 문제(후보를 켜면 70개 → request_too_large)를 상위 20곳+통신사로 자르는 수정이 먼저다. webFilled가 낮은 이유가 "도메인 목록 때문에 호출이 깨져서"일 수 있다.
품질 담당에게 — 후보 43곳·Google 비율·GDELT. briefing:check를 이 환경에서 못 돌렸다. 추정: 약 35곳 생존, 본문(content:encoded)을 주는 곳은 세계 쪽 6~8곳. 켜면 직접 주소 기사 약 +500건, Google 비율 58% → 약 40~45%. 비율보다 stats.attached(Google 기사가 직접 기사에 붙은 수)가 오르는 것이 중요 — 국내 20곳이 켜지면 붙는 비율이 크게 뛴다. GDELT는 sourcelang:kor로 제목·URL·도메인을 주지만 본문도 묶음도 없다. 서버에서 curl 한 줄로 도메인 분포를 보면 국내 커버를 바로 알 수 있다. 세계 "언론사 수" 신호로만, 실측 뒤.
회의론자에게 — "70곳은 추정" 동의, 네이버는 양보. 약관 때문에 철회: 네이버 개발자센터 검색 API는 2026-07-31부터 신규 신청 중단, NAVER API HUB로 이관됐고 개정 약관이 검색 결과의 저장·캐싱·AI 입력·요약 활용을 금지한다. 우리는 제목을 Haiku에 넣고 요약하므로 바로 걸린다. 다만 "키 = 월 1회 장애"를 일반 규칙으로는 받지 않는다 — 기준은 약관과 만료 정책.

## 2. 양보·고수

### 1. 질문에 대한 답
출처 → 분류 ② 없애기. 분류는 분야를 모르는 직접 RSS 기사에만 돈다. 150건이면 Haiku 5.5로 2회·$0.003 — 없앨 가치가 없고, 선별이 분류까지 떠안으면 토큰이 오히려 는다. "사건 묶음 + 언론사 수"의 값은 비용이 아니라 중요도 판정 신호 — 찬성, 이유는 품질. web_search 도구 버전: Haiku 5.5 지원 버전 문서 없음 → 1회 호출로 확인, 둘 다 안 되면 웹 보강만 4.5에 남긴다(차이 $0.15). 100K 절벽: 최대 프롬프트 ≈ 10k 토큰으로 10배 여유. 진짜 위험은 allowed_domains 70개 — 통신사 4 + 국내 상위 10으로 줄인다.
품질 → "핵심 6건 겹침 ≥ 4" 회귀 검증: 같은 후보 집합에 두 모델을 동시에 돌려야 한다(비교 모드, 선별 +$0.03). 같은 모델 2회의 겹침 기준선부터 잰다. 배치 누적 지연: 전 단계 6라운드 = 보통 30분~2시간, 최악 6시간+. 캐싱 절감률 합계 2~3% — 안 한다.
회의론자 → 단계별 분해(추정): Sonnet 요약 55%, 출력($0.65)이 입력($0.57)보다 크다. 10/1 실측도 Sonnet 49%. Haiku 5.5 생각 토큰: 공식 수치 없음, JSON 추출은 5~15%로 본다. usage.output_tokens_details.thinking_tokens를 Usage에 더하면 첫 회차에 확정. 100% 붙어도 단가 1/10이라 4.5보다 싸다.
배치 재설계: 양보한다. 정직한 규모 200~300줄 + 새 실패 모드 3개(배치 거부·만료·부분 실패). 얻는 것 월 $18. "하루 1회 버튼"에 최대 1시간 대기를 얹는 대가로 안 맞고, "아침 자동 + 배치"는 사용자가 자동 생성을 안 쓴다 했으니 전제가 없다. 하지 말 것.

## 1. 질문에 답
- 비용 담당 — "버튼 누르고 1시간": 버튼 사용자로서는 아니다. 2초 폴링으로 진행을 보는 제품에서 1시간은 실패로 보인다. 새벽 자동 생성이면 받아들일 수 있다 — 단 사용자가 이미 "자동은 거의 안 쓴다"고 정했다. 만료 꼬리는 코드가 동기 재실행해야 한다. 숨은 상호작용 셋: ① update.sh는 running이면 컨테이너 교체를 미룬다 → 배치 90분 창 동안 배포가 막힌다. ② 재시작 시 recoverStaleRuns()가 running을 전부 실패로 닫는다 → batch id를 DB에 남기고 기동 시 폴링을 재개하지 않으면 돈 낸 결과가 고아가 된다. ③ Sonnet의 fallbacks: 'default'는 배치에서 거부된다. 코드 규모 ≈ 250~350줄 + ERD·API 문서. 절감 월 $18.

- 출처 담당 — 비용의 몸통: Sonnet 55% 동의. "주요 1곳 본문"은 반대 — 스크린샷의 얕은 글 4건이 전부 "주요 1곳"이다. 먼저 깎을 곳은 출력 다이어트($0.1)와 실측 뒤 핵심 입력 길이다.
