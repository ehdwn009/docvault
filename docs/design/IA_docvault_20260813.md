## 레이아웃 개요

> v0.53/0.54 재설계는 아래 "앱 구조 재설계 — 안 B · 홈 중심" 절이 우선한다. 이 절은 v0.52까지의 모습이다.

로그인 후 전체 화면은 단일 워크스페이스(SCR-100)입니다. 좌측 아이콘 레일(48px)에서 패널을 전환하고, 패널 우측 본문 영역에 뷰어/편집기 또는 설정 콘텐츠가 표시됩니다. 모바일에서는 레일+패널이 드로어(서랍)로 전환됩니다.

## 비고

- **글로벌 내비게이션**: 아이콘 레일이 유일한 전역 내비게이션. 상단 헤더는 두지 않고 뷰어/편집기 헤더에 파일명·액션 버튼을 배치합니다.
- **URL 라우팅**: SPA지만 딥링크를 지원합니다 — `/login`, `/f/{fileId}` (파일 열람), `/admin/*`. 폰에서 특정 문서를 북마크해 바로 열 수 있게 하기 위함입니다.
- **단축키**: `[` 파일 패널 토글, `Ctrl+K` 커맨드 팔레트, `E` 편집 모드, `Ctrl+S` 저장(편집 유지), `Ctrl+Enter` 저장하고 닫기, `Escape` 패널 닫기. 모바일에는 해당 없음.
- **날짜 표기(v0.43)**: 화면의 날짜·시각은 "10월 1일 오전 7:34"(올해가 아니면 "2025년 10월 1일 …"), 날짜만이면 "10월 1일"로 통일한다(`lib/date.ts`). 브라우저 기본 표기 "2026. 10. 1. 오전 7:34:12"는 점·초가 섞여 읽기 어려웠다.
- **확인 창(v0.43)**: 버튼에 하는 일을 쓴다 — "확인/취소" 대신 [버리고 이동]/[계속 쓰기], [영구 삭제], [폴더 삭제], [로그아웃]. 편집 "취소"를 누른 뒤 다시 "취소/확인"을 고르게 하면 어느 쪽이 버리는 것인지 헷갈렸다.
- **권한 정책**: 모든 화면이 로그인 필수(로그인 화면 제외). 관리자 메뉴는 role=admin에만 렌더링하며 서버 API도 이중으로 검사합니다.
- **터치 크기**: 터치 기기에서 누르는 자리는 40~44px 이상 — 뷰어 헤더 ★·파일명, 아래 도구막대 버튼, 파일 트리 줄과 ⋯, 목차 항목, 휴지통의 [복원]·[영구 삭제], 서랍 ☰. PC 밀도는 그대로 둔다(`touch:` 변형만 키운다).
- **반응형 기준**: md(768px) 미만에서 레일은 하단 탭 또는 햄버거 드로어로, 편집기 분할 화면은 탭 전환(에디터/미리보기)으로 대체합니다.
- 화면별 상세 구성·동작은 다음 단계인 화면설계서에서 다룹니다.

## 탭 바 + 분할 보기 (2026-08-27, v0.15)

서버 변경 없는 클라이언트 확장. **"열려 있다"(탭)와 "보이고 있다"(분할)를 분리**하는 것이 핵심 설계.

**탭 바 (SCR-153, 항상 표시)**
- 본문 영역 맨 위 한 줄. 문서를 열면 탭이 쌓이고, 이미 열린 문서는 그 탭으로 전환. 탭 클릭 = 전환, 호버 시 × = 닫기, 넘치면 탭 바 안에서 가로 스크롤.
- 몰입 모드에서는 탭 바도 숨긴다 (몰입 모드의 약속: 본문만).
- 탭·분할 상태는 **기기마다 기억한다**(v0.43, localStorage `dv_workspace:{userId}` — 탭 최대 20개·칸·활성 칸·분할 비율). 폰과 PC는 화면이 달라 열어 두는 문서도 달라서 서버에 두지 않는다(사용자 결정). 새로고침하면 그대로 돌아오고, 주소의 `/f/{id}`가 목록에 없으면 그 문서를 더해 연다. 지워졌거나 권한이 없어진 문서는 조용히 뺀다. URL 라우팅은 기존 그대로 활성 문서만 `/f/{id}`. **되살린 직후 주소를 활성 문서의 `/f/{id}`로 맞춘다**(2026-10-19) — 홈 화면 앱은 다시 켜면 시작 주소 `/`에서 열려, 화면은 문서인데 주소는 "문서 없음"이었고, 그 뒤 뒤로가기(브리핑 기사 시트의 [목록] 등)가 `/`로 돌아가 문서를 전부 닫았다.

**분할 (SCR-154)**
- 배치 규칙: **보던 문서는 제자리, 새 문서가 새 칸으로.** 진입은 파일 컨텍스트 메뉴(⋯/우클릭)의 "분할로 열기"와 PC의 Alt+클릭 (Ctrl+클릭은 다중 선택이 선점).
- 데스크톱(768px 이상): 프리셋 — 2개=좌우, 3개=좌1+우2, 4개=2×2 (상한 4). 주 구분선 드래그로 비율 조절(20~80%).
- 모바일(768px 미만): **상하 2분할까지만**. 3번째부터는 탭 대기.
- 활성 칸: 마지막에 조작한 칸에 강조 테두리. 탭 클릭·단축키는 활성 칸에 적용. 이미 화면에 있는 문서의 탭을 누르면 그 칸을 활성화.
- 자리 바꾸기: 2분할일 때 구분선 가운데의 ⇄ 버튼 (경우의 수가 하나라 버튼이 드래그보다 빠름). 탭 드래그 배치는 후속(v2).
- 칸 닫기: 각 칸의 × 는 칸만 닫고 탭은 남는다. 탭 × 는 문서를 완전히 닫는다.
- 각 칸은 독립 뷰어 — 글자 배율·스크롤·목차·편집이 문서별로 따로. 분할 중 E(편집)는 활성 칸 자리만 편집기로 바뀐다 (왼쪽 보면서 오른쪽에 쓰기).

## 분할 컨트롤러 + 모바일 UX 재편 (2026-08-28, v0.16)

**원칙**: 모바일의 본질은 읽기다 — **크롬(UI)은 기본적으로 안 보이고, 부르면 엄지 앞(바텀 시트)에 온다.** 조작 패러다임은 기기 특성(터치/PC, CSS pc:/touch: 변형과 같은 판정)으로 가른다.

**분할 컨트롤러 (SCR-155, 전 기기)**
- 구분선의 ⇄/⇅ 마이크로 버튼을 없애고 **알약 손잡이**로 교체. 손잡이 **탭 = 컨트롤러 팝업**: 비율 프리셋 3개(왼/위 크게 · 반반 · 오른/아래 크게) + 자리 바꾸기(2칸일 때) + 분할 해제(활성 칸만 남김).
- 폰에서 원하는 비율은 연속값이 아니라 이산 선택이라는 판단 — 정밀 드래그를 기본 경로에서 제외. **드래그는 보조**로 유지하되 보이지 않는 확장 터치 존(±12px)으로 잡기 쉽게. 탭/드래그 구분은 이동 거리 임계값.
- ⋯ 메뉴에 **"분할 보기"**: 이미 열린 탭끼리 분할. 대기 탭이 하나면 즉시 분할, 여럿이면 선택 대화상자. (트리의 "분할로 열기"=새 문서, ⋯의 "분할 보기"=열린 문서 — 진입점의 역할 분담)

**모바일(터치) 재편**
- **크롬 자동 숨김**: 본문을 아래로 스크롤하면 헤더·하단 도구막대가 접히고, 위로 긁거나 문서 상단 근처(48px)면 복귀. 편집 모드·몰입 모드는 예외. 화면 맨 위에 **읽기 진행률 줄**(2px, 우리가 그리는 형식만 — HTML은 iframe이라 전체 높이를 모름).
- **탭 바 제거 → 문서 스위처 시트**: 터치에서는 상단 탭 바를 렌더링하지 않는다. 헤더의 파일명이 버튼(▾)이 되어 **열린 문서 목록 바텀 시트**를 연다(항목: 이름·활성 표시·분할로 열기·닫기). **헤더 좌우 스와이프**로 이전/다음 문서 전환.
- **바텀 시트 통일**: ⋯ 메뉴와 목차(SCR-151)를 터치에서는 팝오버/좌측 드로어 대신 화면 하단에서 올라오는 시트로. safe-area 여백 포함.
- **이어 읽기 첫 화면**: 터치에서 열린 문서가 없을 때, 안내 문구 대신 **최근 열람 카드**(최대 3개, 마지막 열람 시각 표시)를 보여준다. 서버에 저장된 열람 기록을 그대로 활용.
- 하단 고정 통합 바는 **채택하지 않음** — 자동 숨김 크롬 + 시트가 같은 목적(엄지 존)을 비용(키보드·safe-area·분할 간섭) 없이 달성.
  - _v0.53에서 뒤집음_: 하단 **탭 바**(SCR-102)를 채택했다 — 통합 도구 바가 아니라 섹션 전환용이고, 읽을 때는 크롬과 함께 숨어 비용이 없다. 아래 "앱 구조 재설계 — 안 B" 참조.

**문서 내부 링크 (같은 릴리스)**
- md 문서 속 상대 경로 링크(`[이름](부록/용어집.md)`)는 브라우저 이동 대신 **그 파일을 탭으로** 연다. Alt+클릭 = 분할로. 링크를 품은 문서의 폴더에서 출발해 `../`·하위 폴더명을 클라이언트가 트리에서 풀며, 서버 변경 없음.
- 줄 번호 앵커(`#L16-L26`)가 붙으면 파일을 열고 **그 줄로 스크롤 + 형광펜 하이라이트** (코드 뷰어).
- 대상이 트리에 없으면(업로드 범위 밖·공유 문서 기준) "연결된 파일을 찾을 수 없습니다" 토스트. 외부 URL(`http…`)과 `#제목` 앵커는 기존 브라우저 동작 그대로.

## 읽는 흐름 개선 (2026-08-31, v0.17)

서버 변경 없는 클라이언트 확장. "설명 md + 대상 코드(html)"를 나란히 읽는 흐름을 목표로 한다.

**코드로 보기 (SCR-150 확장)**
- ⋯ 메뉴에 **"코드로 보기 ↔ 문서로 보기"** 토글. md·html·텍스트를 렌더링 대신 코드 뷰어(문법 강조 + 줄 번호)로 보여준다. 같은 본문을 보여주는 방식만 바꾸는 것이라 서버·저장과 무관, 상태는 세션 한정.
- **줄 번호 앵커(`#L16-L26`)가 붙은 링크로 열리면 자동으로 코드 보기** — 줄을 가리키는 링크는 "코드를 보라"는 뜻으로 해석한다. 이로써 html 대상 줄 앵커도 동작하게 된다 (기존에는 렌더링돼 버려 줄 하이라이트가 불가능했다).
- 코드 보기 중에는 목차 버튼을 숨기고, 읽던 위치 저장도 멈춘다 (검사용 임시 모드이지 읽기 모드가 아니다 — 렌더링 보기의 읽던 위치를 덮어쓰지 않게).

**탭 우클릭 메뉴 + Alt+클릭 (SCR-153 확장, PC 전용)**
- 탭 우클릭 → 컨텍스트 메뉴: 분할로 열기 / 닫기 / 다른 탭 모두 닫기 / 오른쪽 탭 모두 닫기. 일괄 닫기에 미저장 문서가 섞여 있으면 확인 한 번.
- **Alt+클릭 = 분할로 열기** — 트리·md 링크와 같은 문법을 탭에도 준다 (배울 게 늘지 않게 문법 통일).

**탭 드래그 배치 (SCR-153·154, v0.15에서 "후속(v2)"로 미뤘던 것)**
- 탭을 끌어 **탭 바 안에 놓으면 순서 바꾸기**, **본문 영역에 놓으면 배치**: 기존 칸 위 = 그 칸에 표시(이미 다른 칸에 보이는 문서면 두 칸을 맞바꿈), 오른쪽 끝(세로 분할이면 아래 끝) 스트립 = 새 칸으로 분할.
- 드래그 중에만 본문 위에 드롭 존 오버레이를 깐다 — iframe(HTML·PDF)이 드래그 이벤트를 삼키는 문제를 드래그 막(비율 드래그와 같은 수법)으로 푼다. 터치에는 탭 바가 없으므로 PC 전용.

**분할 구분선 히트 존 보정 (SCR-155)**
- 구분선의 넓은 투명 히트 존(±12px)이 왼쪽 칸의 세로 스크롤바를 덮어 스크롤바를 집기 어려웠다. **PC(정밀 포인터)에서는 히트 존을 왼쪽(첫 칸 쪽)으로 확장하지 않는다** — 스크롤바가 구분선에 붙는 쪽은 왼쪽뿐이고, 넓은 존은 애초에 손가락용이다. 터치는 그대로 ±12px.

**단축키 레지스트리 (도움말 화면은 후속)**
- 단축키·제스처 정의를 `lib/shortcuts.ts` 한 곳에 모은다. 후속(설정 → 단축키 도움말, `?` 치트시트)이 이 목록을 읽어 그린다 — 도움말을 손으로 쓰면 반드시 낡는다 (ERD 이중 기재 원칙과 같은 이유).

## 정리하는 흐름 — 트리 폴더 선택 + 키보드 탐색 (2026-08-31, v0.18)

서버 변경 없는 클라이언트 확장. 다중 선택(Ctrl/Shift+클릭)과 트리 내부 드래그 이동(스프링 로딩 포함)은 기존 기능 — 이번에 더하는 것은 둘이다.

**폴더 선택 (SCR-110 확장, 목록 보기 전용)**
- 폴더 행 클릭 = **펼침 토글 + 선택**. 선택된 폴더는 파일처럼 강조되고, 패널의 **"+ 업로드" / "+ 폴더" / "폴더째 업로드"가 그 폴더를 대상**으로 동작한다 (기존에는 항상 최상위였고, 폴더 지정은 우클릭 메뉴로만 가능했다).
- 선택은 다른 폴더를 클릭하거나 트리의 빈 곳을 클릭하면 풀린다. 파일을 열어도 유지된다 — "이 폴더에서 작업 중"이라는 상태이지 일회성 지정이 아니다.
- 격자 보기(FileGrid)에는 적용하지 않는다 — 격자는 훑어보기 화면이고, 정리 작업은 목록에서 한다.

**키보드 탐색 (SCR-110 확장, PC)**
- 트리가 포커스를 받으면(클릭 또는 Tab): **↑/↓** 위아래 이동(펼쳐진 행 순서), **→** 폴더 펼치기·펼쳐져 있으면 첫 자식으로, **←** 폴더 접기·파일이면 부모 폴더로, **Enter** 파일 열기/폴더 토글+선택, **Space** 파일 다중 선택 토글, **F2** 이름 변경, **Delete** 삭제(파일=휴지통+실행 취소 토스트, 폴더=확인 대화상자 — 기존 삭제 흐름 그대로).
- 포커스 행은 얇은 테두리로 표시하고, 화면 밖으로 나가면 따라 스크롤한다. 이름 변경 입력 중에는 트리 단축키를 멈춘다.
- 새 단축키는 전부 `lib/shortcuts.ts` 레지스트리에 등록한다.

## 내 공간 — 테마 + 단축키 도움말 (2026-08-31, v0.19)

**앱 테마 프리셋 (SCR-141 확장)** — _v0.53부터 "명암 + 강조색"으로 단순화됨: 아래 "앱 구조 재설계 — 안 B" 절의 결정 4 참조_
- 앱 껍데기(레일·패널·탭·헤더)의 색을 프리셋으로 고른다: **미드나잇 블루(기본, 기존 색) · 그래파이트 · 딥 그린 · 오베르진 · 페이퍼(라이트) · 아이보리(라이트 웜)**.
- 구현 방식: Tailwind 4의 색 유틸리티가 CSS 변수를 참조하는 것을 이용해, **`[data-app-theme=…]` 아래에서 slate·sky 램프 변수만 재정의**한다. 컴포넌트의 클래스는 한 줄도 바꾸지 않는다 — 새 테마 추가 = index.css에 변수 블록 하나. 라이트 테마는 램프를 뒤집는다(어두움 기준으로 짜인 의미 체계 — `bg-slate-950`=앱 배경, `text-slate-100`=본문 — 를 그대로 유지하기 위해).
- 저장은 localStorage(`dv_apptheme`) — 보기 모드(list/grid)와 같은 "기기별 취향" 분류. 서버 설정이 아니므로 스키마 변경 없음. 라이트 테마는 `color-scheme: light`로 스크롤바·네이티브 컨트롤도 맞춘다.
- 코드 뷰어의 어두운 배경(에디터 관례)과 뷰어 본문 테마는 앱 테마와 독립 — "밝은 껍데기 + 어두운 본문" 조합도 가능하다.

**뷰어 테마 확장 (SCR-141)**
- 3종 → 6종: 라이트 · 세피아 · **북 그린(연녹 종이)** · **그레이(눈부심 줄인 연회색)** · 다크 · **나이트(부드러운 다크)**.
- 렌더러들의 다크 판정은 `theme === 'dark'` 직접 비교 대신 공용 `isDarkViewerTheme()`로 통일한다 — 테마를 더할 때 판정 누락이 안 나게. HTML 문서에 남기는 `data-theme` 표식은 기존 3값(light/dark/sepia) 계약을 유지하고 새 테마를 가장 가까운 값으로 접는다.
- 서버 zod enum·Drizzle enum도 함께 확장 (컬럼 자체는 text — 마이그레이션 없음).

**단축키 도움말 (SCR-145 신설) + 신규 단축키**
- `?` (또는 Ctrl+/) 어디서든 → 단축키·제스처 치트시트 오버레이. 설정 패널의 "단축키·제스처" 버튼도 같은 오버레이를 연다. 내용은 `lib/shortcuts.ts` 레지스트리를 읽어 그린다 (손으로 쓴 표 금지 — 레지스트리 원칙).
- 신규 단축키 (입력 중에는 무시): **E** = 활성 문서 편집 (⋯ 메뉴가 이미 "편집 (E)"라고 약속하고 있었으나 미구현이었다), **Z** = 몰입 모드 토글, **Ctrl+B** = 왼쪽 패널 접기/펴기(PC), **Alt+1~4** = 분할 칸 활성화.

## 모바일 크롬 — 오버레이 방식 정리 (2026-09-14, v0.21.2)

v0.21.0에서 크롬 자동 숨김을 **레이아웃 접기 → 오버레이 슬라이드**로 바꿨으나 문서에 반영되지 않아 여기서 정리한다. (위 v0.16 항목의 "헤더·하단 도구막대가 접히고"는 이 절로 대체된다.)

**현재 방식 (터치 전용, PC는 기존 흐름 유지)**
- 헤더·하단 도구막대는 `absolute` + `transform: translateY()`로 여닫는다. **본문 상자의 크기는 변하지 않는다** — 레이아웃이 안 바뀌므로 iframe 안 문서가 다시 그려지지 않고, 합성만 쓰므로 스크롤이 끊기지 않는다.
- 크롬이 본문 위에 겹치므로, **우리가 그리는 본문**(md·텍스트·코드·PDF)은 스크롤 컨테이너 안쪽에 상단·하단 여백(`touch:pt-14`/`pt-10`, `pb-24`/`pb-20`)을 둬 첫 줄·마지막 줄이 가리지 않게 한다.

**HTML(iframe)만의 예외 — 남의 문서에는 여백을 넣을 수 없다 (v0.21.2)**
- HTML은 남이 만든 문서를 iframe에 담는 유일한 경로라 안쪽에 여백을 줄 수단이 없다. 그대로 두면 문서가 가진 **자체 목차 버튼(`position:fixed; top:14px`)·상단 sticky 메뉴(`top:0`)가 우리 헤더 밑에 깔린다.**
- 그래서 **크롬이 떠 있는 동안에는 iframe을 헤더 높이(56px, 우리 본문의 `pt-14`와 같은 값)만큼 내려 둔다.** 크롬이 물러나면 0으로 돌아가 화면을 꽉 채운다. 미는 대상은 **스크롤 컨테이너**이고 크기는 그대로라 iframe은 다시 그려지지 않는다 (html은 이 상자로 스크롤하지 않아 부작용도 없다).
- 같은 이유로 **앱의 떠 있는 ☰ 드로어 버튼도 크롬과 함께 슬라이드**한다 — 크롬이 숨어 문서가 화면 맨 위까지 올라오면, 남아 있는 우리 버튼이 문서의 좌상단 고정 버튼과 정확히 겹친다.

**반응 즉시화 (v0.21.2)**
- iframe 심의 스크롤 보고를 400ms 디바운스 → **rAF 스로틀(프레임당 1회)**. 디바운스로는 손을 뗀 뒤에야 헤더가 튀어나왔다. 서버 저장은 부모가 따로 묶으므로 영향 없다.
- 판정은 프레임 단위 델타를 **같은 방향으로 누적**해서 내린다(방향이 바뀌면 0으로 리셋): 아래로 48px 누적 → 숨김, 위로 24px 누적 → 복귀(되돌리기가 더 쉬워야 한다). 문서 상단 근처(48px)는 항상 펼침.

## 바텀 시트 손잡이 제스처 (2026-09-14, v0.21.3)

- 터치의 세 시트(목차 SCR-151 · ⋯ 메뉴 SCR-150 · 문서 스위처 SCR-153)는 모두 위쪽에 **알약 손잡이**를 그려 왔으나 **장식일 뿐 아무 동작이 없었다.** 손잡이는 "끌 수 있다"는 약속이라, 그려 놓고 안 되면 없느니만 못하다.
- 손잡이를 끌면 시트가 **손가락을 그대로 따라** 내려온다(끄는 동안에는 전환을 끈다). 놓았을 때 90px 넘게 내려왔거나 아래로 튕겼으면(0.5px/ms) 닫고, 아니면 제자리로 돌아간다. 위로는 고무줄처럼 1/4만 따라온다 — 시트는 위로 더 열리지 않는다.
- 제스처는 **손잡이에만** 건다. 시트 본문은 세로로 스크롤되므로(`overflow-y-auto`) 본문에 걸면 스크롤과 끌기가 같은 손가락을 두고 다툰다. 손잡이는 스크롤할 것이 없는 자리라 다툼이 없다. 얇은 알약은 손가락으로 못 잡으므로 잡히는 영역을 위아래로 넓혀 둔다 (SCR-155의 히트 존과 같은 원리).
- `touch-none`을 걸어 브라우저가 이 끌기를 스크롤로 가로채지 않게 한다 — 가로채면 touchend 대신 touchcancel이 와서 제스처가 끊긴다(헤더 스와이프에서 얻은 교훈).
- 구현은 `lib/sheetDrag.ts`의 공용 훅 — 같은 동작을 세 곳이 쓰므로 공통화한다.

## 구글 드라이브 연동 (2026-09-16 설계 — 구현 보류)

**원칙** — 드라이브 문서는 **빌려 보는 것**이지 우리 것이 아니다. 사본을 만들지 않으므로 드라이브에서 고치면 다음에 열 때 바로 반영되고, 우리 디스크도 늘지 않는다. 대신 검색(SCR-170·API-081)·태그·버전·즐겨찾기·휴지통은 **걸리지 않는다** — 화면이 그 사실을 숨기지 않는다(뷰어 헤더에 "드라이브 문서" 표시, 편집·버전·태그 버튼은 아예 그리지 않는다).

**SCR-135 구글 드라이브 패널**
- 미연결이면 패널 자체가 레일에 안 나온다. 연결은 설정(SCR-146)에서만 — 기능 입구와 계정 연결을 섞지 않는다.
- 구성은 위에서부터 ① **[드라이브에서 열기]** 버튼(구글 피커 SCR-136을 띄운다) ② **최근 연 문서** 목록(DRIVE_RECENTS). 폴더 트리는 없다 — `drive.file` 권한으로는 드라이브 전체를 훑을 수 없고, 탐색·검색은 구글 피커가 맡는다.
- 최근 목록의 항목은 **바로가기**다. 한 번 고른 파일의 접근 권한은 계속 유효하므로 피커를 다시 거치지 않고 열 수 있다. 원본이 지워졌으면 열 때 "드라이브에서 찾을 수 없습니다"로 드러나고 그 자리에서 목록에서 지울 수 있다.
- 열면 기존 뷰어(SCR-150)를 **그대로** 쓴다. 탭·분할·목차·글자 크기·이어 읽기 모두 동일하게 동작한다 — 다른 렌더러를 만들지 않는다.

**SCR-136 구글 피커** — 구글이 제공하는 창이라 우리가 디자인하지 않는다. 우리 앱은 ① 단기 토큰을 건네고 ② 고른 결과(파일 ID·이름)를 돌려받을 뿐이다.

**SCR-146 구글 계정 연결 (설정 패널)**
- 연결 전: 무엇을 할 수 있게 되는지(드라이브 문서 열람)와 **무엇은 못 하는지**(우리가 드라이브 전체를 보지 못한다)를 먼저 적고 [구글 계정 연결] 버튼. 동의 화면은 팝업으로 연다.
- 연결 후: 연결된 이메일·연결 시각 + [연결 해제]. 해제는 구글 쪽 권한까지 회수하며, 최근 목록도 함께 지운다.
- 사용자마다 각자 연결한다. 남의 드라이브는 어떤 경우에도 보이지 않는다.

**SCR-304 자동 백업 (관리자)**
- on/off 스위치 · 실행 시각(0~23시) · 보관 개수 · **[지금 실행]** · 최근 실행 결과(성공/실패·시각·사유).
- 관리자 본인의 구글 계정이 연결되어 있어야 켤 수 있다. 연결이 없으면 스위치 대신 "먼저 설정에서 구글 계정을 연결하세요" 안내와 바로가기.
- 백업 내용물은 `data/` 전체(SQLite + 바이너리 원본)이며 `scripts/backup.sh`가 만들던 것과 같은 tar.gz다. **다른 점은 놓이는 곳뿐** — 서버 디스크가 아니라 드라이브라, VM이 통째로 사라져도 남는다.

## 크롬 추종 — 손가락을 따라 접힌다 (2026-09-16, v0.22.0)

v0.21.2의 판정(누적 48px → 숨김, 24px → 복귀)은 켜짐/꺼짐 둘뿐인 **토글**이었다. 손가락을 20px 밀면 아무 일도 없다가 48px을 넘기는 순간 200ms 동안 제 속도로 접혔다 — 모바일 크롬 주소창처럼 손가락에 붙어 있지 않았다. 시안 세 가지(임계값 토글 · 1:1 추종 · 1:1 + 붙임)를 폰에서 비교하고 셋째를 골랐다. 이 절이 v0.21.2의 "반응 즉시화"의 판정 규칙을 대체한다.

**방식 (터치 전용)**
- 크롬(헤더·하단 도구막대·☰ 드로어 버튼·HTML iframe 상자)은 **진행도 하나(0=펼침, 1=접힘)** 로 함께 움직인다. 스크롤 델타를 헤더 높이(56px)로 나눠 진행도에 더한다 — 민 만큼 그대로 접히고, 되올린 만큼 그대로 펴진다.
- **손을 떼면(스크롤 보고가 140ms 없으면) 가까운 쪽으로 붙인다.** 반쯤 접힌 채 두지 않는다 — 반만 보이는 목차 버튼은 눌리지도 않는다. 크롬 주소창은 스크롤 중에 누를 일이 없는 배경 UI라 반쯤 걸쳐도 되지만, 우리 ☰는 문서의 주요 조작이다. 순수 크롬 방식을 택하지 않은 이유.
- 붙이는 기준은 비대칭: 내려가는 중엔 절반을 넘겨야 접히고, 올라오는 중엔 1/4만 되돌아와도 편다 (v0.21.2의 48:24와 같은 의도 — 복귀가 더 쉬워야 한다). 문서 상단 48px 안에서는 항상 펼침, 문서 전환·편집기 진입 시 즉시 펼침은 그대로.
- 따라가는 동안에는 전환(transition)을 끈다 — 켜 두면 손보다 늦게 따라와 미끄러진다. 붙일 때만 200ms 전환.

**구현 결정 — React 상태가 아니라 DOM에 직접 쓴다**
- 스크롤 보고는 프레임마다 온다. 진행도를 React 상태로 들면 프레임마다 리렌더가 나서 스크롤이 먼저 끊긴다. 그래서 `lib/chromeCollapse.ts`가 진행도를 모듈 변수로 들고 등록된 요소들의 `transform`을 직접 쓴다. React가 알아야 하는 건 안착한 뒤의 켜짐/꺼짐뿐(aria·pointer-events)이라 그것만 훅으로 내보낸다. Workspace의 `chromeHidden` 상태와 뷰어의 `onChromeHint` 보고 경로는 없어졌다.
- 요소 등록은 안정적인 ref로 한다 — 리렌더마다 등록이 풀렸다 붙으면 진행 중인 전환이 끊긴다.
- "손을 뗐다"는 터치 이벤트가 아니라 **스크롤 보고의 부재**로 판정한다 — HTML 문서의 스크롤은 iframe 안에서 일어나 우리에게 터치가 오지 않지만, 보고가 끊기는 것은 어디서 스크롤하든 같다.

**HTML(iframe)의 한계 — 알고 둔 것**
- HTML은 크롬이 떠 있는 만큼 iframe 상자 자체를 내려 두므로(v0.21.2), 접히는 56px 구간에서 문서가 손가락 속도에 더해 위로 이동한다 — 글이 손가락보다 빨리 흐른다. 크롬 주소창은 접히면 화면이 넓어지는 것이라 내용이 제자리에 있지만, 우리는 문서를 옮기는 것이라 생기는 차이다. 대안(상자 크기를 키우기)은 iframe 재렌더로 스크롤이 끊기는 것이 v0.21.0에서 확인됐으므로 택하지 않는다. md·텍스트·코드·PDF는 여백이 고정이라 이 현상이 없다. 폰에서 실측해 거슬리면 HTML만 임계값 방식으로 되돌릴 여지를 남긴다.

## 시작 시간 측정 (2026-09-20, v0.36.0)

"첫 로딩이 길다"를 감이 아니라 숫자로. `lib/bootTiming.ts`가 시작 단계마다 걸린 ms를 모으고(`timed()`), 첫 화면이 다 그려지면(`finishBoot()`: 딥링크면 문서 본문까지, 아니면 트리까지) 브라우저의 네비게이션 시간(TTFB·다운로드)과 JS 파일 수·크기를 앞에 붙여 sessionStorage에 남긴다. 관리자 → 성능(SCR-306, v0.38.0에 설정 → 정보에서 이동)에 "이 기기의 이번 시작 시간" 표. 서버로 보내지 않는다 — 개인 기기 사정이다. 처방은 칸에 따라 다르다: TTFB가 크면 서버(e2-micro 콜드 스타트 → 헬스체크 핑), 다운로드가 크면 번들·압축(Caddy encode)·PWA 캐시, 요청 칸들이 크면 왕복 수(/bootstrap 합치기)·응답 크기(트리 스냅샷 먼저 그리기).

**요청별 분해 (v0.37.0).** 첫 측정에서 설정·트리 요청이 3.5초였는데 서버 로그는 3ms — 단계 표만으로는 "회선인지 폰인지"를 못 가른다. 그래서 시작 중에 나간 API 요청마다 브라우저의 Resource Timing으로 넷을 쪼개 두 번째 표에 보인다: 대기(보내기 전) → 응답(답을 기다린 시간) → 받기(다운로드) → 그 뒤(응답이 다 온 뒤 단계가 끝나기까지 = 폰이 바빠서 못 챙긴 시간). 서버가 실제로 일한 시간은 모든 `/api` 응답의 `Server-Timing: app;dur=…` 헤더로 따로 와서 응답 칸 옆 괄호에 적는다 — "응답 − 서버"가 곧 회선이다. 같은 작업에서 확실한 것부터 처리: Caddy `encode zstd gzip`(앱 JS 412KB → 약 1/3), `/assets/*`는 1년 immutable 캐시(재방문은 다운로드 0, 표에는 "캐시"로), `index.html`은 no-cache(새 배포가 바로 보이게), 요청 로그에서 `/health` 제외(도커 헬스체크가 30초마다 찍어 진짜 요청을 밀어냈다).

**남은 둘 (v0.39.0).** 인덱스 뒤 표: 전체 3.4초. (1) 서버 깨우기 — TTFB 610ms + `/auth/me` 서버 904ms(토큰 검사 하나가 로컬 1ms): e2-micro 1GB에서 한동안 안 쓰면 Node 메모리가 스왑으로 밀려나 첫 요청이 끌어온다. (2) `/tree` 받기 966ms — 목록 응답이 커서 회선을 독차지하는 동안 `/tags`·`/me/settings`(서버 7·11ms)가 정확히 그 뒤(1,474ms)에 끝났다. 처방: 트리 응답에서 파일마다 반복되는 기본값 state·빈 tags를 빼고 읽던 위치(JSON)는 싣지 않는다(API-021, 열 때 API-073 GET). 표에 "크기"(회선으로 받은 KB, 캐시면 "캐시") 칸을 더해 효과를 다음 표에서 본다.

**범인과 처방 (v0.38.0).** 두 번째 표에서 `/tree`가 서버 안에서 2,852ms, 그 뒤에 출발한 `/tags`·`/me/settings`는 서버 일감 2ms인데 3.5초를 기다렸다 — Node 한 줄 + 동기 SQLite라 느린 요청 하나가 나머지를 줄 세운다. 원인은 `files` 표를 처음부터 끝까지 훑는 목록 질의: 같은 행에 본문(content_text)이 있고 목록에 필요한 칸들이 본문 뒤에 있어서, 목록 한 번이 곧 DB 전체 읽기였다(로컬 92MB 재현: 42.8ms → 커버링 인덱스 후 2.8ms, 느린 디스크에서는 초 단위 차이). 처방: 목록 칸만 모은 커버링 인덱스 `files_owner_kind_idx`(ERD 참조) — 목록 질의가 본문을 아예 안 건드린다. 재발 대비로 서버가 `SLOW_REQUEST_MS`(0.5초) 넘게 일한 요청은 로그에 `[slow] GET /api/v1/tree folders;dur=… files;dur=… app;dur=…`로 남기고, `/tree`는 네 질의(folders·files·state·tags) 각각을 Server-Timing에 단다.

## 배움 카드 활용 ⑤ — 카드 지도 (2026-09-20, v0.34.0)

서랍의 세 번째 보기 "지도"(SCR-184). 점=카드, 선=연결 칸, 색=주제(주제 카드는 파랑, 주제 없음은 회색), **점선 점=연결 칸에는 있지만 아직 없는 카드**. cose 배치라 연결된 것끼리 모이고 외딴 카드는 밖으로 — 어디가 빽빽하고 어디가 비었는지가 자리로 보인다. 점을 누르면 아래에 제목·한 줄·연결 수 + [열기]; 없는 카드는 [빈 카드 만들기]. 검색어는 지도에도 적용된다. 손가락으로 끌어 옮기고 두 손가락으로 확대(cytoscape 기본).

- 라이브러리는 mermaid가 이미 끌어온 cytoscape — 직접 의존성으로만 올리고 지연 로드한다. 글자색은 앱 테마 변수(--color-slate-*)에서 읽는다(캔버스라 클래스가 안 먹는다).
- 연결은 제목뿐 아니라 별칭으로도 잇는다(연결 칸에 별칭을 써도 선이 생긴다). 같은 두 카드 사이 선은 하나.
- 서버 변경 없음 — API-111 목록으로 충분하다.

## 배움 카드 활용 ④ — 질문 때 카드 문맥 (2026-09-20, v0.33.0)

질문 패널(SCR-180)에서 질문 글·인용·드래그 문맥에 **내 카드의 제목·별칭이 나오면** 그 카드(최대 3장)의 한 줄 정의 + 본문 앞 400자가 LLM 시스템 프롬프트에 덧붙는다 — "이 사람은 이미 이걸 정리해 뒀다"를 알고 이어서 답하게. 같은 설명을 반복하지 않고, 카드가 틀렸으면 바로잡으라고 지시한다.

- **입력창 위 띠** "📚 내 카드 N장 함께 보냄 · [큐잉 지연 ✕] [링크 ✕]" — 무엇을 보내는지 모르게 하지 않는다. ✕는 이번 질문에서만 뺀다(`excludeCardIds`). 클라이언트가 서버와 같은 규칙(`mentions`)으로 미리 계산해 보여 주고, 서버가 다시 계산해 보낸다 — 화면은 예고, 서버가 결정.
- **답 아래 "📚 함께 본 카드: 링크 · 라우터"** — meta 이벤트의 cards를 답 id에 붙여 그린다. 누르면 그 카드. 저장하지 않으므로 지난 대화를 다시 열면 안 보인다(ERD 비고).
- 설정 → 배움 카드 → "질문할 때 관련 카드 함께 보내기"(USER_SETTINGS.ask_with_cards, 기본 켬). 비용은 카드 3장 × 수백 토큰.
- 주제 카드는 뺀다(요약이라 문맥으로 부적합). 영문 이름은 단어 경계에서만("link"가 "linked"에 안 걸리게).

## 배움 카드 활용 ③ — 복습 (2026-09-20, v0.32.0)

서랍 맨 위 띠 "오늘 복습 N장 · 내일 M장 [시작]" (없으면 "오늘 복습할 카드 없음 · 내일 M장", 둘 다 0이면 띠 없음). **SCR-186 복습 시트**: 앞면은 제목(+별칭 힌트), 누르면 뒤집혀 한 줄 정의 + 본문(md). [몰랐다 · 내일 다시] / [알았다 · N일 뒤] — 버튼에 다음 간격을 미리 적는다. 다 끝나면 "오늘 N장 끝 · 내일 M장"만 — 점수·연속 일수는 두지 않는다(공부가 게임이 되면 카드가 가벼워진다). [카드 열기]로 복습 중 카드로 갈 수 있다.

- 규칙은 라이트너 상자를 가장 단순하게: 몰랐다 → 1일, 알았다 → 두 배(2·4·8…60일 상한). 새 카드는 만든 다음 날 첫 복습에 들어온다. 하루 20장 상한.
- 상태는 USER_FILE_STATE(next_review_at·review_interval_days) — 카드는 파일이고 "얼마나 외웠나"는 사용자×파일 사실이라 즐겨찾기와 같은 자리.
- 채점을 하나라도 하면 닫을 때 띠를 다시 센다.

## 배움 카드 활용 ② — 문서 속 용어 밑줄 (2026-09-20, v0.31.0)

카드가 문서로 돌아온다. 문서를 열면 **내 카드의 제목·별칭이 나오는 자리에 점선 밑줄**(SCR-150 확장). 누르면 작은 창: 제목·종류·한 줄 정의 + [카드 열기] [이 용어 질문](그 용어를 인용으로 붙여 질문 패널을 연다 — 드래그 질문과 같은 자리). 본문 맨 위에 "📚 이 문서에 내 카드 N장 · 링크, 라우터" 한 줄.

- LLM 없음. 서랍 목록(API-111)의 제목·별칭을 Workspace가 한 번 받아 두고(카드가 바뀌면 다시) 뷰어에 넘긴다. 찾기는 출처 형광펜과 같은 코드(`lib/findQuote.ts` markTerms).
- **문단마다 첫 등장만** 밑줄 — 전부 치면 문서가 지저분해진다. 링크·코드 안은 건너뛴다. 긴 이름부터 잡아 "링크 계층 스위치"가 "링크"에 먹히지 않게. 영문·숫자 이름은 단어 경계에서만("link"가 "linked"에 안 걸리게). 상한 300개.
- 표시는 CSS Custom Highlight API — DOM을 안 건드려 React가 그린 노드와 다투지 않는다. API가 없는 브라우저(구형)는 밑줄 없음. 클릭 판정은 `caretPositionFromPoint`로 어느 범위 위인지 본다.
- HTML 문서는 심에 `docvault:terms`(부모→심) / `docvault:terms-found`·`docvault:term`(심→부모) 쪽지. 같은 알고리즘의 ES5 복사본.
- 카드 자신을 열었을 때 제 제목에는 안 긋는다. 주제 카드는 용어가 아니라 묶음이라 뺀다.
- 설정 → 배움 카드 → "문서 속 내 카드 용어에 점선 밑줄" (USER_SETTINGS.term_highlight, 기본 켬). 읽기 취향이라 기기가 아니라 사람에 붙는다.
- 시안에 있던 "카드 없는 용어 제안(회색 점선)"은 이 조각에 없다 — 한국어에서 "자주 나오는 용어"를 고르는 기준이 아직 없다.

## 배움 카드 활용 ① — 내보내기 (2026-09-20, v0.30.0)

카드가 쌓이면 카드로만 두기 아깝다 — 첫 출구는 가장 싼 것부터. 서랍 헤더 [내보내기] → **SCR-185 내보내기 시트**: 형식(용어집 md / Anki CSV) · 범위(전체 / 주제 칩 여러 개 / 주제 없음) · 어디로(md만: 내 파일에 넣기 / 다운로드) · **미리보기**(같은 API-118 GET을 텍스트로 받아 보여 준다 — 무엇이 나오는지 보고 누른다). 버튼 글자가 결과다: "용어집 7장 → 내 파일에 넣기", "Anki CSV 12장 다운로드".

- 내 파일에 넣기는 최상위 `용어집.md` **하나**를 만들고, 다시 내보내면 그 파일을 새로 쓴다(이전 판은 버전 기록) — 새 파일이 쌓이지 않게. 저장 뒤 그 파일이 열린다.
- 용어집 모양은 학습자료 `부록/용어집.md`와 같다(가나다 머리별 목록). 카드가 그 원천이 된다.
- Anki CSV는 가져오기 설정을 파일 머리에 싣는다(구분자·HTML) — 사용자가 Anki에서 설정을 만질 일이 없게.
- 카드가 0장이면 버튼 자체가 없다.

## 배움 카드 — 출처·연결 클릭 (2026-09-20, v0.29.0)

카드 뷰(SCR-150 확장)의 아래 두 줄이 글자에서 버튼이 된다. 서버 변경 없음.

- **출처 클릭** → 그 대화의 문서를 열고, 드래그했던 문장을 찾아 **형광펜 + 스크롤**. 출처 줄의 `(대화 #N)`만 열쇠로 쓰고 문서·문장은 API-105로 대화에서 다시 읽는다 — 출처 글자(문서명·80자 인용)가 낡아도 대화는 정확하다. 문서가 지워졌으면(대화의 fileId가 null) "출처 문서가 지워졌어요".
- **문장 찾기**는 번호가 아니라 글자로 한다 (`lib/findQuote.ts`). md는 굵게·링크로 한 문장이 여러 텍스트 노드로 쪼개지므로 노드를 이어 붙인 한 줄에서 찾고 되짚는다. 못 찾으면 앞 30자로 한 번 더, 그래도 없으면 문서만 열고 "문서가 바뀌었을 수 있어요"(설계 흐름 D — 카드는 멀쩡, 위치만 잃음). 형광펜은 CSS Custom Highlight API(DOM을 안 건드림), 없으면 `<mark>`.
- HTML 문서는 격리 iframe이라 부모가 본문을 못 만진다 — 심에 `docvault:find`(부모→심) / `docvault:found`(심→부모) 쪽지를 하나씩 더했다. 드래그 질문(`docvault:selection`)의 반대 방향. 같은 알고리즘의 ES5 복사본이 심에 있다.
- 출처로 연 문서는 읽던 위치 복원을 건너뛴다 (줄 앵커와 같은 규칙).
- **연결 클릭** → 그 이름(제목 또는 별칭)의 카드를 연다. 없는 카드는 "아직 없어요"만 — 빈 카드 만들기는 3판.

## 배움 카드 2판 둘째 조각 — 대화 통째로 카드로 (2026-09-20, v0.28.0)

한 대화에서 꼬리질문으로 여러 개념을 배웠을 때, 답마다 따로 저장하지 않고 한 번에. 설계 흐름 M(대화 정리)을 3판에서 당겨 왔다. 세 방식이 한 화면, 진입점 두 개다.

**SCR-180 질문 패널 (확장)** — 헤더에 [카드로](대화 전체가 재료 → SCR-183). 답마다 오른쪽 위 네모 = **답 골라 담기**: 하나라도 고르면 입력창 위에 "N개 답 골라짐 [해제] [한 장으로]" 띠. 네모는 평소엔 흐리게, 하나 고르면 전부 또렷하게 (파일 트리 선택 모드와 같은 규칙). 답 아래 [📚 카드로 저장]은 그대로.

**SCR-182 카드로 저장 (확장)** — 재료가 셋: 답 하나(개념 하나) · 고른 답들 · 대화 전체(둘 다 "아우르는 한 장" — 종류는 비교·절차처럼 여럿을 담기 좋은 모양). 머리에 "재료: …"를 적는다. 판단·합치기 흐름은 그대로.

**SCR-183 대화 정리 (오버레이, 신설)** — (v0.35.0에서 흐름 수정) 열면 먼저 **저장된 정리가 있나** 본다(API-116 GET). 있으면 바로 체크리스트, 없으면 **시작 전 선택 화면**: [개념별로 나누기](체크리스트로) / [전부 한 장으로](SCR-182로). 누르자마자 LLM을 부르지 않는다. 개념별은 두 단계 — 1단계 목록(몇 초, 초 카운터 표시) → 2단계 본문은 항목별로 뒤에서 채워지며 "본문 쓰는 중 N"이 줄어든다. 저장 버튼은 체크한 항목의 본문이 다 올 때까지 잠긴다. 목록 머리에 "정리 9/20 15:12 · 새 카드 7 · 이어쓰기 1 · [다시 만들기] [한 장으로 바꾸기]" 한 줄(머리와 목록의 구분선 역할). 정리 뒤 대화에 답이 붙었으면 노란 띠 "새로 정리". 결과는 대화에 저장되어 나갔다 와도 그대로이고, 카드로 저장하면 지워진다. 체크리스트: 항목마다 제목·종류·한 줄 + 배지 **"새 카드"** 또는 **"X에 이어쓰기"**(기존 카드와 같은 개념 — "개념 하나 = 카드 한 장" 원칙이 지켜지는 자리). 항목을 누르면 초안(새 카드: 별칭·주제·태그·연결·본문 / 이어쓰기: 무엇이 더해지나 + 다시 짠 본문)이 펼쳐진다. 기본은 전부 체크, 첫 항목만 펼침. 맨 아래 **주제 카드도 만들기**(선택, 기본 켬) — 대화 한 줄 요약 + 개념 카드들로 가는 연결. **버튼 글자가 곧 계약**: "카드 N장 만들기 + M장 이어쓰기 / 주제 카드 1장 포함". 저장은 한 트랜잭션(API-117)이고 토스트의 [되돌리기] 한 번으로 새 카드는 휴지통, 이어쓴 카드는 저장 전 버전으로 — 여섯 장을 하나씩 지우게 하지 않는다. 저장 뒤 주제 카드(없으면 첫 카드)가 열린다.

**SCR-181 서랍 (레일 📚)** — 카드만 보인다. 검색(제목·별칭·한 줄·태그), 주제별/최근 묶기, 종류 칩, [+ 빈 카드]. 카드를 누르면 뷰어에 열린다(카드는 트리에 없어서 요약에서 TreeFile을 만들어 연다). 카드가 저장되면 창 이벤트 `dv:cards-changed`로 목록을 다시 받는다 — 화면끼리 직접 잇지 않는다. 카드 우클릭(터치는 ⋯) → [삭제]는 파일 삭제(API-036)를 그대로 불러 휴지통으로 보낸다 — 확인 없이 보내고 토스트의 [실행 취소]로 복원한다(파일 트리와 같은 흐름). 카드도 files의 한 행이라 휴지통 목록·30일 자동 정리에 문서와 같은 규칙으로 걸린다.

**SCR-182 카드로 저장 (오버레이)** — 답 아래 [📚 카드로 저장]. ① 초안 로딩(AI가 초안 + 비슷한 카드 판단) → ② 비슷한 카드가 있으면: 두 카드 나란히 + AI 판단(관계·근거) + 선택 세 개(합쳐서 다시 짜기 / 따로 만들고 연결 / 기존 카드만 열기, AI 추천에 표시) → ③ 머리말(제목·종류·한 줄·별칭·태그·주제·연결) + 본문(자유 md) 확인 → 저장 → 카드가 열린다. 합치기: "무엇이 바뀌었나" + 지금/합친 뒤 나란히 + 지시 입력으로 다시 짜기 → 이대로 저장(버전 기록에 이전 판). PC 모달, 터치 전체 화면.

**카드 뷰 (SCR-150 확장)** — kind=card인 md는 머리말을 표로(제목·한 줄 콜아웃·별칭·종류·주제·태그), 본문은 md로, 아래에 연결·출처. [이어서 질문] 버튼. 드래그 질문은 문서와 똑같이 된다 — 카드가 카드를 낳는다. "코드로 보기"에서는 머리말이 글자 그대로 보인다.

## 뉴스 브리핑 (2026-10-01, v0.42.0)

설계 전문은 [뉴스브리핑_docvault_20261001.md](뉴스브리핑_docvault_20261001.md). 원래 별도 앱으로 기획한 "데일리 뉴스 브리핑"을 들인 것이다. **회차 하나 = 문서 하나**라서 보관함은 트리(`뉴스 브리핑/2026-10/…`), 검색은 커맨드 팔레트, 북마크는 즐겨찾기다 — 화면을 새로 만드는 것은 아래 셋뿐이다. 세 화면 모두 관리자 계정에만 있다(LLM 요금을 내는 사람).

**SCR-190 뉴스 브리핑 패널 (레일, "내 것" 묶음의 대화 아래, 신문 아이콘)**
- 맨 위 [브리핑 만들기]. 누르면 곧바로 진행 표시로 바뀐다 — "요약 중 6/12 · 2분 10초"(단계: 수집·분류·선별·요약·저장). 이미 도는 중이면(자동 실행 포함) 버튼 대신 그 진행이 보인다. 연달아 눌러도 하나만 돈다. (구독 실행이 도는 중에는 예외 — 진행 카드의 **[직접 만들기로 대체]**가 그것을 취소로 기록하고 시작한다. v0.50, 아래 "구독 생성 방식")
- 끝나면 토스트 "저녁판 164건을 만들었어요 [열기]", 실패면 패널에 빨간 한 줄로 이유가 남는다 ("출처 2곳 실패"는 눌러서 이름을 편다). 실패해도 직전 회차는 그대로다.
- 그 아래 "이번 달 ≈ $12.40 / $50", "자동: 꺼짐 (설정에서 켜기)" 또는 "자동: 다음 17:30".
- 최근 회차 10개(누르면 뷰어). [뉴스 브리핑 폴더 열기]는 내 파일 패널로 가서 그 폴더를 선택한다.
- 접이식 "실행 기록" — 최근 30회의 상태·건수·비용·걸린 시간·이유.
- 한도를 넘은 달에 [브리핑 만들기]를 누르면 "이번 달 한도($50)를 넘었어요. 그래도 만들까요?" 확인을 한 번 거친다.

**SCR-191 브리핑 뷰어 (뷰어 SCR-150 안, kind=briefing)**
- 머리: "10월 1일 저녁판" · 다룬 범위(12:00~17:30) · 기사 수 · 생성 비용(작게).
- 국내/세계 탭(기사 수 표시) → 대분류 칩(누르면 그 분야로 스크롤) → 중요도 필터 [전체 · 주요 이상 · 핵심만] + [모두 펼치기·접기]. 필터는 기기가 기억한다.
- 세부 분야 머리 아래 기사 줄: 중요도 배지(핵심=빨강 · 주요=주황 · 참고=회색 글자) + 제목 + NEW/업데이트. 누르면 그 자리에서 펼침: 요약 → 의미(강조 상자) → 언론사 · 시각 → [원문 보기](새 탭) → 같은 사건 다른 보도(언론사 이름 링크).
- 폰 우선: 표를 쓰지 않고 한 줄 한 기사. 터치 영역은 줄 전체.
- 색은 뷰어 테마(밝음·세피아·어두움…)를 따른다. md는 prose가 글자색을 정하지만 이 화면은 우리가 그려서 테마를 직접 받는다 — OS 다크 모드가 아니라 뷰어 테마 기준이다. 시각은 기기 시간대와 상관없이 한국시간으로 보인다(한국 뉴스 기준).
- 헤더 ⋯ 메뉴에서 편집은 빠지고 "코드로 보기"(원문 JSON)는 남는다. 본문이 브리핑 형식이 아니면(깨진 JSON·모르는 version) 코드 뷰어로 열고 "브리핑 형식이 아니에요" 띠.
- 즐겨찾기·태그·이동·속성(SCR-113)은 다른 문서와 같다. 삭제는 회차 문서가 트리에 없으므로 ⋯ 메뉴의 **[회차 삭제 (휴지통)]**(내 회차만, 확인 한 번) — 지우면 그날 그 회차를 자동·구독 생성이 다시 만든다(v0.51, 사용자 결정 2026-10-31).

**SCR-147 설정 → 뉴스 브리핑**

## 뉴스 브리핑 구독 생성 방식 (v0.50 — 설계 2026-10-27, 서버·화면 구현 2026-10-30)

설계 전문은 [뉴스브리핑_docvault_20261001.md](뉴스브리핑_docvault_20261001.md) "구독 생성 방식". 회차를 Anthropic API 대신 **서버가 켠 claude.ai 예약 작업**(사용자의 Claude 구독)이 만든다. 회차 문서·뷰어·묻기·카드는 바뀌지 않는다 — 화면이 달라지는 곳은 둘뿐이다.

**SCR-147 설정 → 뉴스 브리핑** (`BriefingSubscriptionSettings.tsx`, 블록은 비용 줄과 "앱 안 원문 보기" 사이)
- **자동 생성** 스위치의 설명이 구독 모드에서 바뀐다 — 「아래에서 켠 회차의 90분 전에 claude.ai 예약 작업을 켜고, 회차 시각 30분 뒤까지 완성본을 기다려요. 안 오면 패널에 알리고 [지금 만들기]로 만들 수 있어요 · 다음 예약 작업 10/30 05:00」. 구독 모드의 스위치는 AI 키 없이 켜진다.
- **이번 달 비용** 줄은 그대로 — 구독 모드에서는 뒤에 「(구독 회차는 $0으로, 비용에 쌓이지 않아요)」가 붙는다(구독 회차는 $0으로 쌓이지 않는다).
- **생성 방식** 라디오: ( ) 앱이 직접 만들기 (API) 「서버가 Anthropic API로 만들어요 — 회차마다 비용이 들고 월 한도가 있어요」 / ( ) 구독으로 받기 (Claude 예약 작업) 「정한 시각 90분 전에 서버가 claude.ai 예약 작업을 켜고, 완성본을 받아 저장해요 — 내 Claude 구독으로, 추가 비용 없음」. 회차 세 줄(켜기·시각)은 두 방식이 공유한다.
- **방식을 바꾸는 길** — 라디오를 "구독으로 받기"에 두어도 방식은 아직 바뀌지 않는다(열쇠·트리거가 없어도 라디오는 그 자리에 남고 아래 블록이 펼쳐진다). 라디오 아래 노란 줄이 상태를 말한다: 준비 안 됨 「아래 열쇠와 트리거를 준비하면 바꿀 수 있어요. 그동안은 앱이 직접 만들어요」 / 준비 됨 「열쇠와 트리거가 준비됐어요 — [연결 확인]이 "연결 확인됨"이면 바꾸세요」 + 단추 **[구독으로 바꾸기]**. 트리거 저장은 방식을 바꾸지 않는다 — 연결을 확인한 사람이 이 단추를 누른다. API로 되돌릴 때 예약 작업이 도는 중이면 확인창 「앱이 직접 만들기로 바꿀까요?」/「지금 도는 예약 작업은 취소로 기록되고 완성본을 받지 않아요. claude.ai의 세션은 스스로 멈추지 않으니 거기서도 꺼 두세요.」. 라디오 아래 상시 안내는 모드에 따라 — 구독일 때 「앱이 직접 만들기로 바꾸면 지금 도는 예약 작업은 취소로 기록되고 더 켜지지 않아요 — claude.ai의 예약 작업도 꺼 두세요. 열쇠·트리거는 남아 있어 다시 구독으로 바꾸면 바로 이어서 써요」, API일 때 「회차 켜기·시각은 두 방식이 함께 써요」.
- 펼쳐지는 블록(구독 상태 API-143을 못 읽으면 그 자리에 「구독 상태를 불러오지 못했어요 — <이유>」):
  - **연결 열쇠 (예약 작업이 docvault에 들어올 때)** — 미발급 「아직 발급하지 않았어요」 + [발급]. 발급 직후 **그 자리의 노란 상자**(모달이 아니다) 「이 창을 닫으면 다시 볼 수 없어요 — claude.ai 환경의 네트워크 시크릿(Bearer)의 헤더 값에 넣어 두세요」 + 열쇠 원문 + [복사]·[닫기]; 블록을 접어도(라디오를 API로) 원문은 사라진다. 닫은 뒤 「`dvt_8f3k…` · 발급 10/30 12:00 · 마지막 사용 10/30 05:31」 또는 「… · 아직 사용 안 함」, 단추는 [다시 발급]·[삭제]. [다시 발급] 확인창 「열쇠가 샌 것 같을 때만 하세요 — 새면 남이 가짜 회차를 보낼 수 있어요. 지금 열쇠는 바로 쓸 수 없게 되고, claude.ai 환경의 DOCVAULT_TOKEN도 새 값으로 바꿔야 해요.」(+ 도는 중이면 「지금 도는 예약 작업은 옛 열쇠라 완성본을 보내지 못해요.」). [삭제] 확인창 「예약 작업이 더는 docvault에 들어올 수 없고, 생성 방식은 "앱이 직접 만들기"로 돌아갑니다.」(+ 도는 중이면 「지금 도는 예약 작업은 취소로 기록돼요.」).
  - **예약 작업 트리거 (docvault가 예약 작업을 켤 때)** — 설명 「claude.ai에서 예약 작업을 만들면 나오는 트리거 주소와 토큰. 주소는 `https://api.anthropic.com/v1/claude_code/routines/<id>/fire` 모양만 받아요. 저장하면 값은 다시 보이지 않아요」. 주소·토큰 두 칸(자리글은 주소 모양·「트리거 토큰」, 설정 뒤 「바꾸려면 새 주소」·「바꾸려면 새 토큰」) + [저장](설정 뒤 [바꾸기]·[지우기]). 저장 토스트 「트리거를 저장했어요 — [연결 확인]으로 시험해 보세요」, 상태 「설정됨 ✓」, 복호화 실패(`triggerBroken`)면 「트리거를 읽을 수 없어요(서버 비밀키가 바뀜) — 다시 넣어 주세요」, 주소 모양이 틀리면 「주소: <이유>」. [지우기] 확인창 「서버가 예약 작업을 켤 수 없게 되고, 생성 방식은 "앱이 직접 만들기"로 돌아갑니다.」(+ 도는 중이면 「지금 도는 예약 작업은 취소로 기록돼요.」).
  - **설정 체크리스트 펼치기/접기** — 여섯 단계(선행 조건 표시는 없다 — 순서가 곧 조건): ① 위에서 연결 열쇠를 발급해 두세요 (한 번만 보여요) ② claude.ai → 설정 → Claude Code → 환경(기본 브랜치 main)에 두 가지 — 네트워크 시크릿(Bearer · 허용된 웹사이트 = docvault 호스트 · 경로 접두사 `/api/v1/briefing/jobs/` · 헤더 Authorization/Bearer/값 = 발급한 열쇠, [복사] 둘) + 환경 변수 `DOCVAULT_URL=<주소>`([한 줄 복사]); 「열쇠는 환경 변수에 넣지 않아요 — 그 화면은 환경을 쓰는 모두가 값을 볼 수 있어요」 ③ 같은 환경의 네트워크 허용 목록에 docvault 주소와 수집 목록의 언론사 도메인을 넣어요 [도메인 n곳 복사] ④ 예약 작업을 만들어요 — 저장소는 docvault, 일정은 비워 두고(서버가 켜요), 지시문은 아래 한 줄: (API-143 `checklist.taskPrompt`) [지시문 복사] ⑤ 예약 작업의 트리거 주소와 토큰을 위 칸에 저장해요 ⑥ [연결 확인]을 눌러 "연결 확인됨"이 나오면 위의 [구독으로 바꾸기]를 눌러요. 복사 단추는 셋(docvault 주소·도메인·지시문) — 환경변수 이름은 칩으로 보여 주기만 한다.
  - **[연결 확인]** — 트리거가 없으면 잠김, 누르면 「확인하는 중…」. 결과 다섯(API-143 `lastPingResult`, `PING_LABEL`): `fired` 「켰어요 — 세션을 기다리는 중」 / `ok` 「연결 확인됨」 / `trigger_failed` 「예약 작업을 켜지 못했어요 — 트리거 주소·토큰을 확인하세요」 / `token_invalid` 「연결 열쇠가 맞지 않습니다」 / `no_request` 「아직 연결 기록 없음 — 세션이 docvault를 부르지 않았어요 (네트워크 허용 목록·환경변수를 확인)」. `no_request` 외 넷은 뒤에 " (HH:MM)". 아래 「예약 작업을 한 번 켜서 지시서만 받아 가게 해요. 회차는 만들지 않아요」. 결과는 **5초마다 최대 6분** 다시 읽는다(`BRIEFING_PING_POLL_MS`·`BRIEFING_PING_WAIT_MS`).
  - **시각과 최근 N회** — 「예약 작업은 회차 90분 전에 켜지고, 마감은 회차 30분 뒤예요 — 아침 06:30 → 05:00 켜기 · 점심 11:30 → 10:00 켜기 · …」(켠 회차가 없으면 「켜 둔 회차가 없어요」). 「최근 N회: 성공 n · 도착 안 함 n · 실패 n · 평균 n분」(0회면 숨김; 평균은 지시서를 받아 간 때부터) + 힌트 `earlier` 「— 마감에 자주 몰려요. 수집 목록의 출처나 켜 둔 분야를 줄여 보세요」 / `later` 「— 넉넉히 끝나요. 회차 시각을 30분 늦추면 더 최근 기사까지 담을 수 있어요」.

**SCR-190 브리핑 패널**
- 구독 실행이 도는 동안 **진행 카드**(`RemoteProgressCard`): 머리글은 지시서를 받아 가기 전 「예약 작업을 켰어요 — 세션을 기다리는 중」, 받은 뒤 세션이 보고한 세부 단계(「요약 12/40」 등, 없으면 「구독 작업 중」) + 「· 12분 3초」(지시서를 받아 간 때부터); 막대; 단계 줄 수집 · 분류 · 선별 · 원문 읽기 · 웹 검색 · 요약 · 보기 쓰기 · 검수(지난 단계에 ✓); 작은 줄 「구독 작업 중 · 05:00 시작 · 마감 07:00 · 마감까지 안 오면 알려 드려요. 멈추려면 claude.ai의 예약 작업에서」; [진행 기록 접기/보기](기본 펼침, 줄마다 HH:MM — 예약 작업이 보낸 API-152); 오른쪽 끝([중지] 자리) **[직접 만들기로 대체]** — 설계 문서의 "마감 전에 직접 만들기"다. 확인창 「예약 작업을 기다리지 않고 직접 만들까요?」/「지금 도는 예약 작업은 취소로 기록되고 늦게 온 완성본은 받지 않아요. 아침판을 앱이 API로 만들어요(이 회차만 비용). claude.ai의 세션은 스스로 멈추지 않으니 거기서도 꺼 두세요.」, AI 키가 없으면 잠김. **[중지]는 없다**(docvault가 claude.ai 세션을 멈출 수 없다 — 멈추려면 claude.ai에서). 구독 실행은 **15초**마다 상태를 다시 읽는다(`BRIEFING_REMOTE_POLL_MS` — API 실행의 2초와 다르다).
- 마감까지 안 오면 **알림 띠**(기존 노란 띠 패턴): 「아침판이 도착하지 않았어요 (마감 07:00) [지금 만들기]」. [지금 만들기]는 API 방식으로 그 회차 이름으로 만든다(API-132 `slot`; 그 회차만 비용, 월 한도 확인은 그대로). 어떤 실행이든 도는 중이면 띠는 숨고, AI 키가 없으면 단추가 잠기며, 같은 실행의 "최근:" 줄은 겹치니 숨긴다. 끝나는 것을 보고 있었으면 토스트 「아침판이 마감까지 도착하지 않았어요 — [지금 만들기]로 만들 수 있어요」. 앱 안 띠이고 **푸시가 아니다** — 웹 푸시는 설계 문서의 2차 그대로.
- AI 키가 없을 때 머리의 안내는 구독 모드에서 「AI 키가 없어 [지금 만들기]는 쓸 수 없어요. 구독으로 받는 회차는 그대로 와요.」.
- **실행 기록** 세 형식 — 성공 「구독 · 아침판 137건 · 구독 생성 · $0 · 52분 · 검사에서 3건 뺌 · 10/30 06:40」(API 실행의 "n초"는 없다; 분은 지시서를 받아 간 때부터) / `missing` 「구독 · 아침판 도착 안 함 — <이유> · 10/30 07:00」(노랑) / 도는 중 「구독 · 예약 작업이 만드는 중 · 10/30 05:00」.
- **바닥**과 **예정 카드**: 바닥 「구독으로 받기 · 다음 예약 작업 05:00 아침판」; 오늘의 예정 카드 「아침판 (구독)」/「05:00에 예약 작업 시작 · 06:30 회차」.

- 설정 패널(288px)이 "내 취향"과 "운영 콘솔"을 섞는다 — 세로 길이 일반 ~1,200px, 관리자 1,900~2,800px(폰 3~4화면). 비밀번호를 바꾸러 와도 뉴스 브리핑 운영 블록을 지나야 한다.

- 앱 테마 = `scheme`(system/light/dark) × `accent`(sky/emerald/violet/amber). `lib/appTheme.ts`가 localStorage `dv_apptheme`에 `{scheme, accent}` JSON으로 저장하고(옛 프리셋 이름은 읽을 때 매핑), `<html>`에 `data-scheme`(light만; 어두움은 속성 없음)·`data-accent`(sky 제외)를 적는다. `system`은 JS가 `prefers-color-scheme`로 풀어 적고, 바뀌면 바로 따라간다. 테마가 바뀌면 `dv:apptheme` 창 이벤트. 뷰어 테마 6종·코드 뷰어 항상 어두움은 그대로.
- 색 변수는 `index.css` 한 곳: `[data-scheme='light']`가 slate와 의미색(amber·red·emerald·teal) 램프를 뒤집고, `[data-accent=…]`가 sky 램프를 고른 색으로 바꾼다(밝음은 그 색을 뒤집은 램프). 뒤집는 규칙 — 글자용 50~400 ↔ 바탕용 950~700을 서로 바꾸고 **500·600(단색 버튼)은 그대로** 두어 버튼 위 흰 글자가 안 죽게 한다. Tailwind의 `dark:` 변형도 기기 설정이 아니라 `data-scheme`를 따르게 재정의.
- 의미 토큰은 Tailwind 색 램프로 노출한다(`@theme inline`): `accent-*`(=sky) `warn-*`(=amber) `danger-*`(=red) `good-*`(=emerald) `card-*`(=teal, 배움 카드·물어보기). **새 코드는 램프 이름이 아니라 이 뜻으로 쓴다**(`bg-accent-600`, `text-warn-400`). 옛 클래스는 그대로 두되 손대는 파일에서 만나면 바꾼다 — 컴포넌트 클래스를 한 줄도 바꾸지 않는 v0.19 원칙을 보조색까지 넓힌 것.
- 기기 판정은 `lib/device.ts`의 상수 `IS_TOUCH`·`IS_PC`(한 번만 잼 — 기기 특성은 실행 중 안 바뀜)와, 문서 안 스크립트에 문자열로 심을 때 쓰는 `PC_MEDIA_QUERY`. `pc:`/`touch:` CSS 변형과 같은 질문이다. 화면 너비(`min-width: 768px`)로 가르는 `isWide`는 레이아웃 판정이라 별개로 둔다(Workspace).
