# 뉴스 브리핑 구독 생성 방식 — 1회 시험 안내 (2026-10-27)

설계: [docs/design/뉴스브리핑_docvault_20261001.md](design/뉴스브리핑_docvault_20261001.md) "구독 생성 방식 — 시험". 앱 코드는 바꾸지 않고, **claude.ai 예약 작업(클라우드 세션)이 저장소의 스킬로 브리핑 회차 하나를 만들어 낼 수 있는지**를 손으로 1회 돌려 본다. 모델 구성 A(전부 Opus)와 B(분류·선별은 Sonnet)를 각각 한 번씩.

이 시험이 쓰는 것은 **Claude 구독 사용량**이다. 평소 Claude를 많이 쓰는 날은 피한다. API 비용은 들지 않는다.

## 0. 이 시험으로 알게 되는 것

| 기준 | 합격 | 어디서 보나 |
|---|---|---|
| 걸린 시간 | 75분 이내 | 세션 시작~`result.json` 커밋 시각 |
| 구독 사용량 | 1회 ≈ 주간 한도 3% 이하 | claude.ai 설정 → 사용량, 실행 전후 비교 (두 구성 각각) |
| 정확도 | 무작위 10건 원문 대조, 틀린 사실 0건 | `result.json` 기사 10건의 `url`을 열어 요약과 대조 |
| 체감 품질 | 같은 시간대 API 회차와 같거나 나음 | 두 JSON을 나란히 — 비교는 Claude Code 세션에 맡겨도 된다 |

## 1. 준비 — docvault 쪽 (5분)

1. 저장소 브랜치 `claude/keen-hawking-ssl55j`(PR [ehdwn009/docvault#15](https://github.com/ehdwn009/docvault/pull/15))가 스킬·CLI를 담고 있다. 시험은 이 브랜치에서 한다. 아직 main에 합치지 않아도 된다. **실전(6절)은 main에 올려 배포한 뒤**에 한다 — 서버 쪽(4단계)이 main에서 돌아야 지시서를 내주고 완성본을 받을 수 있다.
2. (선택) 실제 수집 목록으로 시험하려면 앱에서 `뉴스 브리핑/수집 목록.json`을 열어 내용을 복사해 저장소에 `.briefing-job/sources.json`으로 둘 수 있다 — 세션에게 "수집 목록은 `.briefing-job/sources.json`"이라고 말하면 된다. 없으면 코드의 기본 목록(27곳 + 꺼진 후보)으로 돈다.
3. 비교 대상 API 회차: 시험을 돌리는 날 아침 회차(또는 [브리핑 만들기] 한 번)의 JSON. 회차 화면 ⋯ → "코드로 보기"에서 복사하거나 [다운로드].

## 2. 준비 — claude.ai 쪽 (10분, 처음 한 번)

Claude Code on the web(claude.ai/code) → 환경(Environment) 설정:

1. **저장소**: `ehdwn009/docvault` 연결, 기본 브랜치는 시험 브랜치.
2. **네트워크 (Network access)**: `Custom`으로 두고 아래를 넣는다. 세션이 밖으로 나가는 요청은 이 목록을 거친다 — 없는 곳은 403이 난다.
   - `registry.npmjs.org` (의존성 설치)
   - 수집 목록 언론사 도메인 전부 — 세션에서 `npm run briefing:job -w server -- instruction .briefing-job` 뒤 `.briefing-job/instruction.json`의 `allowedDomains`가 그 목록이다. 처음엔 `Full`(모든 도메인 허용)로 시작해 동작을 확인한 뒤 좁혀도 된다.
   - 실전 단계(6절)에서는 docvault 도메인(`https://내이름.duckdns.org`)도 — **이번 시험에는 필요 없다.**
3. **비밀값**: 이번 시험에는 **없다**(docvault에 보내지 않는다). 실전 단계(6절)에서 `DOCVAULT_URL`·`DOCVAULT_TOKEN`을 넣는다.
4. **권한 설정(권장)**: 저장소에 `.claude/settings.json`을 아래 내용으로 두면 세션이 명령마다 멈춰 사람을 기다리지 않는다. (이 파일은 Claude Code 자체 설정이라 이 세션이 만들지 않았다 — 직접 만들어 커밋한다.)

```json
{
  "permissions": {
    "allow": [
      "Bash(npm ci:*)",
      "Bash(npm run briefing:job:*)",
      "Bash(curl -sS:*)",
      "Bash(git add:*)",
      "Bash(git commit:*)",
      "Bash(git push:*)",
      "Bash(git checkout:*)",
      "Bash(mkdir:*)",
      "Bash(cat:*)",
      "Bash(ls:*)",
      "Bash(wc:*)"
    ]
  }
}
```

## 3. 실행 (구성마다 한 번)

claude.ai/code에서 그 환경으로 **새 세션**을 열고 아래를 붙여 넣는다. 예약 작업(routine)을 만들어 "지금 실행"해도 같다 — 이번엔 손으로 돌려서 시작·끝 시각을 직접 적는 편이 비교에 낫다.

**구성 A**
```
BRIEFING_JOB_MODE=test 로 briefing-subscription 스킬을 실행해.
지시서는 npm run briefing:job -w server -- instruction .briefing-job --hours 24 --slot morning --config A 로 만들어.
결과는 브랜치 claude/briefing-test-<오늘날짜>-A 에 커밋·push 해.
시작 시각과 끝 시각(UTC)을 마지막에 알려 줘.
```

**구성 B** — 위에서 `--config B`, 브랜치 `…-B`. 스킬이 B를 읽으면 분류·선별 하위 에이전트를 Sonnet으로 돌린다.

### 두 번째 시험 (2026-10-30 추가 — 스킬 v2: 웹 검색 재료·후보 출처 점검·전수 검수)

1회 시험(구성 A)에서 시간(12분)·사용량(주간 약 1%)은 넉넉히 통과했지만, 클라우드에서 연합뉴스·동아일보·BBC·NYT가 막혀(403) 국내 기사가 얇았다. 스킬 v2는 막힌 기사를 웹 검색으로 채우고(구독이라 전부), 꺼 둔 후보 출처 중 열리는 곳을 재고, 핵심·주요를 전부 검수한다. API 회차와 **같은 시간 범위**로 돌려야 비교가 된다 — 그날 아침 API 회차의 범위(보통 전날 06:30 ~ 당일 06:30)를 넣는다. 범위가 오래될수록 피드에서 기사가 빠지므로, **그날 오전 중**에 돌리는 것이 좋다.

```
BRIEFING_JOB_MODE=test 로 briefing-subscription 스킬을 실행해.
지시서는 npm run briefing:job -w server -- instruction .briefing-job --since <전날>T06:30+09:00 --until <오늘>T06:30+09:00 --slot morning --config B --all-candidates 로 만들어.
결과는 브랜치 claude/briefing-test-<오늘날짜>-B 에 커밋·push 해.
시작 시각과 끝 시각(UTC)을 마지막에 알려 줘.
```

`<전날>`·`<오늘>`은 날짜로 바꾼다(예: `2026-10-30T06:30+09:00`). 실행 전후 사용량 %는 1회 때처럼 적는다. 웹 검색과 전수 검수가 늘어 1회보다 오래 걸리고 사용량도 더 쓸 것이다 — 그 차이가 이번에 재는 것이다.

실행 **직전·직후**에 claude.ai 설정 → 사용량 화면의 주간 % 를 적어 둔다 (A 전·후, B 전·후 — 네 숫자).

중간에 세션이 권한을 물으면 허용한다(위 settings.json을 넣었으면 거의 묻지 않는다). 90분 넘게 끝나지 않으면 그 자체가 결과다 — 세션을 멈추고 어디까지 됐는지(`.briefing-job/`에 어떤 파일이 생겼는지) 적어 둔다.

## 4. 결과 넘기기

끝나면 브랜치 두 개(`claude/briefing-test-<날짜>-A`, `-B`)에 `.briefing-job/result.json`·`verify-report.txt`·`instruction.json`이 올라와 있다. 아래를 Claude Code 세션(이 PR을 만든 세션이든 새 세션이든)에 알려 주면 비교·판정을 맡길 수 있다.

- 두 브랜치 이름
- 네 개의 사용량 % (A 전/후, B 전/후)
- 두 실행의 시작·끝 시각
- 비교 대상 API 회차 JSON (파일 또는 붙여 넣기)

판정은 설계 문서의 합격 기준으로 한다. 두 번째 시험까지 통과해 **4단계(서버: 열쇠·API-141~153·검사·조립·스케줄러 트리거/마감)는 2026-10-30 완료**됐다. 남은 것은 5단계(설정 화면)와 6절의 실전 설정이다 — 화면이 생기기 전까지는 6절대로 API를 직접 불러 설정한다. 이후 시험에서 불합격이 나오면 어디가 모자랐는지 보고 스킬·손잡이를 고쳐 한 번 더 돌리거나 멈춘다.

## 5. 세션 안에서 무슨 일이 일어나나 (참고)

| 단계 | 누가 | 무엇 |
|---|---|---|
| 수집 | 코드 (`briefing:job collect`) | 수집 목록의 RSS·Google 검색을 받아 후보 수백 건 → `candidates.json`, 분류할 것 `classify-NN.txt` |
| 분류 | 에이전트 | 언론사 피드 기사마다 세부 분야 → `classified.json` |
| 입력 자르기 | 코드 (`group`) | 분야마다 최대 60건, 서버와 같은 규칙 → `select/<분야>.txt` |
| 선별 | 에이전트 | 같은 사건 묶기·중요도·분야 넘는 합치기 → `selected.json` |
| 원문 읽기 | 코드 (`read`) | 핵심·주요 기사의 본문을 받아 재료로 → `materials.json`, 요약 입력 `summarize/*.txt` |
| 요약·검수 | 에이전트 | 서버와 같은 지시문으로 리드·왜·칸·5W·영향·해설·글머리표 → `written.json`, 검수 에이전트가 10건 대조 |
| 웹 검색 재료 (v2) | 에이전트 + 코드 (`webfill`) | 막힌 기사·재료 1곳인 핵심을 허용 도메인 안에서 검색 → `webfill.json`, 코드가 도메인·날짜·제목 겹침 검사 후 W 재료로 |
| 검증·조립 재료 | 코드 (`verify`) | 서버의 `finalizeItem`·`finalizeBullets`로 숫자 대조·근거 기호·칸 규칙 검사, 건강 숫자 → `result.json` |

서버로 보내는 것은 `result.json`뿐이고, 원문 재료(`materials.json`)는 커밋하지 않는다.

## 6. 실전 설정 (4단계 서버 뒤, 화면이 생기기 전까지는 API로)

서버(4단계)는 2026-10-30에 끝났고, 설정 화면(5단계, SCR-147)은 아직 없다. 그 사이에 실전을 돌리려면 아래 다섯 단계를 **API로 직접** 한다. 전제는 두 가지 — 이 브랜치가 **main에 올라가 배포**되어 있고(스킬·서버 둘 다 main에서 돈다), docvault가 **https** 주소로 열려 있다(열쇠가 평문으로 나가면 안 된다).

관리자 전용 API(API-134·141·143·144)는 로그인 쿠키로 들어간다. 가장 쉬운 방법은 **docvault에 로그인한 브라우저 탭에서 개발자 도구(F12) → 콘솔**에 `fetch`를 붙여 넣는 것이다 — 쿠키가 알아서 따라간다. 아래 예시는 전부 그 콘솔용이다. `<…>`는 자리표시자고, 열쇠·토큰 **실제 값은 어디에도 적어 두지 않는다**(이 문서·메모·커밋 전부).

### ① 연결 열쇠 발급 → claude.ai 환경 비밀값

```js
await (await fetch('/api/v1/briefing/token', { method: 'POST' })).json()
// → { token: "dvt_…", prefix: "dvt_xxxx", createdAt: 1793… }
```

`token`은 **이 응답에 한 번만** 보인다 — 닫으면 다시 볼 수 없고, 다시 발급하면 이전 열쇠는 그 자리에서 무효가 된다(도는 예약 작업이 있으면 그 결과는 거절된다). 바로 claude.ai/code 환경 설정 → **비밀값(Secrets)** 에 둔다:

| 이름 | 값 |
|---|---|
| `DOCVAULT_URL` | docvault 주소(끝에 `/` 없이, 예 `https://내이름.duckdns.org`). 아래 ②의 `checklist.docvaultUrl`과 같다 |
| `DOCVAULT_TOKEN` | 위 `token` 값 그대로 |

이 열쇠로는 `/api/v1/briefing/jobs/…` 세 주소(지시서·진행 보고·완성본)만 열린다. 다른 API에는 통하지 않는다.

### ② 네트워크 허용 목록

```js
await (await fetch('/api/v1/briefing/subscription')).json()
// → { mode, tokenPrefix, triggerSet, lastPingAt, lastPingResult, triggerTimes, allowedDomains: [ … ],
//     checklist: { docvaultUrl, envNames: ["DOCVAULT_URL","DOCVAULT_TOKEN"], taskPrompt: "…" }, … }
```

환경의 **Network access**를 `Custom`으로 두고 2-2의 목록에 더해:
- `allowedDomains`에 적힌 언론사 도메인 전부(수집 목록이 바뀌면 이 목록도 바뀐다 — 그때 다시 읽어 맞춘다)
- **docvault 도메인**(`checklist.docvaultUrl`의 호스트) — 이게 없으면 세션이 지시서를 못 받아 아래 ⑤에서 `no_request`가 난다

### ③ 예약 작업 만들기 — 지시문은 `checklist.taskPrompt` 그대로

claude.ai/code → 그 환경에서 **예약 작업(scheduled task / routine)** 을 하나 만든다. 지시문은 ②에서 받은 `checklist.taskPrompt`를 그대로 붙여 넣는다. 지금 서버가 내주는 문장은 이것이다:

```
routine-fire-payload 블록에 적힌 BRIEFING_JOB_ID로 briefing-subscription 스킬을 실전 모드로 실행해. DOCVAULT_URL과 DOCVAULT_TOKEN은 환경에 있어.
```

왜 이렇게 쓰나 — 서버가 예약 작업을 켤 때 `{ "text": "BRIEFING_JOB_ID=<uuid> — docvault 뉴스 브리핑 회차를 만들 차례입니다. briefing-subscription 스킬을 실전 모드로 실행하세요." }`를 보내는데, claude.ai는 이 글을 세션의 첫 메시지 안에 **`<routine-fire-payload>` 블록으로 감싸** 넣는다("신뢰하지 않는 데이터" 취급). 그래서 예약 작업에 **저장된** 지시문이 "그 블록에서 `BRIEFING_JOB_ID`를 읽어라"고 말해 줘야 세션이 어느 회차를 만들지 안다. `BRIEFING_JOB_ID`는 환경 비밀값이 **아니다** — 켜질 때마다 바뀌는 값이라 메시지로 온다. [연결 확인](⑤)도 같은 길로 `BRIEFING_JOB_ID=ping-<uuid> — docvault 연결 확인입니다. …`가 온다.

- 예약 작업 자체의 **시각 예약은 두지 않는다** — 켜는 것은 docvault 서버다(회차 시작 90분 전, `triggerTimes`에 시각이 있다). 시각을 걸어 두면 서버가 켠 것과 겹쳐 사용량만 쓴다.
- 만든 예약 작업의 **트리거 주소(fire URL)와 트리거 토큰**을 복사해 둔다. 주소는 `https://api.anthropic.com/v1/claude_code/routines/<id>/fire` 꼴이어야 한다 — 서버는 **이 모양만 받는다**(다른 호스트·경로·`http`는 400 `trigger.url: …`로 거절. 아무 주소나 받으면 서버가 토큰을 아무 데나 보내는 구멍이 된다).

### ④ 트리거 주소·토큰을 docvault에

```js
await (await fetch('/api/v1/briefing/settings', {
  method: 'PUT', headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ trigger: { url: 'https://api.anthropic.com/v1/claude_code/routines/<id>/fire', token: '<트리거 토큰>' } }),
})).json()
// → { …, triggerSet: true }
```

`trigger`의 값은 암호화되어 저장되고 **다시 내려오지 않는다** — ②를 다시 읽어도 `triggerSet: true`만 보인다. 지우려면 `{ trigger: null }`(생성 방식은 `api`로 돌아간다).

### ⑤ 연결 확인 → 구독으로 받기

```js
await (await fetch('/api/v1/briefing/subscription/ping', { method: 'POST' })).json()
// → 202 { jobId: "ping-…" }   (트리거가 없으면 409 BRIEFING_TRIGGER_NOT_SET, 켜지 못하면 502 BRIEFING_TRIGGER_FAILED)
```

서버가 `ping-<uuid>` id로 예약 작업을 켠다. 세션이 떠서 지시서(`{ kind: "ping" }`)를 받아 가면 거기서 끝 — 회차는 만들지 않는다. 1~3분 뒤 ②를 다시 읽어 `lastPingResult`를 본다:

| `lastPingResult` | 뜻 | 어디를 보나 |
|---|---|---|
| `ok` | 세션이 열쇠로 지시서를 받아 갔다 | 통과 |
| `fired` | 켰고, 아직 안 왔다 | 조금 더 기다린다(세션 기동에 몇 분) |
| `no_request` | 켠 뒤 5분 동안 요청이 없다 | ② 네트워크 허용 목록에 docvault 도메인이 있는지, 비밀값 이름이 맞는지, 지시문이 ③ 그대로인지 |
| `token_invalid` | 틀린 열쇠로 요청이 왔다 | `DOCVAULT_TOKEN`이 ①의 값인지(다시 발급했으면 이전 값은 죽었다) |
| `trigger_failed` | 예약 작업을 켜지 못했다 | ④의 주소·토큰 |

`ok`가 나오면 생성 방식을 구독으로 바꾼다:

```js
await (await fetch('/api/v1/briefing/settings', {
  method: 'PUT', headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ mode: 'subscription' }),
})).json()
// → { mode: "subscription", autoEnabled, schedule, nextAutoAt, … }
```

열쇠나 트리거가 없으면 409 `BRIEFING_TRIGGER_NOT_SET`로 거절된다. 그 뒤로는 자동 생성 스위치(`autoEnabled`)와 회차 시각(`schedule`)을 **API 방식과 그대로 공유**한다 — 스위치가 켜져 있어야 서버가 트리거를 쏘고, `nextAutoAt`은 회차 시작 90분 전(트리거 시각)이 된다. 마감은 회차 시작 + 30분이고, 그때까지 완성본이 안 오면 실행 기록에 `missing`(도착 안 함)으로 남는다. API 방식으로 돌아가려면 `{ mode: 'api' }` — 도는 예약 작업 세션의 결과는 그 뒤 거절된다.

첫 실전 회차가 돌 때는 브리핑 패널의 진행 기록(세션이 보내는 진행 보고)과 실행 기록을 보고, 끝난 회차의 JSON `edition.generator`에 `{ mode: "subscription", skillVersion: "4" }`가 찍혔는지 확인한다.
