# 3부. 프로젝트 단위 — 도구, 데이터, 그리고 요청 하나의 일생

2부가 "코드를 읽는 눈"이었다면, 3부는 "**프로젝트가 굴러가는 원리**"입니다. 부품은 어디서 오는가(npm), 역사는 어떻게 관리되는가(Git), 서버는 어떻게 조립돼 있는가(Hono), 기억은 어디에 담기는가(DB), 무엇을 의심하도록 설계됐는가(보안) — 그리고 마지막에 이 전부를 꿰는 총결산: **Ctrl+S 한 번의 왕복 여행**.

이 부의 예제도 전부 우리 저장소의 실물입니다. 2부와 달리 여기서는 "파일 하나"가 아니라 "파일들의 관계"를 읽습니다.

# 3-1. npm — 부품 창고와 계약서

## 이 장을 끝내면 알게 되는 것

- [ ] `package.json` — 프로젝트의 신분증이자 **계약서**를 줄 단위로 읽기
- [ ] dependencies와 devDependencies의 차이
- [ ] `^1.13.7` 같은 버전 표기와 `package-lock.json`의 존재 이유
- [ ] **워크스페이스** — 우리 명령어의 `-w`가 뭘 고르는 건지
- [ ] `npm install` / `npm run`이 실제로 하는 일

## 3-1-1. npm이라는 생태계

0장에서 "프로그래밍은 부품 조립"이라 했습니다. 그 부품들의 세계 최대 창고가 **npm 레지스트리**(인터넷 상의 공개 저장소)이고, `npm`은 거기서 부품을 내려받아 관리하는 도구입니다. React도, Hono도, 볼드 사건 때 설치한 `remark-cjk-friendly`도 전부 누군가 만들어 이 창고에 올린 공개 부품입니다.

부품을 내려받으면 `node_modules/`에 쌓입니다. 수만 개 파일이지만 **소모품**입니다 — 지워져도 `npm install` 한 번이면 복구됩니다. 어떻게? 뭘 설치할지가 **파일 두 개에 기록**되어 있기 때문입니다.

## 3-1-2. package.json — 계약서 해부

우리 루트의 실물 전문입니다:

```json
{
  "name": "docvault",
  "private": true,
  "version": "0.3.0",
  "workspaces": ["client", "server"],
  "scripts": {
    "dev": "npm run dev --workspaces --if-present",
    "dev:server": "npm run dev -w server",
    "dev:client": "npm run dev -w client",
    "build": "npm run build -w client",
    "start": "npm run start -w server"
  }
}
```

- **version: "0.3.0"** — 바로 우리 패치노트의 그 버전입니다. 서버가 이 값을 읽어 새 버전 감지를 한다는 것, CHANGELOG 규칙에서 배웠죠.
- **workspaces** — "이 프로젝트는 사실 **작은 프로젝트 두 개(client, server)의 묶음**"이라는 선언. 그래서 client와 server가 각자 자기 package.json을 따로 갖고, 루트가 그 둘을 관리합니다 (모노레포 구성).
- **scripts** — 명령어 별명 사전. `npm run dev:client`를 치면 실제로는 `npm run dev -w client`가 실행됩니다. **`-w client` = "client 워크스페이스에서"**. 0장부터 써 온 명령들의 정체가 이 다섯 줄입니다.

부품 목록은 각 워크스페이스 쪽에 있습니다. `server/package.json`의 실물 일부:

```json
"dependencies": {
  "hono": "^4.7.0",
  "better-sqlite3": "^12.4.1",
  "zod": "^3.24.1", ...
},
"devDependencies": {
  "typescript": "^5.7.3",
  "drizzle-kit": "^0.30.4", ...
}
```

- **dependencies** — 앱이 **돌아가는 데** 필요한 부품 (서버가 실행 중에 씀)
- **devDependencies** — **개발할 때만** 필요한 부품 (타입 검사기, 마이그레이션 생성기 — 배포된 서버에선 안 씀)

이 구분 덕에 배포 이미지를 만들 때 개발 도구를 빼고 가볍게 쌀 수 있습니다.

## 3-1-3. `^`와 package-lock — 재현성의 장치

`"hono": "^4.7.0"`의 **`^`는 "4.7.0 이상, 5.0.0 미만이면 아무거나"**라는 범위 표기입니다. 버전 세 자리는 **시맨틱 버저닝**이라는 약속입니다:

```
4  .  7  .  0
주(major) 부(minor) 수(patch)
호환 깨짐 | 기능 추가 | 버그 수정
```

"주 버전이 같으면 호환된다"는 약속 위에서, `^`는 "호환되는 최신까지 허용"이 됩니다. 그런데 이러면 문제가 하나 생깁니다 — **오늘 설치와 다음 달 설치가 다른 버전을 받을 수 있다**는 것. 내 컴퓨터에선 되는데 서버에선 안 되는 지옥의 문이죠.

그래서 **`package-lock.json`**이 있습니다: 실제로 설치된 **정확한 버전 전부**(부품의 부품까지)를 기록한 영수증. `npm install`은 lock 파일이 있으면 그대로 재현합니다. package.json이 "희망 사항"이라면 lock은 "실제 내역" — **둘 다 Git에 올리는 이유**입니다 (node_modules는 안 올리고요 — 영수증만 있으면 재현되니까).

## 직접 해보기 (5분)

1. 터미널에서 `npm run` (이름 없이) → 쓸 수 있는 스크립트 목록이 나옵니다 — scripts 사전을 npm이 읽어주는 것
2. `npm ls --depth=0 -w client` → client에 직접 설치된 부품 목록. 볼드 사건의 `remark-cjk-friendly`가 보일 겁니다
3. `package-lock.json`을 열어(<kbd>Ctrl</kbd>+<kbd>P</kbd> → 파일명 입력) `remark-cjk-friendly`를 검색 → 정확한 버전과 다운로드 주소, 무결성 해시까지 기록된 것 확인 — 영수증의 실물

# 3-2. Git — 시간을 다루는 도구

## 이 장을 끝내면 알게 되는 것

- [ ] 커밋 = **스냅샷**, 그리고 "작업 폴더 → 스테이지 → 저장소" 3구역
- [ ] `.gitignore` — 왜 `data/`와 `node_modules/`는 기록 안 하나
- [ ] 원격(GitHub)과 push/pull — "내 컴퓨터의 역사"와 "공유된 역사"
- [ ] 우리 저장소의 실제 역사 읽는 법
- [ ] push가 방아쇠 — 커밋이 배포까지 이어지는 파이프라인

## 3-2-1. 문제와 답 — 게임 세이브

"최종.zip, 진짜최종.zip, 진짜진짜최종2.zip" — Git이 없던 시절의 실화입니다. Git의 답은 게임 세이브와 같습니다: **언제든 세이브 포인트(커밋)를 만들고, 어느 포인트로든 돌아갈 수 있다.** 각 커밋은 "그 순간 프로젝트 전체의 스냅샷 + 누가 언제 왜(메시지)"를 담습니다.

우리 저장소의 실제 역사를 봅시다 (`git log --oneline`):

```
c3f3831 docs: CLAUDE.md에 업데이트 기록(CHANGELOG) 상시 갱신 규칙 추가
a44eed5 feat: 사이드바 접기 토글 + 한글 볼드 렌더링 수정 (v0.3.0)
cf659c8 docs: GHCR 패키지 공개 전환 절차 상세화 — ...
a1069fb feat: CI/CD — GitHub Actions가 이미지를 빌드해 GHCR로, 서버는 pull만
```

앞의 `c3f3831`은 커밋의 **지문**(해시) — 내용에서 계산된 고유 번호라 위조가 불가능합니다. 메시지의 `feat:`/`docs:` 접두어는 우리 CLAUDE.md 규칙("타입: 요약, 한국어")이고, **"기능 하나 완성 = 커밋 하나"** 원칙 덕에 역사가 목차처럼 읽힙니다. 볼드 사건이 어느 커밋인지 바로 보이죠?

## 3-2-2. 3구역 모델 — add와 commit의 정체

Git은 파일을 세 구역으로 나눠 생각합니다:

```
작업 폴더          스테이지            저장소(역사)
(지금 편집 중)  →   (찍을 것 선별)  →   (커밋 = 확정된 스냅샷)
         git add            git commit
```

**스테이지**가 왜 있을까요? 작업하다 보면 여러 변경이 섞입니다 — "볼드 수정 + 사이드바 토글"을 동시에 만졌더라도, add로 **골라 담아** 두 개의 깔끔한 커밋으로 나눌 수 있습니다 (실제로 우리가 v0.3.0 때 코드 커밋과 문서 커밋을 나눈 방법). `git status`는 "각 파일이 지금 어느 구역에 있나"를 보여주는 명령입니다.

**`.gitignore`**는 "Git이 쳐다보지도 말 것"의 목록입니다. 우리 프로젝트에선 `node_modules/`(영수증으로 재현 가능한 소모품)와 `data/`(코드가 아니라 **사용자의 데이터** — 역사에 남기면 안 되는 것)가 대표. 원칙: **저장소에는 재료(코드·설정·문서)만, 산출물과 데이터는 제외.**

## 3-2-3. 원격 — push와 pull

지금까지는 내 컴퓨터 안의 역사입니다. **원격 저장소**(우리는 GitHub의 `ehdwn009/docvault`)는 그 역사의 **공유 사본**입니다:

- **push** — 내 커밋들을 원격에 올린다 (우리가 "커밋푸시"할 때마다 한 일)
- **pull** — 원격의 새 커밋들을 내려받는다 (GCP 서버가 새 코드를 받는 방법!)

이 구조 덕에 컴퓨터가 불타도 역사는 GitHub에 있고, 여러 컴퓨터(혹은 사람)가 같은 역사를 공유합니다. **브랜치**는 역사를 갈래로 나누는 기능인데(실험용 평행우주), 우리는 아직 main 한 줄기만 씁니다 — 혼자 개발이라 갈래가 필요해질 때 배우면 됩니다.

## 3-2-4. push는 방아쇠 — 배포 파이프라인 전체 지도

우리 프로젝트에서 push는 단순 백업이 아니라 **배포의 방아쇠**입니다. 역사에 있던 그 커밋(`a1069fb feat: CI/CD`)이 만든 구조:

```
push → GitHub Actions가 감지 → 이미지 빌드(타입검사+빌드+포장) → GHCR(이미지 창고)에 업로드
                                                                      ↓
                                    GCP 서버에서 docker compose pull → 새 버전 실행
```

**CI/CD**라고 부르는 이것의 요점: **빌드를 사람 손이 아니라 기계가, 매번 같은 방식으로** 하게 만든 것. 커밋 → 초록불 확인 → 서버에서 pull — 우리의 배포 절차가 이 세 단계로 끝나는 이유입니다. (상세 절차는 4부 = GCP 가이드)

## 3-2-5. 되돌리기 — 이름만 알아두기

시간 여행 명령은 강력한 만큼 위험해서, 지금은 **존재만** 알아둡니다:

| 하고 싶은 것 | 명령 | 위험도 |
|---|---|---|
| 과거 구경 (읽기 전용) | `git log`, `git show 해시` | 안전 |
| 파일 하나를 마지막 커밋 상태로 | `git restore 파일` | ⚠️ 지금 편집 내용이 사라짐 |
| 커밋 하나를 "반대 커밋"으로 취소 | `git revert 해시` | 안전한 편 (역사 보존) |
| 역사를 거슬러 리셋 | `git reset` | ⚠️⚠️ 배우기 전엔 금지 |

실전 수칙 하나면 충분합니다: **막막하면 일단 `git status`, 지우기 전엔 커밋.** 커밋만 되어 있으면 무엇이든 복구 가능합니다 — 그게 Git을 쓰는 이유니까요.

## 직접 해보기 (10분)

1. `git log --oneline -15` → 우리 프로젝트의 역사를 읽으며 "커밋 = 기능 단위"가 지켜졌는지 감상
2. `git show a44eed5 --stat` → 사이드바 커밋이 건드린 파일 목록. `--stat`을 떼면 실제 변경 내용(diff)까지 — `+`가 추가된 줄, `-`가 삭제된 줄
3. 아무 파일이나 한 글자 고치고 `git status` → "modified" 표시 확인 → VS Code 왼쪽 **소스 제어 탭**에서 같은 정보가 그래픽으로 보이는 것 확인 → 파일의 변경 부분 클릭하면 diff가 뜸 → 되돌리고(Ctrl+Z) 저장
4. VS Code에서 파일 우클릭 → **타임라인** → 그 파일의 커밋 역사만 골라 보기

# 3-3. 서버 해부 — 요청받는 기계의 조립도

## 이 장을 끝내면 알게 되는 것

- [ ] `server/src/index.ts` — 서버 전체가 조립되는 순서를 줄 단위로
- [ ] **authGuard** 미들웨어 완전 해부 — deny by default의 실물
- [ ] 라우트 핸들러의 문법: `c`(컨텍스트) 사전
- [ ] 검증(zod) → 권한 → 본론이라는 표준 3단 구조
- [ ] SPA 폴백 — 딥링크 주소가 어떻게 React까지 도달하나

## 3-3-1. 조립도 — index.ts를 위에서 아래로

서버의 시작 파일은 부품 조립 순서 그 자체입니다 (`server/src/index.ts` 요약):

```ts
initDb();                          // ① DB 열기 + 마이그레이션 자동 적용
seedAdmin();                       // ② 계정이 하나도 없으면 admin 생성 (폐쇄형이라 필수)

const app = new Hono();            // ③ 서버 뼈대
app.use(logger());                 // ④ 모든 요청을 기록

const api = new Hono<AppEnv>();
api.use('*', authGuard);           // ⑤ ★ API 전체에 인증 검문소
api.get('/health', ...);           // ⑥ 개별 창구들 등록
api.route('/files', fileRoutes);   //    도메인별 라우트 파일 연결
...
app.route('/api/v1', api);         // ⑦ 전부 /api/v1 아래에 마운트

app.use('*', serveStatic(...));    // ⑧ 그 외 주소는 빌드된 클라이언트 파일 서빙
app.get('*', serveStatic(index));  // ⑨ 그래도 없으면 index.html (딥링크 폴백)

serve({ fetch: app.fetch, port }); // ⑩ 문 열기
```

**Hono**는 "주소·메서드별로 처리 함수를 등록해 두는" 서버 뼈대(프레임워크)입니다. 요청이 오면 위에서 등록한 것 중 맞는 놈을 찾아 실행합니다. ⑧⑨가 흥미로운 부분인데 — `/f/123` 같은 딥링크는 서버에 그런 창구가 없으므로 **index.html로 폴백**됩니다. 그러면 React 앱이 로드되고, 2부에서 본 `fileIdFromPath`가 주소를 읽어 해당 파일을 엽니다. **"서버는 모르는 주소를 전부 클라이언트에게 넘긴다"** — SPA(단일 페이지 앱) 라우팅의 표준 수법입니다.

## 3-3-2. authGuard — deny by default의 실물

⑤번 한 줄이 우리 보안의 척추입니다. 실물 전문 (`server/src/middleware/auth.ts`):

```ts
// deny by default (CLAUDE.md 보안): /api/v1 전체에 인증을 강제하고 예외만 여기에 등록한다.
const PUBLIC_PATHS = new Set(['/api/v1/health', '/api/v1/auth/login']);

export const authGuard = createMiddleware<AppEnv>(async (c, next) => {
  if (PUBLIC_PATHS.has(c.req.path)) return next();          // 예외 명단만 통과

  const token = getCookie(c, SESSION_COOKIE);
  if (!token) return fail(c, 401, 'UNAUTHORIZED', '로그인이 필요합니다');

  const userId = await verifySessionToken(token);
  if (userId === null) return fail(c, 401, 'UNAUTHORIZED', '세션이 만료되었습니다');

  // 토큰만 믿지 않고 매 요청 DB를 확인한다 — 삭제·비활성화가 즉시 반영되게.
  const user = db.select().from(users).where(eq(users.id, userId)).get();
  if (!user) return fail(c, 401, 'UNAUTHORIZED', '존재하지 않는 계정입니다');
  if (!user.isActive) return fail(c, 403, 'FORBIDDEN', '비활성화된 계정입니다');

  c.set('user', { id: user.id, username: user.username, ... });
  return next();
});
```

읽는 법 — 전형적인 **문지기 사슬**(2-4)입니다:

1. 공개 명단이면 통과 (`next()` = "다음 처리로 넘겨라")
2. 쿠키에서 통행증(토큰) 꺼내기 — 없으면 401
3. 통행증 검증(위조·만료) — 실패면 401
4. **통행증이 유효해도 DB를 다시 확인** — 계정이 삭제·정지됐으면 즉시 차단. "토큰만 믿지 않는다"는 주석이 설계 의도 그 자체
5. 통과자의 신원을 `c.set('user', ...)`으로 실어 보냄 — 이후 모든 핸들러의 `c.get('user')`가 이걸 꺼내는 것

핵심 설계는 **방향**입니다: 라우트마다 "인증 추가"가 아니라, **전체 차단 후 예외 등록**. 새 라우트를 만들며 인증을 깜빡해도 — 자동으로 잠겨 있습니다. 실수가 사고로 이어지지 않는 구조를 만드는 것, 이게 보안 설계의 요체입니다 (3-5에서 계속).

## 3-3-3. 핸들러 문법 — c 사전과 표준 3단

라우트 핸들러에서 만나는 `c`(컨텍스트 = "이번 요청의 서류철") 사전:

| 표현 | 뜻 |
|---|---|
| `c.req.param('id')` | 주소의 `:id` 자리 값 (`/files/123` → `'123'`) |
| `c.req.valid('json')` | **zod 검증을 통과한** 요청 본문 |
| `c.get('user')` | authGuard가 실어 보낸 로그인 사용자 |
| `c.json(값)` | JSON 응답 만들기 |
| `fail(c, 403, 'FORBIDDEN', ...)` | 우리 공통 에러 응답 `{ code, message }` |

그리고 모든 핸들러가 같은 3단 구조입니다 — 태그 수정 창구 실물 (`routes/files.ts`):

```ts
.put('/:id/tags', jsonBody(z.object({ tagIds: z.array(z.number().int().positive()).max(50) })), (c) => {
  const user = c.get('user');                    // ← 신원
  const id = parseId(c.req.param('id'));         // ┐
  if (id === null) return fail(c, 400, ...);     // ├ 1단: 검증 문지기
  const { tagIds } = c.req.valid('json');        // ┘
  ...권한 확인...                                  // 2단: 인가 문지기
  ...본론...                                      // 3단: 실제 작업 + c.json
})
```

`jsonBody(z.object(...))` 부분이 2-7에서 배운 **경계의 런타임 검증**입니다 — 본문이 "양수 정수 배열, 최대 50개"가 아니면 핸들러에 들어오기도 전에 400. 이 구조를 알면 서버의 어떤 라우트 파일을 열어도 10초 안에 지도가 그려집니다.

## 이 장을 끝내면 알게 되는 것

## 3-4-1. 왜 DB인가

문서 내용을 그냥 `.txt` 파일들로 저장하면 안 될까요? 곧 이런 요구를 만납니다 — "제목에 '경제' 들어간 파일 전부", "이 사용자의 파일만", "두 명이 동시에 저장하면?", "본문만 바꾸고 나머진 그대로". 파일 시스템으로 이걸 다 하려면 결국 DB를 재발명하게 됩니다. **DB = 검색·관계·동시성·부분 수정을 전문으로 하는 저장 엔진**입니다.

우리가 쓰는 **SQLite**는 "서버 없이 **파일 하나**로 동작하는 DB"입니다. `data/` 폴더 안의 그 파일이 전부고, 그래서 CLAUDE.md의 "이 폴더가 곧 백업 단위"라는 말이 성립합니다. 대형 서비스는 별도 DB 서버(PostgreSQL 등)를 쓰지만, 문서 열람 서비스 규모엔 SQLite가 정확한 선택입니다 — 단순함도 설계입니다.

단, 우리 설계는 **이원화**되어 있죠 (0장부터 반복된 그 구분): 텍스트 본문은 DB 안(`content_text`), 이미지·PDF 원본은 디스크(`data/files/{ownerId}/{uuid}`)에 두고 DB에는 경로만. 큰 바이너리를 DB에 넣으면 DB가 비대해지고 느려지기 때문입니다.

## 3-4-2. 테이블과 SQL 4문장

DB는 **테이블**(표)의 모음입니다. 표의 가로줄이 **행**(데이터 한 건), 세로줄이 **열**(속성). 우리 `users` 테이블이라면:

| id | username | password_hash | role | is_active |
|---|---|---|---|---|
| 1 | admin | $2b$10$... | admin | 1 |
| 2 | hong | $2b$10$... | user | 1 |

표를 다루는 언어가 **SQL**이고, 동사 네 개가 전부입니다 (HTTP 메서드와 닮은 게 우연이 아닙니다):

```sql
SELECT * FROM users WHERE role = 'admin';          -- 읽기: 조건에 맞는 행들
INSERT INTO users (username, ...) VALUES (...);    -- 새 행 추가
UPDATE files SET content_text = '...' WHERE id = 3; -- 조건에 맞는 행의 특정 열 수정
DELETE FROM file_versions WHERE file_id = 3;        -- 행 삭제
```

여기에 `ORDER BY`(정렬), `LIMIT`(개수 제한)만 얹으면 우리 서버의 쿼리 대부분을 읽을 수 있습니다. 실제로 버전 20개 유지 쿼리(잠시 뒤 등장)가 이 여섯 개의 조합입니다.

## 3-4-3. 관계 — DB의 진짜 힘

테이블들은 **서로를 가리킵니다**. 우리 스키마 실물 (`server/src/db/schema.ts`):

```ts
export const files = sqliteTable('files', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  ownerId: integer('owner_id')
    .notNull()
    .references(() => users.id, { onDelete: 'cascade' }),   // ★
  folderId: integer('folder_id').references(() => folders.id, { onDelete: 'cascade' }),
  ...
```

- **primaryKey** — 행의 주민번호. autoIncrement라 1, 2, 3... 자동 발급 (딥링크 `/f/123`의 그 번호!)
- **references** — **외래 키**: "files의 owner_id 칸에는 **users의 id에 실존하는 값만**". 파일마다 주인이 있고, 유령 주인은 불가능하다는 걸 DB가 강제합니다
- **onDelete: 'cascade'** — "가리키던 행이 지워지면 나도 지워라". 계정을 삭제하면 그 사람의 폴더·파일·버전·태그가 **연쇄로** 정리됩니다. 고아 데이터가 남을 수 없는 구조

전체 관계도를 글로 그리면: **users** 1명이 **folders**/**files**를 여럿 소유하고, **files** 하나가 **file_versions**(편집 스냅샷) 여럿을 가지며, **files↔tags**는 다대다(중간 테이블 file_tags). 이 그림이 머리에 있으면 어떤 기능도 "어느 테이블을 만지는 일인가"로 번역됩니다.

## 3-4-4. Drizzle — 스키마가 곧 타입

위 코드에서 눈치챘겠지만, 우리는 SQL 문서가 아니라 **TypeScript로 스키마를 정의**합니다. **Drizzle**이라는 부품의 역할이고, 이점이 명확합니다:

**① 스키마에서 타입이 저절로** — `db.select().from(files)`의 결과가 자동으로 올바른 타입입니다. 열 이름 오타는 빨간 줄 (2-7의 가치가 DB까지 연장).

**② 이름 경계의 자동 변환** — `ownerId: integer('owner_id')` 한 줄이 "TS에선 camelCase, DB에선 snake_case"를 선언합니다. CLAUDE.md의 네이밍 경계 규칙("변환은 Drizzle 스키마가 담당, 밖에서 수동 변환 금지")의 구현체가 바로 이 자리입니다.

**③ 쿼리도 TS로** — 읽는 법만 익히면 SQL과 1:1 대응입니다:

```ts
db.select().from(users).where(eq(users.id, userId)).get()
// = SELECT * FROM users WHERE id = ? 하고 한 건만(.get)
```

`.get()`은 한 행, `.all()`은 여러 행, `.run()`은 결과 필요 없는 실행. (CLAUDE.md의 "better-sqlite3는 동기 드라이버라 `.returning()`은 `.get()/.all()`로" 주의사항이 이 문법 이야기입니다.)

## 3-4-5. 마이그레이션 — 스키마의 Git

운영 중에 "열 하나 추가"가 필요해지면? 이미 데이터가 든 DB의 구조 변경은 **이력 관리**가 필요합니다. 그 방식이 Git과 똑같습니다:

1. `schema.ts`를 고친다 (예: 열 추가)
2. `npm run db:generate -w server` → 현재 DB와 새 스키마의 **차이를 SQL 파일로** 생성 (커밋에 해당)
3. 서버가 기동할 때 아직 적용 안 된 마이그레이션을 **순서대로 자동 적용** (①번 `initDb()`가 하는 일)

그래서 새 서버든 기존 서버든, 켜기만 하면 DB가 최신 구조가 됩니다. "스키마를 바꾸면 db:generate만 돌리면 됨" — CLAUDE.md 명령어 표의 그 줄이 이 체계였던 겁니다.

## 3-4-6. 트랜잭션 — 전부 아니면 전무

저장 로직 실물을 보면 `db.transaction((tx) => { ... })`으로 감싸여 있습니다. 안에서 하는 일이 세 가지거든요: ① 현재 본문을 버전으로 스냅샷 ② 본문 UPDATE ③ 20개 초과 버전 삭제. 만약 ②까지 하고 서버가 죽으면? 본문은 바뀌었는데 스냅샷 기록과 어긋난, **어중간하게 깨진 상태**가 됩니다.

**트랜잭션**은 "이 묶음은 **전부 성공하거나, 하나라도 실패하면 전부 없던 일**"을 DB가 보장하는 장치입니다. 돈 이체(출금+입금)를 생각하면 필연성이 바로 보입니다 — 출금만 되고 입금이 안 되는 세상은 안 되니까요. **"함께 성공해야 말이 되는 변경들은 트랜잭션으로 묶는다"** — DB 설계의 기본 수칙입니다.

# 3-5. 보안 — 의심의 설계

## 이 장을 끝내면 알게 되는 것

- [ ] 비밀번호를 서버도 모르는 이유 — **해시**
- [ ] 로그인 상태의 정체 — **서명된 통행증(JWT) + httpOnly 쿠키**
- [ ] **인증 vs 인가** — 401과 403이 나뉘는 지점
- [ ] 경로 조작(path traversal) 공격과 방어
- [ ] 이 모든 걸 관통하는 원칙: **기본 거부, 클라이언트 불신**

## 3-5-1. 비밀번호 — 서버도 모르게 저장한다

3-4의 users 표에서 열 이름이 `password`가 아니라 `password_hash`였습니다. 우리 시드 코드 실물:

```ts
passwordHash: bcrypt.hashSync(config.adminInitialPassword, 10),
```

**해시**는 "되돌릴 수 없는 반죽"입니다 — 비밀번호를 넣으면 `$2b$10$N9qo8uLO...` 같은 문자열이 나오는데, 이걸로 원래 비밀번호를 **역산할 수 없습니다**. 로그인 검사는 "입력값을 같은 방식으로 반죽해서 **반죽끼리 비교**"로 합니다. 원문은 어디에도 저장되지 않죠.

왜 이렇게까지? **DB가 통째로 유출되는 최악의 상황을 전제**하기 때문입니다. 해시만 있다면 유출돼도 비밀번호 원문은 안전합니다. bcrypt의 `10`은 반죽 횟수(2^10번) — 일부러 느리게 만들어 무차별 대입을 비경제적으로 만드는 장치입니다. 서비스들이 "비밀번호 **찾기**"가 아니라 "**재설정**"만 제공하는 이유가 이제 설명되죠 — **서버도 모르니까, 찾아줄 수가 없습니다.**

## 3-5-2. 로그인 상태 — 통행증의 물리학

HTTP는 요청마다 남남입니다(1장). 그럼 "로그인했음"은 어떻게 유지될까요? 우리 구현 (`lib/session.ts` + authGuard):

```
로그인 성공
  → 서버가 JWT 발급: "사용자 7번, 7일간 유효" + 서명
  → dv_session이라는 httpOnly 쿠키에 담아 브라우저에 전달
  → 이후 브라우저가 모든 요청에 자동으로 동봉
  → authGuard가 매 요청 서명 검증 (+ DB 재확인)
```

두 장치가 핵심입니다:

**① JWT의 서명** — 통행증 내용(사용자 번호, 만료일)에 서버만 아는 비밀키(`JWT_SECRET`)로 도장을 찍습니다. 내용을 한 글자라도 고치면 도장이 안 맞아 즉시 들통 — 그래서 "사용자 7번"을 "1번(admin)"으로 조작하는 게 불가능합니다. 배포 시 JWT_SECRET이 필수인 이유: **이 도장이 뚫리면 전부 뚫립니다.**

**② httpOnly 쿠키** — 이 쿠키는 **JavaScript로 읽을 수 없습니다.** 왜 중요하냐면, 악성 스크립트가 페이지에 섞여 들어오는 공격(XSS)이 성공해도 **통행증만은 훔쳐 갈 수 없기** 때문입니다. api.ts의 주석 "세션은 httpOnly 쿠키라 코드에서 다룰 것이 없다"가 이 설계의 클라이언트 쪽 흔적입니다.

그리고 authGuard의 마지막 의심 — 서명이 유효해도 **매 요청 DB에서 계정 상태를 재확인**합니다. 통행증은 발급 후 7일간 유효하지만, 관리자가 계정을 비활성화하면 **다음 요청부터 즉시** 차단됩니다. 통행증조차 끝까지 믿지 않는 것.

## 3-5-3. 인증과 인가 — 401과 403의 경계선

비슷해 보이지만 다른 두 질문입니다:

- **인증(authentication)** — "너 누구야?" → 실패 시 **401** (authGuard 담당)
- **인가(authorization)** — "너인 건 알겠는데, **이걸 할 자격**이 있어?" → 실패 시 **403** (각 라우트의 `canReadFile`/`canWriteFile` 담당)

인가 규칙은 CLAUDE.md 원칙대로 **공용 함수 한 곳**(`lib/access.ts`)에 모여 있습니다 — "소유자거나, 공유된 파일이거나, 관리자거나". 라우트 40개가 각자 권한 로직을 복붙하면 하나쯤 틀리는 게 필연이라, **판단 기준을 한 곳에 두고 전부 그걸 호출**하게 만든 겁니다. 보안 로직의 중복은 편의 문제가 아니라 취약점입니다.

## 3-5-4. 입력이 경로가 될 때 — path traversal

고전적이고 치명적인 공격 하나를 알아둡시다. 파일 저장 경로가 `data/files/{ownerId}/{파일명}`인데, 사용자가 파일명을 이렇게 지으면?

```
../../data/docvault.db
```

`..`은 "한 칸 위"(0장!)니까, 곧이곧대로 이어 붙이면 경로가 저장 폴더를 **탈출**해서 DB 파일 자체를 덮어쓸 수 있습니다. 방어는 두 겹입니다: 사용자 입력을 경로에 쓸 때 **정규화·검증**하고(CLAUDE.md 보안 규칙 세 번째 줄), 애초에 우리 저장 설계는 디스크 파일명을 사용자 입력이 아니라 **서버가 만든 uuid**로 짓습니다 (`data/files/{ownerId}/{uuid}` — 스키마 주석 실물). **"사용자 입력이 경로·쿼리·명령어가 되는 지점"은 언제나 최우선 의심 대상**입니다.

## 3-5-5. 원칙 총정리

3부 전체에 흩어져 있던 보안 장치들은 사실 한 문장의 변주입니다 — **"실수해도 안전한 쪽으로 무너지게 설계한다":**

| 장치 | 실수 시나리오 | 무너지는 방향 |
|---|---|---|
| deny by default 미들웨어 | 새 라우트에 인증 깜빡 | 잠긴 채로 (뚫린 채가 아니라) |
| 해시 저장 | DB 유출 | 원문은 그래도 안전 |
| httpOnly | XSS 성공 | 통행증은 그래도 못 훔침 |
| 매 요청 DB 재확인 | 유효 토큰 도난 | 계정 정지로 즉시 무력화 가능 |
| 권한 함수 단일화 | 새 기능에서 권한 실수 | 고칠 곳이 한 곳 |
| 서버 uuid 파일명 | 악의적 파일명 | 경로에 영향 없음 |

## 직접 해보기 (10분)

1. docvault 로그인 후 <kbd>F12</kbd> → **애플리케이션(Application)** 탭 → 쿠키 → `dv_session` 확인. **HttpOnly 열에 체크**가 되어 있는 것 — 이 체크 하나가 XSS 방어입니다. 콘솔에서 `document.cookie` 쳐 보면 dv_session이 **안 보입니다**
2. 값(JWT)을 복사해 https://jwt.io 같은 디코더에 넣어보면 내용(sub=사용자 번호, exp=만료)이 **읽힙니다** — JWT는 암호화가 아니라 **서명**입니다. 내용은 공개, 위조만 불가. (그래서 토큰에 비밀 정보를 넣으면 안 됩니다)
3. 로그아웃 → 주소창에 `/api/v1/tree` → `{"code":"UNAUTHORIZED",...}` 401을 맨눈으로. 다시 로그인하면 통과

# 3-6. 총결산 — Ctrl+S 한 번의 왕복 여행

마지막 장은 새 개념이 없습니다. 지금까지의 **전부를 한 줄에 꿰는** 장입니다. 여러분이 편집기에서 <kbd>Ctrl</kbd>+<kbd>S</kbd>를 누른 순간부터, 그 글자들이 디스크에 안착하고 화면이 갱신되기까지 — 실제 코드의 실제 경로입니다.

## 왕복 12단계

**[클라이언트 — 브라우저]**

1. **키 입력 감지** — 에디터 컴포넌트가 Ctrl+S를 잡아 저장 함수를 호출 `(2-8 이벤트)`
2. **요청 발사** — `api('/files/123/content', { method: 'PUT', body: JSON.stringify({ content, baseUpdatedAt }) })` — 본문과 함께 "내가 편집을 시작한 시점의 updatedAt"을 동봉 `(2-5 비동기, 1장 HTTP)`
3. 브라우저가 **dv_session 쿠키를 자동 동봉** `(3-5)`

**[서버 — 검문]**

4. **authGuard** — 쿠키 → JWT 서명 검증 → DB에서 계정 재확인 → `c.set('user', ...)` `(3-3, 3-5)`
5. **zod 검증** — 본문이 `{ content: string, baseUpdatedAt: number }` 모양인가. 아니면 400 `(2-7 경계 검증)`
6. **문지기 사슬** — id가 숫자인가(400) → 파일이 존재하는가(404) → **canWriteFile**(403) → 텍스트 파일인가(400) `(2-4 early return, 3-5 인가)`
7. **충돌 검사** — `file.updatedAt !== baseUpdatedAt`이면 **409 EDIT_CONFLICT**. 뜻: "네가 편집을 시작한 뒤, 다른 기기에서 누가 먼저 저장했다." 낙관적 잠금이라 부르는 고전 기법입니다 — 이 검사가 없으면 나중에 저장한 쪽이 먼저 저장한 쪽을 **소리 없이 덮어씁니다** `(설계의 백미)`

**[서버 — 본론, 트랜잭션 안에서]** `(3-4)`

8. **스냅샷** — 덮어쓰기 **전의** 본문을 file_versions에 INSERT — "저장 직전 상태"가 복원 지점이 됨
9. **본문 교체** — files 행을 UPDATE (content_text, size_bytes, updated_at)
10. **다이어트** — 그 파일의 버전이 20개(MAX_VERSIONS_PER_FILE)를 넘으면 오래된 것부터 DELETE — 8~10이 **한 트랜잭션**이라, 중간에 뭐가 죽어도 어중간한 상태는 없다

**[돌아오는 길]**

11. **200 응답** — `{ updatedAt, versionId }` JSON `(1장)`
12. **화면 갱신** — 클라이언트가 응답의 updatedAt을 **다음 저장의 baseUpdatedAt으로** 보관하고(다음 충돌 검사의 기준!), 상태를 갱신 → React가 다시 그림 → "저장됨" `(2-8)`

이 12단계에 1장(HTTP·상태 코드), 2부(비동기·문지기·타입·상태), 3부(미들웨어·zod·인가·트랜잭션·상수)가 전부 들어 있습니다. **이 표를 안 보고 설명할 수 있다면, 이 교재의 목표는 달성된 겁니다** — 다른 웹 서비스를 봐도 이제 같은 뼈대가 보일 테니까요.

## 보너스 트랙 — 그 코드가 세상에 나가기까지

기능 하나의 일생은 저장에서 끝나지 않습니다. 우리 프로젝트의 전체 궤도:

```
코드 수정 → 동작 확인 → CHANGELOG.md 갱신(패치노트 규칙)
  → git add/commit (기능 단위, "타입: 요약")  → git push          (3-2)
  → GitHub Actions: 타입검사·빌드·Docker 이미지 → GHCR 업로드       (3-2, 4부)
  → GCP 서버: docker compose pull & up                            (4부)
  → 사용자: 다음 로그인 때 패치노트 모달 "v0.3.0 — 사이드바 접기..."
```

## 다음은?

여기까지 왔다면 "따라 하는 사람"에서 "**읽고 판단하는 사람**"으로 넘어온 겁니다. 이후의 성장은 교재보다 실전에서 옵니다:

- **기능을 직접 하나 추가해 보기** — 작게. 예: 파일 개수를 보여주는 API + 화면 표시. 12단계를 자기 손으로 한 바퀴
- **에러를 두려워하지 않기** — 에러 메시지 → 어느 단계(12단계 중)의 문제인지 위치 특정 → 그 층의 도구(콘솔/네트워크 탭/서버 로그)로 확인. 디버깅은 감이 아니라 이 절차입니다
- **설계 문서 읽기** — `docs/design/`의 API 명세서·ERD가 이제 술술 읽힐 겁니다. "구현과 어긋나면 문서 먼저 갱신"이라는 우리 원칙의 의미도요
- 새 개념을 만날 때마다 — 인박스와 용어집은 계속 자랍니다
