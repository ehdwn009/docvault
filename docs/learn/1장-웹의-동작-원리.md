# 1장. 웹의 동작 원리 — 주소를 치면 무슨 일이 일어나나

## 이 장을 끝내면 알게 되는 것

- [ ] **클라이언트/서버**가 뭔지, 왜 `client/`와 `server/` 폴더가 나뉘어 있는지
- [ ] **주소(URL)**를 부위별로 읽는 법 (프로토콜·도메인·포트·경로)
- [ ] 웹의 모든 일이 **요청 → 응답** 한 쌍으로 이뤄진다는 것 (HTTP)
- [ ] **404, 401** 같은 상태 코드 읽는 법
- [ ] **API**와 **JSON**이 뭔지
- [ ] docvault에서 파일 하나를 클릭하면 일어나는 일을 **처음부터 끝까지** 따라가기
- [ ] 브라우저 **개발자 도구**로 이 모든 걸 직접 훔쳐보기

## 1-1. 클라이언트와 서버 — 손님과 주방

웹은 식당처럼 두 쪽으로 나뉩니다.

| | 식당 | 웹 | 우리 프로젝트 |
|---|---|---|---|
| **클라이언트** | 주문하는 손님 | 내 브라우저 (요청하는 쪽) | `client/` 폴더의 코드 |
| **서버** | 주방 | 저 멀리 컴퓨터 (응답하는 쪽) | `server/` 폴더의 코드 |

손님은 주방에 직접 들어가지 못하고 **주문서**만 보낼 수 있습니다. 주방은 주문을 받아 검사하고(로그인했나? 권한 있나?), 재료 창고(DB)에서 꺼내 요리해서 내보냅니다.

이 구분이 중요한 진짜 이유는 **신뢰**입니다. 클라이언트 코드는 사용자의 브라우저에서 돌기 때문에, 사용자가 마음만 먹으면 뜯어보고 조작할 수 있습니다. 그래서 **지켜야 할 것(비밀번호 검사, 권한 확인, 데이터)은 전부 서버에** 둡니다. 0장에서 본 폴더 구분이 바로 이 경계선입니다.

> 💡 개발하며 평생 써먹는 원칙: **"클라이언트는 믿지 않는다."** 화면에서 버튼을 숨기는 건 예의일 뿐이고, 진짜 문단속은 항상 서버가 합니다. CLAUDE.md의 보안 규칙("인증을 전체에 기본 적용")이 이 원칙의 구현입니다.

## 1-2. 주소(URL) 해부

우리 서비스 주소를 부위별로 잘라 봅시다:

```
https://docs.example.com:443/f/123
──┬── ───────┬───────── ┬── ──┬──
프로토콜     도메인       포트  경로
```

- **프로토콜** — 대화 방식의 약속. `https`는 "암호화된 웹 대화"라는 뜻 (GCP 가이드에서 Caddy가 자동으로 붙여준 그 자물쇠).
- **도메인** — 서버 컴퓨터의 **이름**. 컴퓨터의 진짜 주소는 `34.x.x.x` 같은 숫자(IP)인데, 사람이 외우기 힘드니 이름을 붙이고 DNS가 번역해 줍니다 (4장에서 배운 내용).
- **포트** — 한 컴퓨터에 나 있는 **여러 개의 문** 중 몇 번 문으로 들어갈지. 웹의 기본 문은 443(https)이라 평소엔 생략됩니다. 개발할 때 본 `localhost:5173`의 5173이 바로 포트 — "내 컴퓨터의 5173번 문".
- **경로** — 그 서버 안에서 **무엇을** 달라는 것인지. `/f/123`은 "123번 파일 화면".

> 💡 개발 중 포트가 두 개인 이유: 내 컴퓨터에서 `5173`번 문은 화면 배달 담당(Vite), `3000`번 문은 서버(Hono)가 지킵니다. 실서비스에서는 Caddy가 443번 문 하나로 받아 안에서 나눠줍니다 — 손님 입장에선 문이 하나인 게 편하니까.

## 1-3. 요청과 응답 — 웹의 유일한 대화 형식

웹에서 일어나는 **모든** 일은 딱 한 가지 형식입니다: 클라이언트가 **요청(request)** 하나를 보내면, 서버가 **응답(response)** 하나를 돌려준다. 이 대화 규칙의 이름이 **HTTP**입니다.

요청에는 "무엇을 어떻게"가 담깁니다:

```
GET /api/v1/files/123/content     ← "123번 파일의 본문을 줘" (읽기)
PUT /api/v1/files/123/content     ← "123번 파일의 본문을 이걸로 바꿔" (쓰기)
```

`GET`(읽기), `POST`(새로 만들기), `PUT`(바꾸기), `DELETE`(지우기) — 이 동사들을 **메서드**라고 합니다. 0장에서 본 `api.get('/health', ...)`의 `get`이 바로 이것 — "GET 요청이 오면 이렇게 응답하라"는 등록이었던 겁니다.

응답에는 **상태 코드**(세 자리 숫자)와 내용이 담깁니다. 자주 만나는 것들:

| 코드 | 뜻 | docvault에서 언제 |
|---|---|---|
| **200** | 성공 | 정상 응답 전부 |
| **401** | 너 누구야 (로그인 안 됨) | 세션 만료 → 로그인 화면으로 |
| **403** | 누군진 알겠는데 권한 없음 | 남의 비공개 파일에 접근 |
| **404** | 그런 거 없음 | 삭제된 파일의 딥링크 |
| **500** | 서버 잘못 (우리 버그) | 이게 뜨면 서버 로그를 봐야 함 |

> 💡 40x는 "요청한 쪽 문제", 50x는 "서버 쪽 문제"입니다. 첫 자리만 봐도 어느 쪽을 의심할지 정해집니다.

## 1-4. API와 JSON — 프로그램끼리의 주문서 양식

사람이 보는 화면 말고, **프로그램이 프로그램에게** 데이터를 요청하는 창구를 **API**라고 합니다. 우리 서버의 창구는 전부 `/api/v1/...` 주소 아래에 모여 있습니다 (`v1`은 "1번째 판"이라는 버전 표시).

API가 주고받는 데이터는 대부분 **JSON**이라는 글자 양식입니다:

```json
{ "status": "ok", "version": "0.3.0" }
```

`이름: 값` 쌍을 중괄호로 묶은 것 — 사람도 읽을 수 있고 프로그램도 읽기 쉬워서 웹의 표준 양식이 됐습니다. 0장에서 `/health` 주소로 받았던 응답이 바로 JSON이었습니다.

## 1-5. 실전 추적 — 파일 하나를 클릭하면

docvault에서 파일 이름을 클릭하고 본문이 뜨기까지, 배운 걸 전부 이어 봅시다:

1. **[클라이언트]** 클릭을 감지하고 요청을 보냅니다 → `GET /api/v1/files/123/content`
2. **[서버]** 문지기(인증 미들웨어)가 먼저 검사합니다 — 쿠키에 유효한 세션이 있나? 없으면 여기서 **401**로 끝.
3. **[서버]** 권한 검사 — 이 사용자가 123번 파일의 주인인가, 공유받았나, 관리자인가? 아니면 **403**으로 끝.
4. **[서버]** 통과했으면 DB에서 본문을 꺼내 JSON으로 포장해 응답합니다 → **200** + `{ "content": "# GCP 배포...", ... }`
5. **[클라이언트]** JSON을 받아 렌더러에게 넘깁니다 — 마크다운 글자가 꾸며진 화면이 되는 순간 (그 유명한 볼드 사건이 일어나는 지점).

모든 기능이 이 다섯 단계의 변주입니다. 저장은 방향만 반대(`PUT` + 본문 실어 보내기), 삭제는 `DELETE`, 검색은 `GET /search?q=단어`. **"클릭 → 요청 → 검사 → 응답 → 그리기"** 틀만 잡히면 웹 앱 전체가 읽힙니다.

## 직접 해보기 (10분) — 개발자 도구로 대화 훔쳐보기

> 배우는 것: 지금까지 배운 요청/응답이 상상이 아니라 실제로 오가는 걸 눈으로 확인

1. 브라우저에서 docvault에 접속해 로그인합니다 (실서비스든 `localhost:5173`이든 상관없음)
2. <kbd>F12</kbd>를 눌러 **개발자 도구**를 열고 → 상단 탭에서 **네트워크(Network)** 선택
3. 파일 목록에서 아무 md 파일이나 클릭 → 네트워크 탭에 줄이 몇 개 생깁니다. `content`라고 적힌 줄을 찾아 클릭
   - **헤더(Headers)**: 요청 메서드가 `GET`, 상태 코드가 `200`인 것 확인
   - **응답(Response)**: 방금 화면에 뜬 문서의 **원본 글자가 JSON에 담겨** 온 것 확인
4. 이번엔 편집 → 저장(Ctrl+S)을 해보세요 → `PUT` 요청이 새로 생깁니다. 이번엔 **페이로드(Payload)** 탭에 내가 보낸 본문이 보입니다 — 방향이 반대인 것 확인
5. 마지막으로 주소창에 직접 쳐 봅시다: `내주소/api/v1/files/999999/content` → 화면에 `{"code":"NOT_FOUND",...}` — 방금 **404 응답을 맨눈으로** 본 겁니다

> 💡 개발자 도구는 앞으로 뭔가 안 될 때 **가장 먼저 여는 창**이 됩니다. "요청이 아예 안 나갔나? 나갔는데 4xx인가? 200인데 화면이 못 그렸나?" — 문제의 위치를 반으로 쪼개주는 도구입니다.

## 자주 하는 실수

- 개발자 도구 네트워크 탭이 **비어 있으면**: 탭을 연 뒤의 요청만 기록됩니다. 열어 두고 다시 클릭하세요.
- `localhost:5173`에선 되는데 폰에서 안 열리면: localhost는 "그 기기 자신"이라는 뜻이라, 폰의 localhost는 폰 자신입니다. 다른 기기에서 보려면 실서버 주소로 접속해야 합니다.
- 401이 자꾸 뜨면 버그가 아니라 **세션 만료**(7일)일 수 있습니다. 다시 로그인부터.
