# 프로젝트 지도 — 모든 파일이 하는 일

폴더 구조를 봤을 때 "이 파일은 왜 있고, 뭘 하고, 누구랑 일하는지"를 한눈에 알기 위한 지도입니다.
파일을 새로 만들거나, 지우거나, 역할이 바뀌면 **이 지도도 같은 작업에서 갱신**합니다 (CLAUDE.md 규칙).

---

## 0. 큰 그림 — 3층 구조

docvault는 세 덩어리로 되어 있습니다. 식당에 비유하면:

```
[브라우저]  client/  ─ 홀: 손님(사용자)이 보고 만지는 모든 화면
     │  HTTP 요청 (api.ts → /api/v1/...)
[서버]      server/  ─ 주방: 요청을 검사하고, 데이터를 꺼내고, 규칙을 지키는 곳
     │  읽기/쓰기
[디스크]    data/    ─ 창고: SQLite 파일 + 바이너리 원본. 이 폴더가 곧 백업 단위
```

핵심 원칙 하나만 기억하세요: **믿을 수 있는 검사는 전부 주방(server)에서** 합니다.
홀(client)은 사용자가 얼마든지 조작할 수 있는 영역이라, 예쁘게 보여주는 일만 맡습니다.

| `docs/learn/` | 학습자료(이 문서 포함) |
| `docs/data_ignored/` | 개인 자료(교재 PDF, 학습용 HTML). **git 밖** |

## 2. client/ — 브라우저에서 도는 모든 것

### 입구와 설정

| 파일 | 왜 있나 |

### src/renderers/ — "형식마다 담당자가 따로 있다"

**"html 다루는 파일, md 다루는 파일이 따로 있는 건가?"의 답이 바로 이 폴더입니다. 맞습니다, 따로 있습니다.**
Viewer는 내용을 직접 그리지 않고, `index.ts`의 표에서 형식별 담당자를 찾아 맡깁니다.

| 파일 | 왜 있나 |
|---|---|
| `index.ts` | **렌더러 레지스트리** — `{ md: Markdown담당, html: Html담당, ... }` 표 하나. 새 형식 지원 = 렌더러 만들어서 여기 등록 (+ 서버 `filetypes.ts`에 확장자 허용) |
| `MarkdownRenderer.tsx` | md 담당 — react-markdown 기반. 한글 조사 볼드 문제 보정(remark-cjk-friendly), 코드 하이라이트, mermaid 다이어그램. 무거워서 지연 로드 |
| `Mermaid.tsx` | md 속 다이어그램 블록 전담 조수 — mermaid가 매우 커서 실제로 쓸 때만 로드 |
| `HtmlRenderer.tsx` | html 담당 — **iframe sandbox로 격리** 렌더링(보안 경계) + 호환 심 주입: #앵커 이동, 읽던 위치 보고, 목차 보고, 테마 표식, **좁은 화면 맞춤**(넘칠 때만 가드 CSS → 원인 요소 스크롤 상자화 → 축소). 부모와는 postMessage로만 대화 |
| `TextRenderer.tsx` | txt·code 담당 (코드 전용 렌더러가 생기기 전까지의 대타) |

### src/lib/ — 자잘한 공용 도구

| 파일 | 왜 있나 |
|---|---|
| `api.ts` | **서버와 대화하는 유일한 창구.** fetch를 감싸 에러 형식을 통일하고, 서버 응답의 타입들(TreeFile, UserSettings…)이 여기 모여 있다. 화면들은 전부 이 함수로만 서버를 부른다 |
| `download.ts` | 내려받기 진입점 — 파일 하나(`downloadFile`), 고른 것·폴더·전체를 ZIP으로(`downloadArchive`). 주소만 브라우저에 넘겨 메모리를 거치지 않게 한다 |
| `toast.tsx` | 우하단 알림 (이동 후 "실행 취소" 버튼도 이것) |
| `dialog.tsx` | 브라우저 기본 confirm/prompt 대체 모달 |

## 4. 한 번의 클릭이 지나가는 길

파일 목록만 보면 각자 떨어져 보이지만, 실제로는 한 줄로 꿰어져 일합니다. 두 여정으로 확인해 봅시다.

### 여정 A — 트리에서 HTML 문서를 클릭해서 열릴 때까지

```
① FileTree      클릭 감지 → "이 파일 선택됨"을 Workspace에 알림
② Workspace     오른쪽 영역에 Viewer를 띄움
③ Viewer        api.ts로 GET /api/v1/files/{id}/content 요청
④ (서버) index.ts → middleware/auth.ts   쿠키의 JWT 검증 (통과 못 하면 여기서 401 끝)
⑤ (서버) routes/files.ts → lib/access.ts  "이 사람이 이 파일을 읽어도 되나?" 권한 검사
⑥ (서버) db                                content_text에서 본문을 꺼내 응답
⑦ Viewer        renderers/index.ts 표에서 'html' 담당을 찾음 → HtmlRenderer
⑧ HtmlRenderer  iframe sandbox에 본문+호환 심을 넣어 렌더링
⑨ (심)          문서가 화면보다 넓으면 좁은 화면에 맞게 보정 (뷰어의 "맞춤" 버튼으로 끌 수 있음)
⑩ (심)          문서의 헤딩 목록·스크롤 위치를 postMessage로 Viewer에 보고
                → 목차 버튼이 채워지고, 읽던 위치가 저장된다
```

md 파일이었다면 ⑦에서 담당만 MarkdownRenderer로 바뀔 뿐, ①~⑥의 여정은 완전히 동일합니다.
이게 렌더러 레지스트리(플러그인 구조)의 힘입니다 — 형식이 늘어도 여정은 그대로.

### 여정 B — 로그인

```
① Login.tsx     아이디·비밀번호를 POST /api/v1/auth/login으로 (auth 미들웨어의 유일한 예외 문)
② routes/auth.ts  DB의 bcrypt 해시와 대조 → 맞으면 lib/session.ts가 JWT를 만들어
                  httpOnly 쿠키로 발급 (JS로 못 훔치는 통행증)
③ 이후 모든 요청   브라우저가 쿠키를 자동 동봉 → middleware/auth.ts가 매번 검증
```

## 5. 이 지도가 낡지 않게

- 파일을 **새로 만들면** — 해당 표에 한 줄 추가
- 파일을 **지우거나 옮기면** — 해당 줄 삭제·수정
- 역할이 **크게 바뀌면** — 설명 갱신 (예: TextRenderer가 진짜 코드 렌더러로 교체되는 날)

"코드는 바뀌었는데 지도는 옛날 것"이 가장 나쁜 상태입니다 — 차라리 없는 것보다 해롭습니다.
