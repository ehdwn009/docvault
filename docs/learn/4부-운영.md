# 4부. 운영 — 내 코드가 세상에서 계속 돌게 하기

마지막 부입니다. 코드는 완성이 아니라 시작입니다 — 이제 그 코드가 **남의 컴퓨터(서버)에서, 내가 자는 동안에도, 몇 달째 똑같이** 돌게 만들어야 합니다. 이 부는 그 원리 편이고, 손으로 하는 실습 편은 이미 완성된 **[GCP 배포 + 클라우드 학습 가이드](../GCP-배포-가이드.md)**가 담당합니다 (VM·SSH·방화벽·DNS는 그쪽에서).

여기서는 그 가이드가 "따라 하세요"라고만 했던 것들의 **속**을 엽니다: Docker 이미지는 어떻게 구워지고, compose 파일의 한 줄 한 줄은 무슨 계약이며, push 한 번이 어떻게 배포로 이어지는가 — 전부 우리 저장소의 실물 파일로.

## 이 부를 끝내면 알게 되는 것

- [ ] **이미지와 컨테이너** — "내 컴퓨터에선 되는데"를 없애는 원리
- [ ] 우리 **Dockerfile**을 줄 단위로 (멀티스테이지 빌드가 왜 두 번 나뉘는지)
- [ ] **docker-compose.yml** 해부 — 볼륨·환경변수·헬스체크·프로필
- [ ] **비밀 관리** — JWT_SECRET이 코드에 없는 이유와 .env 패턴
- [ ] **CI 워크플로**(.github/workflows/docker.yml) 해부
- [ ] 백업·업데이트·장애 대응의 기본기

# 4-1. Docker — 어디서든 똑같이 돌게

## 4-1-1. 문제: "내 컴퓨터에선 되는데요"

앱이 돌려면 코드만으론 부족합니다 — Node 22, 설치된 부품들, 빌드된 클라이언트, 환경 설정까지 **환경 전체**가 필요합니다. 서버에 이걸 손으로 재현하다 하나라도 어긋나면 나오는 말이 저 제목입니다. 배포의 역사는 이 문장과의 전쟁이었습니다.

Docker의 답: **환경 전체를 통째로 포장해서 배달한다.**

- **이미지** — 앱 + 실행 환경 전부를 떠 놓은 **틀(거푸집)**. GCP 가이드 0장에서 "IT의 이미지는 늘 복사본 틀"이라 했던 그것
- **컨테이너** — 그 틀로 찍어낸 **실행체**. 하나의 이미지로 컨테이너를 몇 개든, 어느 컴퓨터에서든 찍을 수 있고 — **전부 똑같이 돕니다**

내 PC에서 구운 이미지가 GCP 서버에서 그대로 도는 이유, "어떤 서버로 가든 절차는 늘 같다"(Docker 설치 → 코드 → .env → up)가 성립하는 이유가 이 포장입니다.

## 4-1-2. Dockerfile 해부 — 이미지 굽는 레시피

이미지를 만드는 명령서가 **Dockerfile**입니다. 우리 실물 전문:

```dockerfile
# ---- build stage: client SPA ----
FROM node:22-slim AS build            # ① Node 22가 깔린 틀에서 시작, 이 단계 이름은 build
WORKDIR /app
COPY package.json package-lock.json ./  # ② 계약서·영수증 먼저 복사
COPY client/package.json client/
COPY server/package.json server/
RUN npm ci                            # ③ 영수증(lock) 그대로 부품 설치
COPY client client                    # ④ 소스 복사
RUN NODE_OPTIONS=--max-old-space-size=2048 npm run build -w client   # ⑤ 클라이언트 빌드

# ---- runtime stage ----
FROM node:22-slim                     # ⑥ 새 틀에서 다시 시작!
WORKDIR /app
ENV NODE_ENV=production
COPY package.json package-lock.json ./
COPY server/package.json server/
RUN npm ci -w server --omit=dev       # ⑦ 서버 부품만, devDependencies 제외
COPY server server
COPY CHANGELOG.md ./                  # ⑧ 패치노트 API가 읽는 그 파일
COPY --from=build /app/client/dist client/dist   # ⑨ ①~⑤의 결과물만 가져옴
ENV DATA_DIR=/app/data
EXPOSE 3000
CMD ["npm", "start", "-w", "server"]  # ⑩ 컨테이너가 켜지면 실행할 명령
```

읽는 포인트 세 가지:

**왜 두 단계인가 (멀티스테이지)** — 클라이언트를 빌드하려면 React·Vite 등 무거운 개발 부품이 필요하지만, **다 굽고 나면 필요한 건 `dist/` 결과물뿐**입니다(3-1의 devDependencies 구분이 여기서 빛납니다). 그래서 빌드용 부엌(①~⑤)에서 굽고, 배달 상자(⑥~⑩)에는 완성품만 담습니다 — ⑨의 `--from=build` 한 줄이 그 이사입니다. 이미지가 작아지고, 공격 표면도 줄어듭니다.

**왜 package.json을 소스보다 먼저 복사하나** — Docker는 각 줄의 결과를 **캐시**하고, 입력이 안 변한 줄은 재사용합니다. 부품 목록(잘 안 변함)을 먼저, 소스(자주 변함)를 나중에 복사하면 — 코드만 고쳤을 때 ③의 설치 단계가 캐시로 스킵됩니다. 빌드가 몇 분에서 몇십 초로 줄어드는 표준 기법입니다.

**⑤의 NODE_OPTIONS** — 주석에 실화가 담겨 있습니다: 1GB 램 서버에서 빌드하면 Node가 메모리 한도를 낮게 잡아 죽어버려서(OOM), 힙 한도를 올려 스왑까지 쓰며 완주하게 한 것. GCP 가이드의 "스왑" 장이 왜 있는지와 연결됩니다. (지금은 CI가 빌드해서 이 고생 자체가 없어졌지만 — 4-4에서)

`npm ci`는 `npm install`의 배포판입니다: package-lock **영수증 그대로만** 설치하고, 어긋나면 실패. 3-1의 "재현성"이 배포에서 강제되는 지점입니다.

# 4-2. docker-compose.yml — 운영 계약서

이미지가 "무엇을"이라면, compose는 "**어떻게 띄울 것인가**"입니다. 컨테이너를 띄울 때 정해야 하는 것들(포트, 데이터 위치, 환경변수, 재시작 정책...)을 명령줄 옵션으로 매번 치는 대신 **파일로 계약**해 두는 것. 우리 실물의 핵심부:

```yaml
services:
  app:
    # 평소엔 GHCR의 완성 이미지를 pull해서 쓰고(서버), 직접 굽고 싶을 때만 --build(개발 PC)
    image: ghcr.io/ehdwn009/docvault:latest
    build: .
    ports:
      - '3000:3000'                  # 바깥 3000번 문 → 컨테이너 안 3000번 문
    volumes:
      # 영속 데이터는 이 폴더 하나. 백업 = 폴더 복사, 이사 = 폴더 이동.
      - ./data:/app/data
    environment:
      - JWT_SECRET=${JWT_SECRET:?Set JWT_SECRET in .env before running}
      - ADMIN_INITIAL_PASSWORD=${ADMIN_INITIAL_PASSWORD:-admin1234}
    restart: unless-stopped
    healthcheck:
      test: ['CMD', 'node', '-e', "fetch('http://localhost:3000/api/v1/health')..."]
      interval: 30s
```

줄 단위 독해:

- **image + build 공존** — 주석이 전략을 다 말해줍니다: 서버는 완성 이미지를 **pull**(빌드 안 함), 개발 PC에서만 `--build`로 직접 굽기. 하나의 파일로 두 상황을 다 커버합니다.
- **ports `'3000:3000'`** — 1장의 포트가 여기서 재등장합니다. 컨테이너는 격리된 방이라, "바깥 문:안쪽 문"을 이어줘야 외부에서 접속됩니다.
- **volumes `./data:/app/data`** — **이 부에서 가장 중요한 줄.** 컨테이너는 **소모품**입니다 — 업데이트 때마다 부수고 새로 찍습니다. 그 안에 DB가 있었다면? 전멸이죠. 그래서 데이터 폴더만 **컨테이너 밖(진짜 디스크의 ./data)에 연결**합니다. 컨테이너가 몇 번 갈려도 데이터는 그대로 — "data/가 곧 백업 단위"(0장부터 반복된 그 원칙)가 물리적으로 성립하는 지점입니다.
- **`${JWT_SECRET:?...}`** — "JWT_SECRET이 .env에 없으면 **띄우기를 거부하고** 이 메시지를 내라". 3-5에서 "이 도장이 뚫리면 전부 뚫린다"던 그 비밀키를, 깜빡한 채 기동하는 사고를 문법 차원에서 봉쇄한 겁니다. `${...:-admin1234}`는 반대로 "없으면 기본값" — 치명도에 따라 다른 문법을 쓴 것까지 읽어내면 완벽합니다.
- **restart: unless-stopped** — 앱이 죽거나 서버가 재부팅되면 자동으로 다시 띄워라. 새벽 3시의 나 대신 일하는 한 줄.
- **healthcheck** — 30초마다 `/api/v1/health`를 찔러 생존 확인. **0장에서 처음 읽었던 그 한 줄짜리 API**가 사실 운영의 심장 박동이었던 겁니다.

그 아래 `tunnel`(Cloudflare)과 `caddy`(HTTPS) 서비스는 **profiles**로 묶여 있어 평소엔 안 뜨고, `--profile edge up` 처럼 **선택 기동**합니다 — 외부 공개 방식을 갈아끼우는 옵션 부품들입니다 (내용은 GCP 가이드 담당).

# 4-3. 비밀 관리 — 코드에는 비밀이 없다

JWT_SECRET 값은 어디에도 없었습니다 — 코드에도, compose에도, Git 역사에도. `${JWT_SECRET}`이라는 **자리 표시**만 있죠. 실제 값은 각 컴퓨터의 **`.env` 파일**(gitignore 대상!)에만 존재합니다. 대신 저장소에는 **`.env.example`** — "채워야 할 항목의 견본"이 들어 있습니다:

```
JWT_SECRET=generate-a-long-random-string
ADMIN_INITIAL_PASSWORD=admin1234
```

이 패턴이 업계 표준인 이유: 저장소는 **언젠가 공개되거나 유출될 수 있는 곳**이고, Git은 **지워도 역사에 남는** 도구입니다(3-2). 비밀을 한 번이라도 커밋하면 끝 — 그래서 원천적으로 "비밀은 환경변수로, 견본만 커밋"으로 분리합니다. 서버 코드가 `env`에서 읽는 이유(`ADMIN_INITIAL_PASSWORD`, `JWT_SECRET`)가 전부 이 원칙입니다.

> ⚠️ 실수로 비밀을 커밋했다면: 그 비밀은 **오염된 것**입니다. 커밋을 지우는 게 아니라 **비밀 자체를 교체**하는 게 정답입니다 (JWT_SECRET 교체 → 전 사용자 재로그인).

# 4-4. CI 해부 — push가 배포가 되기까지

3-2에서 지도만 봤던 파이프라인의 실물입니다 (`.github/workflows/docker.yml` 전문):

```yaml
# CI: main에 push될 때마다 GitHub의 빌드 서버가 Docker 이미지를 구워 GHCR에 올린다.
# 운영 서버(e2-micro)는 빌드하지 않고 완성된 이미지를 pull만 한다 — 저사양 서버에서 30분 걸리던 빌드 제거.
name: build-image
on:
  push:
    branches: [main]          # ① 방아쇠: main에 push되면
permissions:
  contents: read
  packages: write             # ② 이 작업의 권한: 코드 읽기 + 패키지(이미지) 쓰기만
jobs:
  build:
    runs-on: ubuntu-latest    # ③ GitHub이 빌려주는 일회용 리눅스에서
    steps:
      - uses: actions/checkout@v4          # ④ 코드 받기
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3       # ⑤ GHCR 로그인 (자동 발급 토큰으로)
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6  # ⑥ 4-1의 Dockerfile로 굽고
        with:
          push: true
          tags: ghcr.io/ehdwn009/docvault:latest   # ⑦ 창고에 latest로 업로드
          cache-from: type=gha
          cache-to: type=gha,mode=max      # ⑧ 4-1의 레이어 캐시를 CI에서도
```

읽는 포인트:

- **워크플로 = "이 사건이 나면 이 절차를 실행하라"는 자동화 스크립트.** 파일 위치(.github/workflows/)에 두기만 하면 GitHub이 알아서 감시합니다.
- 맨 위 주석이 **도입 이유 실화**입니다: 1GB 서버에서 30분 걸리며 죽기도 하던 빌드를, GitHub의 빵빵한 빌드 서버로 옮긴 것. **"약한 곳에서 힘든 일을 하지 말고, 힘든 일은 강한 곳에서 미리 해 온다"** — 운영 설계의 전형적 사고방식입니다.
- ② permissions — 최소 권한. 3-5의 deny by default가 CI에도 적용된 모습입니다.
- `uses:`는 남이 만든 절차 부품을 가져다 쓰는 것 — npm의 GitHub Actions 버전이라 보면 됩니다.

이로써 전체 파이프라인이 실물로 연결됩니다:

```
git push (3-2) → docker.yml 발동 (4-4) → Dockerfile로 굽기 (4-1) → GHCR 업로드
→ 서버: docker compose pull && up -d (4-2) → healthcheck 초록불 → 사용자에게 패치노트
```

# 4-5. 운영 감각 — 백업, 업데이트, 장애

마지막으로, 서버를 "돌보는" 일상의 기본기입니다.

**백업** — 우리 설계 덕에 한 문장입니다: **`data/` 폴더가 전부다.** DB도, 업로드 원본도 거기 있으니(3-4), 백업 = 그 폴더 복사, 이사 = 그 폴더 이동. GCP 가이드의 cron 백업 자동화가 실제로 하는 일이 이 폴더를 정기적으로 떠 두는 것입니다. 백업의 철칙 하나만 추가하면: **복원해 본 적 없는 백업은 백업이 아닙니다.** 가끔 다른 곳에 풀어서 열리는지 확인하세요.

**업데이트** — 절차는 항상 같습니다: `git push` → Actions 초록불 확인 → 서버에서 `docker compose pull && docker compose up -d`. 컨테이너는 갈리고, data/는 남고, 마이그레이션은 기동 시 자동 적용되고(3-4), 사용자는 새 버전 안내를 받습니다(패치노트 시스템). 우리가 만든 조각들이 전부 맞물리는 순간입니다.

**장애가 나면** — 당황 대신 **층을 하나씩 내려가며** 확인합니다. 3-6의 12단계가 그대로 진단 지도가 됩니다:

1. 나만 안 되나? (다른 기기/네트워크로 확인)
2. 앱이 살아 있나? — `주소/api/v1/health` (0장의 그 한 줄이 또 일합니다)
3. 컨테이너가 떠 있나? — 서버에서 `docker compose ps`, 로그는 `docker compose logs --tail 100 app`
4. 최근에 뭘 바꿨나? — `git log` (3-2). 대부분의 장애는 마지막 변경 직후에 있습니다
5. 서버 자체가 살아 있나? — GCP 콘솔, 디스크/메모리

**요금·안전** — 예산 알림, 방화벽 최소 개방, 첫 달 청구 확인 습관은 GCP 가이드의 해당 장을 정기적으로 다시 보세요.

## 직접 해보기 (15분) — 파이프라인을 눈으로 완주

Docker 설치 없이도 할 수 있는 것들입니다:

1. **Dockerfile을 소리 내어 읽기** — 4-1의 주석 없이 원본만 열어, 각 줄이 왜 그 순서인지 설명해 보세요 (특히 package.json이 소스보다 먼저인 이유)
2. GitHub 저장소 → **Actions 탭** → 최근 build-image 실행 클릭 → 각 step의 로그 펼쳐보기. ③~⑦이 실제로 돈 기록입니다. 초록불 하나가 "빌드+타입검사+포장+업로드 전부 성공"이라는 뜻
3. GitHub 프로필 → **Packages** → docvault → 우리 이미지의 실물(크기, 태그, 최근 업로드 시각) 구경 — 4-2의 `image:` 줄이 가리키는 그 주소입니다
4. `.env.example`과 `.gitignore`를 열어 비밀 분리 패턴 확인 — `.env`가 무시 목록에 있는지 직접 찾아보기
5. (Docker가 설치된 PC라면, 선택) `docker compose up --build` → localhost:3000 접속 — 방금 읽은 레시피가 내 컴퓨터에서 구워지는 것. `Ctrl+C`로 종료

## 자주 하는 실수

- **볼륨 없이 컨테이너에 데이터 저장** — 업데이트 한 번에 전멸합니다. "컨테이너는 소모품, 데이터는 볼륨"을 주문처럼.
- 비밀을 코드/커밋에 넣기 — 4-3 참조. 넣었다면 지우는 게 아니라 **교체**.
- `latest` 이미지를 pull 안 하고 `up`만 하기 — 새 이미지가 창고에 있어도 서버는 옛것으로 다시 뜹니다. `pull` 먼저.
- 백업을 같은 서버 안에만 두기 — 서버가 죽으면 백업도 같이 죽습니다. 다른 곳(로컬 PC 등)으로 내려받는 것까지가 백업.

```
0~1장   컴퓨터·터미널·웹의 동작 원리          "무슨 일이 일어나는가"
```
