## 2-1. 값과 변수 — 재료에 이름 붙이기

프로그램이 다루는 모든 것은 **값**입니다. 종류는 생각보다 적습니다:

| 종류 | 생김새 | 뜻 |
|---|---|---|
| 숫자 | `20`, `0.3` | 그냥 숫자 |
| 문자열 | `'admin'`, `"파일이 없습니다"` | 글자. **따옴표가 곧 "이건 글자다"라는 표시** |
| 불리언 | `true`, `false` | 참/거짓 딱 두 값. 조건 검사의 재료 |
| null / undefined | `null`, `undefined` | "없음". null은 "일부러 비워둠", undefined는 "아직 아무것도 안 담김" |

**변수**는 값에 이름을 붙여 두는 것입니다. 우리 서버 코드에서:

```ts
const user = c.get('user');
```

읽는 법: "요청(c)에서 로그인한 사용자를 꺼내서, 앞으로 `user`라고 부르겠다." 이름을 붙였으니 이 아래부터는 `user` 한 단어로 그 값을 계속 쓸 수 있습니다.

앞머리의 `const`는 "이 이름표는 **다른 값으로 바꿔 붙이지 않겠다**"는 선언입니다. 바꿀 예정이면 `let`을 씁니다. 우리 코드 거의 전부가 `const`인데, "안 바뀌는 게 기본"이면 읽는 사람이 추적할 게 줄어들기 때문입니다.

> 💡 코드에서 `=`는 수학의 "같다"가 아니라 **"오른쪽 값을 왼쪽 이름에 담아라"**입니다. 그래서 "같은지 비교"는 따로 `===`(3개!)를 씁니다. 이 구분만 알아도 코드 오독의 절반이 사라집니다.

## 2-2. 함수 — 이름 붙인 기계, 그리고 최대 난관 하나

**함수**는 "입력을 넣으면 결과가 나오는 작은 기계"입니다. 우리 코드의 실제 함수:

```ts
function fileIdFromPath(pathname: string): number | null {
  const m = pathname.match(/^\/f\/(\d+)$/);
  return m ? Number(m[1]) : null;
}
```

부위별로 읽습니다:

- `function fileIdFromPath(...)` — "이제부터 이런 기계를 **등록**한다. 이름은 fileIdFromPath"
- `(pathname: string)` — 입력구. "글자(string) 하나를 받는다. 그걸 pathname이라 부르겠다"
- `: number | null` — 출력구. "숫자 **아니면** null이 나온다"
- `return ...` — "이 값을 결과로 내보내라." 기계는 return을 만나는 순간 일을 끝냅니다

가운데 줄의 `/^\/f\/(\d+)$/`는 지금 몰라도 됩니다(글자에서 패턴을 찾는 별도 문법). 중요한 건 — **속을 다 몰라도 이름·입력·출력만 읽으면 이 함수를 쓸 수 있다**는 것: "주소 글자를 넣으면 파일 번호가 나온다. 주소가 파일 주소가 아니면 null." 이게 0장에서 말한 부품(레고) 감각의 정체입니다. 실력이 늘어도 남의 함수는 늘 이렇게 껍데기부터 읽습니다.

**여기서 초심자 최대 난관.** 위 코드는 기계를 **등록**만 한 것이지, 아직 아무 일도 일어나지 않았습니다. 기계가 실제로 도는 건 누군가 이름 뒤에 괄호를 붙여 **호출**할 때입니다:

```ts
fileIdFromPath('/f/123')   // ← 이 순간 기계가 돌고, 123이 나온다
```

**괄호가 실행 버튼입니다.** `이름`만 쓰면 "그 기계 자체"를 가리키는 것이고, `이름(...)`이라야 "돌려라"입니다. 코드를 읽다가 시간 순서가 헷갈리면 십중팔구 정의(등록)를 실행으로 착각한 경우입니다.

### 화살표 함수 — 같은 기계의 짧은 문법

함수를 만드는 문법이 하나 더 있습니다. 0장의 그 줄을 다시 봅시다:

```ts
api.get('/health', (c) => c.json({ status: 'ok' }));
```

`(c) => c.json(...)` 부분이 **화살표 함수** — "c를 받으면 → c.json(...)을 돌려준다"는 이름 없는 즉석 기계입니다. `=>`를 **"넣으면 → 나온다"**로 읽으세요. 왜 이름이 없냐면, 여기서 딱 한 번 쓰고 말 거라서입니다. 이 한 줄의 전체 뜻: "get 요청 처리기를 등록하는데, 처리 방법은 이 즉석 기계다." 우리 클라이언트 코드에 `=>`가 수백 번 나오는데 전부 이 패턴입니다.

## 2-3. 객체와 배열 — 값을 묶는 두 가지 그릇

값이 여러 개면 묶어야 합니다. 그릇은 딱 두 종류입니다.

**객체** — 칸마다 이름표가 붙은 서랍장. `{ }`로 만듭니다:

```ts
{ code: 'NOT_FOUND', message: '파일이 없습니다' }
```

어디서 봤죠? — 1장의 **JSON과 같은 모양**입니다. JSON은 사실 "JavaScript 객체 표기법"의 줄임말입니다. 서랍에서 꺼낼 땐 **점**을 찍습니다: `user.role`은 "user 서랍장의 role 칸" → `'admin'`.

**배열** — 이름표 없이 **순서대로** 줄 세운 목록. `[ ]`로 만듭니다:

```ts
['md', 'html', 'txt']
```

우리 화면의 파일 목록이 실제로 배열입니다: `tree.files` — "트리 서랍장의 files 칸에는 파일들이 줄 서 있다" (객체 안에 배열이 담긴, 실전에서 가장 흔한 조합).

배열은 **명령을 시킬 수** 있습니다. 우리 코드에서 태그 필터가 실제로 하는 일:

```ts
tree.files.filter((f) => f.tags.includes(tagFilter))
```

읽는 법: "files 전체에서(filter = 걸러내라), 각 파일 f마다 → f의 태그 목록에 지금 고른 태그가 들어 있는지 보고, 맞는 것만 남겨라." 화살표 함수가 "거르는 기준"으로 쓰였습니다 — 함수를 재료처럼 다른 기계에 넘기는 것, 이게 JavaScript의 가장 큰 특징입니다.

## 2-4. 조건문 — 갈림길

코드가 위에서 아래로만 흐르면 프로그램이 아니라 목록입니다. **조건문**이 갈림길을 만듭니다. 1장에서 본 서버의 권한 검사, 실제 코드는 이 한 줄입니다:

```ts
if (!canReadFile(c.get('user'), file)) return fail(c, 403, 'FORBIDDEN', '접근 권한이 없습니다');
```

- `if (조건) 행동` — "조건이 참이면 행동해라"
- `!`는 "아니다" — `!canReadFile(...)`은 "읽을 수 **없다면**"
- 참이면 `return` — 즉시 403 응답을 내보내고 **끝**. 함수가 여기서 끝나므로 아래의 "본문 꺼내기" 코드는 실행 자체가 안 됩니다

이 패턴을 **문지기(guard)**라고 합니다: 자격 없는 요청을 입구에서 돌려보내고, 통과한 경우만 아래로 진행. 서버 코드 대부분이 "문지기 몇 줄 + 본론"의 구조라, 이것만 알아도 라우트 코드가 술술 읽힙니다.

짧은 갈림길용 문법도 하나 있습니다 — 아까 함수에서 봤던 `m ? Number(m[1]) : null`. **물음표는 "맞으면 왼쪽, 아니면 오른쪽"**입니다: "m이 있으면 숫자로 바꾼 것을, 없으면 null을." 화면 코드에서 "로그인했으면 이 화면, 아니면 저 화면" 같은 데 무수히 나옵니다.

## 2-5. 타입 — 라벨 붙은 JavaScript

이제 TypeScript의 "Type"을 얹을 차례인데, 사실 이미 다 봤습니다:

```ts
function fileIdFromPath(pathname: string): number | null
```

`: string`, `: number | null` — 이 **라벨**들이 타입입니다. "이 입력구엔 글자만", "이 출력구에선 숫자 아니면 null만". 라벨의 힘은 **실행하기 전에** 검사할 수 있다는 것입니다:

```ts
fileIdFromPath(123)   // ❌ 실행도 하기 전에 빨간 줄: "글자를 받는 곳에 숫자를 넣었다"
```

JavaScript만 쓰면 이런 실수가 **실행 중에, 하필 사용자 앞에서** 터집니다. TypeScript는 저장하는 순간 에디터가 잡아줍니다. `npm run build`가 실패할 때 나오는 에러 대부분이 이 타입 검사 결과입니다 — 귀찮은 게 아니라, **배포 전에 미리 터져 주는** 겁니다.

> 💡 이제 CLAUDE.md의 규칙 "**strict 유지, `any` 금지**"가 읽힙니다. `any`는 "이 값엔 라벨 검사를 하지 마"라는 뜻 — 편하지만 안전망에 구멍을 내는 것이라 금지한 겁니다.
>
> 💡 하나 더: 브라우저는 TypeScript를 직접 못 읽습니다. 그래서 `npm run build`가 ① 타입 검사를 하고 ② 라벨을 떼어 순수 JavaScript로 **변환**합니다. "빌드"라는 말의 정체가 이것입니다.

## 모르는 코드를 만났을 때 읽는 요령 (치트시트)

1. **다 이해하려 하지 않는다.** 함수는 이름·입력·출력만 먼저 읽는다 (속은 필요할 때만)
2. `=`는 "담아라", `===`는 "같은가", `!`는 "아니다", `?  :`는 "맞으면 왼쪽 아니면 오른쪽", `=>`는 "넣으면 → 나온다"
3. `function`/`=>`가 보이면 "지금 실행되는 게 아니라 **등록**"이라고 되뇐다 — 실행은 `이름(...)` 자리에서
4. 점(`.`)의 연쇄는 왼쪽부터: `tree.files.filter(...)` = "tree의 files에게 filter를 시켜라"
5. 대문자로 시작하면 대개 화면 부품(컴포넌트)이나 타입 이름, 소문자면 값이나 함수 — 우리 프로젝트의 작명 규칙이기도 합니다

## 2-1-1. 숫자

JavaScript의 숫자는 한 종류뿐입니다 — 정수와 소수를 구분하지 않습니다. `20`도 `0.5`도 그냥 number.

```
+  -  *  /     사칙연산 (*가 곱하기, /가 나누기)
%              나머지 (7 % 3 → 1)
```

우리 코드의 실전 예 — 업로드 진행률 계산 (`client/src/lib/api.ts`):

```ts
Math.round((e.loaded / e.total) * 100)
```

"받은 양 ÷ 전체 양 × 100을 **반올림해라**." `Math`는 수학 도구 서랍장(내장 부품)이고, `Math.round`는 그 서랍의 반올림 기계입니다. `Math.floor`(내림), `Math.max`(최댓값) 등이 같은 서랍에 있습니다.

주의 하나 — 숫자가 아닌 걸 숫자 계산하면 에러가 아니라 **`NaN`**(Not a Number, "숫자 아님"이라는 특수 값)이 나옵니다. JavaScript는 웬만해선 멈추지 않고 이상한 값을 돌려주며 계속 갑니다. 이 성격은 앞으로도 계속 만납니다.

## 2-1-2. 문자열 — 따옴표 세 종류

```ts
'admin'      // 작은따옴표 — 우리 프로젝트의 기본
"admin"      // 큰따옴표 — 뜻은 같음 (취향/규칙 문제)
`admin`      // 백틱 — 특수 능력이 있음 ↓
```

백틱 문자열은 **템플릿 리터럴**이라고 부르고, `${ }` 구멍에 **값을 끼워 넣을 수** 있습니다. 우리 코드에서:

```ts
const res = await fetch(`/api/v1${path}`, ...);   // api.ts — 주소 조립
```

`path`가 `'/tree'`면 전체 문자열은 `/api/v1/tree`가 됩니다. `+`로 이어붙이는 것(`'/api/v1' + path`)과 결과는 같지만, 구멍 뚫린 틀에 끼우는 쪽이 훨씬 읽기 좋아서 현대 코드는 거의 템플릿 리터럴을 씁니다. 화면 코드의 `className={`...${조건 ? 'A' : 'B'}`}` 패턴도 전부 이것입니다.

문자열도 명령을 받는 값입니다:

```ts
String(children).trim()        // MarkdownRenderer.tsx — 앞뒤 공백을 잘라라
pathname.match(/^\/f\/(\d+)$/) // Workspace.tsx — 이 패턴에 맞는 부분을 찾아라
e.key.toLowerCase() === 'k'    // Workspace.tsx — 소문자로 바꿔서 'k'인지 비교
```

`.length`(길이), `.includes('단어')`(포함 여부), `.split(',')`(쪼개기)도 자주 만납니다. 전부 외울 필요 없습니다 — "문자열 뒤에 점 찍으면 문자열용 명령들이 나온다"는 감각이면 충분하고, 에디터가 목록을 띄워줍니다.

⚠️ **함정**: `+`는 숫자면 덧셈, 문자열이면 이어붙이기입니다. 섞이면? `'1' + 1`은 `'11'`(문자열 승리). 서버에서 온 값이 숫자인 줄 알았는데 문자열이면 이렇게 조용히 틀어집니다 — 나중에 배울 타입과 zod가 바로 이 사고를 막는 장치입니다.

## 2-1-3. 비교 — `===`만 쓴다

| 연산자 | 뜻 |
|---|---|
| `===` / `!==` | 같다 / 다르다 |
| `<` `>` `<=` `>=` | 크기 비교 |

역사적인 이유로 `==`(2개짜리)도 존재하는데, **절대 쓰지 않습니다**. `==`는 비교 전에 값을 멋대로 변환해서 `'1' == 1`이 참이 되는 등 함정투성이입니다. `===`는 "종류까지 같아야 참" — 예측 가능합니다. 우리 코드 전체에 `==`는 한 번도 안 나옵니다.

## 2-1-4. truthy와 falsy — 이 장에서 제일 중요한 절

`if (조건)`의 조건 자리에는 불리언이 아닌 값도 올 수 있습니다. 그러면 JavaScript가 값을 참/거짓으로 **쳐 줍니다**. 거짓으로 치는 값(**falsy**)은 딱 6개뿐입니다:

```
false   0   ''(빈 문자열)   null   undefined   NaN
```

**나머지 전부가 참(truthy)입니다.** 이 규칙을 알아야 우리 코드가 읽힙니다:

```ts
if (!user) ...          // user가 null/undefined면 (= 로그인 정보가 없으면)
if (!res.ok) ...        // 응답이 실패면
if (f) setSelected(f);  // f가 있으면 (null이 아니면) 선택해라
```

`!user`는 "user가 false라는 값인가"가 아니라 "**user를 거짓으로 칠 수 있는가**" = "user가 없는가"로 읽습니다. 코드에서 `if (값)`을 만나면 십중팔구 "**값이 존재하면**"이라는 뜻입니다.

## 2-1-5. `&&` `||` `??` — 단락 평가

논리 연산자는 참/거짓 판정 말고도 **흐름 제어**에 쓰입니다. 핵심 규칙: **왼쪽만 보고 결론이 나면 오른쪽은 아예 실행하지 않습니다** (단락 평가).

**`&&` — "왼쪽이 통과하면 오른쪽을 해라".** 우리 코드 실물 (`Workspace.tsx`):

```ts
const onVisible = () => document.visibilityState === 'visible' && check();
```

"화면이 보이는 상태**면** check를 실행해라." 왼쪽이 거짓이면 `check()`는 실행조차 안 됩니다. `if`문을 한 줄로 접은 관용구입니다. 화면 코드의 `{panel === 'files' && <파일패널 />}`도 같은 원리 — "files 패널일 때**만** 이걸 그려라."

**`||` — "왼쪽이 falsy면 오른쪽으로 대체".** `이름 || '기본값'` 꼴로 기본값 제공에 씁니다.

**`??` — "왼쪽이 null/undefined일 때만 오른쪽으로".** 우리 코드 실물 (`api.ts`):

```ts
code = body.code ?? code;   // 응답에 code가 있으면 그걸, 없으면(null/undefined) 기존 값 유지
```

`||`와의 차이가 중요합니다: `0 || 100`은 `100`이지만(0이 falsy라 대체됨), `0 ?? 100`은 `0`입니다(0은 null이 아니니 유지). **"0이나 빈 문자열도 정상 값인 경우"엔 반드시 `??`**를 씁니다. 우리 코드가 `??`를 즐겨 쓰는 이유입니다.

## 2-1-6. null vs undefined — "없음"의 두 얼굴

- **undefined** — "아무도 안 담았음". 선언만 한 변수, 없는 속성을 읽었을 때, return 없는 함수의 결과.
- **null** — "**일부러** 비워뒀음". 사람이 의도를 담아 넣는 값.

우리 타입 정의를 보면 이 구분이 설계에 쓰이는 게 보입니다 (`client/src/lib/api.ts`):

```ts
folderId: number | null;    // "폴더 없음(최상위)"이라는 상태를 null로 표현
displayName: string | null; // 표시 이름을 안 정한 계정
```

"폴더에 안 들어 있음"은 실수가 아니라 **정상 상태**라서 null로 명시한 겁니다. 읽기 요령: **undefined를 만나면 "뭔가 빠졌나?" 의심하고, null을 만나면 "비어 있는 게 정상인 경우구나"로 읽는다.**

# 2-2. 함수 완전 정복 — 값처럼 다루고, 배낭을 메고 다니는 기계

## 이 장을 끝내면 알게 되는 것

- [ ] 매개변수와 인자, **기본값 매개변수**
- [ ] **함수도 값이다** — 변수에 담고, 다른 함수에 재료로 넘긴다 (**콜백**)
- [ ] `onClick={() => setPanel(target)}`에서 `() =>`를 빼면 안 되는 이유 (초심자 함정 결정판)
- [ ] **스코프** — 어떤 변수가 어디서 보이는가
- [ ] **클로저** — 함수가 태어난 곳의 변수를 기억하는 것
- [ ] 화살표 함수의 문법 변형 전부

## 2-2-1. 입력구 정밀 해부

개관에서 함수 = 입력 → 출력 기계라고 했습니다. 입력구 쪽 용어부터 정리합니다:

```ts
function fileIdFromPath(pathname: string) { ... }   // 정의: pathname은 매개변수 (빈칸 이름)
fileIdFromPath('/f/123')                            // 호출: '/f/123'은 인자 (실제 넣는 값)
```

**매개변수**는 정의할 때 지은 빈칸의 이름, **인자**는 호출할 때 실제로 넣는 값입니다. 구분해서 부를 일이 종종 있어서 용어를 알아두면 좋습니다.

매개변수에는 **기본값**을 걸 수 있습니다. 우리 코드 실물 (`MarkdownRenderer.tsx`):

```ts
function MarkdownRenderer({ content, theme = 'dark' }) { ... }
```

"theme를 안 주면 `'dark'`로 쳐라." 호출하는 쪽이 `theme`를 생략해도 동작하게 만드는 장치입니다.

출력은 하나뿐이지만(return은 값 하나), **여러 값을 돌려주고 싶으면 객체나 배열로 묶어서** 하나로 만듭니다. React의 `useState`가 정확히 이 수법입니다 — `[값, 바꾸는함수]` 배열 하나를 돌려줍니다. 2-3에서 그 대괄호의 정체를 밝힙니다.

## 2-2-2. 함수도 값이다 — 이 장의 심장

JavaScript에서 함수는 숫자·문자열과 똑같은 **값**입니다. 그래서:

**① 변수에 담을 수 있고:**

```ts
const check = () => void api('/health').then(...);   // Workspace.tsx — check라는 이름에 함수를 담음
```

**② 다른 함수에 인자로 넘길 수 있습니다:**

```ts
window.setInterval(check, 10 * 60 * 1000);           // "10분마다 check를 실행해 줘"
```

이렇게 "나중에 실행해 달라고 맡기는 함수"를 **콜백**(callback — 다시 불러줘)이라고 합니다. 웹 코드의 절반이 콜백입니다: "클릭되면 이걸 해줘", "응답이 오면 이걸 해줘", "10분마다 이걸 해줘" — 전부 함수를 값으로 넘기는 것.

여기서 **개관의 규칙이 결정적으로 중요해집니다**: 괄호 없이 `check`는 "기계 자체", `check()`는 "지금 당장 실행". 위 코드를 실수로 이렇게 쓰면:

```ts
window.setInterval(check(), 10 * 60 * 1000);   // ❌ 재앙
```

`check()`가 **그 자리에서 즉시 실행**되고, setInterval에는 그 결과값(undefined)이 넘어갑니다. "10분마다 실행"은 물 건너가죠. **"함수를 넘길 땐 괄호를 붙이지 않는다"** — 이 규칙 하나로 수많은 버그를 예방합니다.

### 실전 함정 결정판 — onClick

우리 사이드바 버튼 코드 (`Workspace.tsx`):

```tsx
<button onClick={() => setPanel(target)}>
```

왜 `onClick={setPanel(target)}`이 아닐까요? 그렇게 쓰면 **화면을 그리는 순간** `setPanel(target)`이 즉시 실행됩니다 — 클릭도 안 했는데. 심지어 setPanel은 다시 그리기를 유발하므로 "그린다 → 실행된다 → 다시 그린다 → ..." 무한 루프.

`() => setPanel(target)`은 "**클릭되면** setPanel(target)을 실행하는 **즉석 기계**"를 만들어 넘기는 것입니다. 실행 시점을 클릭 순간으로 미루는 포장지인 셈이죠. React 코드에서 `onClick={() => ...}` 꼴이 무한 반복되는 이유가 이것입니다.

> 💡 인자가 필요 없을 땐 포장 없이 바로 넘겨도 됩니다: `onClick={handleLogout}` (우리 로그아웃 버튼이 실제로 이 꼴). "괄호 없이 = 기계 전달"이니까요.

## 2-2-3. 스코프 — 변수가 보이는 범위

변수는 자기가 태어난 **중괄호 블록 안에서만** 보입니다:

```ts
function outer() {
  const a = 1;
  if (true) {
    const b = 2;
    // 여기선 a, b 둘 다 보임 (안쪽에서 바깥은 보임)
  }
  // 여기선 a만 보임 (바깥에서 안쪽은 안 보임)
}
// 여기선 둘 다 안 보임
```

방향 규칙 하나면 됩니다: **안에서 밖은 보이고, 밖에서 안은 안 보인다.** 함수 안에서 만든 변수가 함수 밖을 오염시키지 않는 것 — 프로그램이 커져도 안 무너지는 비결입니다.

## 2-2-4. 클로저 — 배낭 메고 다니는 함수

안에서 밖이 보인다면, 이런 질문이 생깁니다: 함수가 **자기 바깥의 변수를 쓴 채로** 다른 곳에 넘겨지면? 답: **함수는 자기가 태어난 곳의 변수들을 배낭에 넣고 다닙니다.** 이걸 **클로저**라고 합니다.

우리 코드가 실제로 그렇습니다 (`Workspace.tsx`):

```tsx
const railButton = (target: Panel, icon: string, label: string) => (
  <button onClick={() => setPanel(target)}>...</button>
);
```

`railButton('files', ...)`이 만들어 낸 `() => setPanel(target)`이라는 즉석 기계는, 자기가 태어날 때의 `target`('files')을 **배낭에 담은 채** 버튼에 붙습니다. 나중에 클릭될 때(railButton 실행은 한참 전에 끝났는데도) 배낭에서 `'files'`를 꺼내 씁니다. 버튼 5개가 각자 다른 target을 기억하는 이유 — **호출마다 배낭이 따로**이기 때문입니다.

클로저는 "고급 개념"으로 소문났지만, 실체는 이게 전부입니다: **함수는 태어난 환경을 기억한다.** React 코드는 이 성질 위에 서 있어서, 모르면 코드가 마법처럼 보이고 알면 당연해집니다.

## 2-2-5. 화살표 함수 문법 총정리

전부 같은 기계를 만드는 표기 변형입니다:

```ts
(a, b) => a + b            // 한 줄이면 그 식이 자동으로 return됨
(a, b) => { return a + b } // 중괄호를 열면 return을 직접 써야 함
x => x * 2                 // 매개변수가 1개면 괄호 생략 가능 (우리 코드 스타일은 괄호 유지)
() => check()              // 매개변수 없음
(f) => ({ id: f.id })      // ⚠️ 객체를 한 줄로 돌려줄 땐 괄호로 감싼다 — 중괄호가 "블록"으로 오해받아서
```

읽을 때 갈림길은 하나뿐입니다: **`=>` 뒤에 중괄호가 있으면 "여러 줄 절차(return 명시)", 없으면 "이 식의 값을 바로 돌려줌".**

## 직접 해보기 (10분) — 클로저를 손으로 만들기

<kbd>F12</kbd> 콘솔에서:

1. 함수를 값으로: `const greet = (name) => `안녕, ${name}`` 엔터 → `greet('홍길동')` → 실행. 이제 `greet` (괄호 없이) → 함수 자체가 표시됨. "값이다"의 체감
2. 콜백: `setTimeout(() => console.log('3초 뒤의 나'), 3000)` → 3초 기다리면 출력. 방금 "나중에 실행해 달라"고 함수를 맡긴 겁니다
3. 함정 재현: `setTimeout(console.log('즉시 실행되어 버림'), 3000)` → 3초를 기다리지 않고 바로 찍힘 — 괄호를 붙여 즉시 실행해 버렸기 때문
4. 클로저: 아래를 통째로 붙여넣기
   ```js
   const makeCounter = () => { let n = 0; return () => ++n; };
   const count = makeCounter();
   ```
   → `count()` `count()` `count()` → 1, 2, 3. makeCounter는 진작 끝났는데 `n`이 살아서 증가합니다 — 배낭 속에 있으니까. `const count2 = makeCounter()` → `count2()` → 1. **배낭이 호출마다 따로**인 것까지 확인

## 자주 하는 실수

- **콜백에 괄호를 붙여 즉시 실행** — `onClick={fn()}`, `setInterval(fn(), ...)`. 증상: "클릭도 안 했는데 실행돼요" / "한 번만 실행되고 끝나요".
- 화살표 함수에서 중괄호를 열고 return을 빼먹음 — `(x) => { x * 2 }`는 undefined를 돌려줍니다.
- 스코프 착각 — if 블록 안에서 만든 변수를 밖에서 쓰려고 함. 밖에서 쓸 값은 밖에서 선언.

# 2-3. 객체와 배열 다루기 — 데이터 조작의 90%

## 이 장을 끝내면 알게 되는 것

- [ ] **참조** — "복사한 줄 알았는데 같은 그릇"이라는 실무 버그 1위 지대
- [ ] **스프레드(`...`)** — 그릇을 새로 만들어 붓는 세 글자
- [ ] **구조 분해** — `const [panel, setPanel] = ...`과 `const { className, children }`의 정체
- [ ] **옵셔널 체이닝(`?.`)** — "있으면 꺼내고 없으면 undefined"
- [ ] 배열 5대 명령: **map · filter · find · sort · includes**

---

## 2-3-1. 참조 — 이 장에서 제일 중요한 절

숫자·문자열 같은 단순 값은 변수에 **값 자체**가 담깁니다. 그런데 객체와 배열은 다릅니다 — 변수에는 **그릇이 있는 위치(참조)**가 담깁니다. 그래서:

```js
const a = [1, 2];
const b = a;        // 그릇을 복사한 게 아니라 "같은 그릇의 위치"를 복사
b.push(3);          // b의 그릇에 3을 넣으면...
a                   // → [1, 2, 3] — a도 바뀌어 있다?! 같은 그릇이니까
```

`const`인데 내용이 바뀌는 것도 이제 설명됩니다 — const가 고정하는 건 "**어느 그릇을 가리키는지**"이지, 그릇 속 내용물이 아닙니다.

진짜 복사가 필요하면 **새 그릇을 만들어 부어야** 합니다. 그 도구가 **스프레드(`...`)** — "내용물을 펼쳐라"입니다:

```js
const b = [...a];        // 새 배열을 만들고 a의 내용물을 펼쳐 담음 — 이제 남남
const d = { ...c, x: 9 } // c를 펼쳐 담고 x만 9로 덮어쓴 새 객체 — 원본 무사
```

우리 코드의 실물 (`Workspace.tsx`, 정렬 기능):

```ts
return [...filtered].sort((a, b) => ...);
```

왜 `filtered.sort(...)`가 아니라 `[...filtered].sort(...)`일까요? **`.sort()`는 원본 그릇을 직접 뒤섞는** 명령이기 때문입니다. 원본(화면의 대들보인 파일 목록)을 건드리지 않으려고 복사본을 만들어 그걸 정렬한 겁니다. "**원본은 두고 새 그릇을 만든다**" — React 세계의 제1원칙이고(이유는 2-8에서), 우리 코드 곳곳의 `...`가 다 이 원칙의 실천입니다.

## 2-3-2. 구조 분해 — 그릇을 한 번에 여러 변수로

그릇에서 값을 꺼내 이름 붙이는 일이 하도 많아서, 전용 축약 문법이 있습니다.

**객체 구조 분해** — 우리 코드 실물 (`MarkdownRenderer.tsx`):

```ts
code: ({ className, children, ...props }) => { ... }
```

"들어온 객체에서 `className` 칸과 `children` 칸을 같은 이름의 변수로 꺼내고, **나머지 전부**는 `props`라는 새 객체에 모아라." (`...`이 여기서는 "나머지 수집"으로 쓰였습니다 — 만들 때는 "펼치기", 받을 때는 "모으기".)

**배열 구조 분해** — 드디어 그 대괄호의 정체:

```ts
const [panel, setPanel] = useState<Panel>('files');
```

`useState`는 `[현재값, 바꾸는함수]` 두 칸짜리 배열을 돌려줍니다. 배열 구조 분해는 **순서대로** 꺼내므로, 첫 칸을 `panel`, 둘째 칸을 `setPanel`이라 이름 붙인 것입니다. 이름은 우리 마음대로라서 `const [tags, setTags]`, `const [sortBy, setSortBy]`처럼 매번 상황에 맞게 짓습니다. 마법이 아니라 그냥 "배열 두 칸 꺼내기"였던 거죠.

**함수 매개변수 자리에서도** 됩니다 — 아까 MarkdownRenderer가 그랬고, 이런 것도 자주 봅니다:

```ts
.then(({ version }) => ...)   // Workspace.tsx — 응답 객체에서 version만 바로 꺼내 받음
```

## 2-3-3. 옵셔널 체이닝 — 없을지도 모르는 서랍장

`user.role`은 user가 null이면 **에러로 즉사**합니다 ("null의 role을 읽을 수 없음" — 콘솔 빨간 글씨의 최다 출연자). 그래서 "있으면 꺼내고, 없으면 undefined"라는 안전 점찍기가 있습니다 — `?.`:

```ts
selectedId={selected?.id ?? null}   // Workspace.tsx 실물
```

읽는 법: "selected가 **있으면** 그 id를, 없으면 undefined → `??`가 받아서 null로." 2-1의 `??`와 콤비로 다니는 이유가 이것입니다 — `?.`가 만든 undefined를 `??`가 기본값으로 바꿔줍니다.

⚠️ 남용 주의: `?.`는 "없어도 정상인 곳"에만. 있어야 마땅한 곳에 습관적으로 붙이면 버그(왜 없지?)를 조용히 삼켜서 원인 추적이 어려워집니다.

## 2-3-4. 배열 5대 명령 — 반복문 없는 반복

옛날 코드는 for 반복문으로 배열을 돌렸지만, 현대 코드는 **배열에게 함수를 주며 시킵니다**. 전부 "각 요소마다 이 함수를 적용해라" 패턴이고, **원본은 건드리지 않고 새 배열을 돌려줍니다** (sort만 예외 — 그래서 아까 복사했던 것).

**map — 하나씩 변환** (화면 그리기의 심장):

```tsx
{tags.map((tag) => (
  <button key={tag.id} onClick={() => setTagFilter(tag.id)}>...</button>
))}
```

"태그 각각을 → 버튼으로 바꿔라." 데이터 배열이 화면 요소 배열이 됩니다. React 목록 그리기의 표준 패턴 (key는 2-8에서).

**filter — 조건에 맞는 것만**:

```ts
tree.files.filter((f) => f.tags.includes(tagFilter))   // 이 태그가 달린 파일만
```

**find — 첫 번째 하나만** (없으면 undefined):

```ts
t.files.find((f) => f.id === prev.id)   // 새 트리에서 아까 선택했던 파일 찾기
```

**sort — 정렬** (비교 함수를 받음):

```ts
[...filtered].sort((a, b) => a.name.localeCompare(b.name, 'ko'))
```

비교 함수 읽는 법: 두 요소 a, b를 받아 "a가 앞이면 음수, b가 앞이면 양수"를 돌려줍니다. `localeCompare(…, 'ko')`는 "한국어 사전 순서로 비교" — 가나다 정렬이 되는 이유. 숫자 정렬은 `(a, b) => a - b`, 최신순은 `(a, b) => b.updatedAt - a.updatedAt` (우리 '최근 수정순' 정렬 실물).

**includes — 들어 있는가** (true/false): 위 filter 예제 안에서 이미 봤습니다.

> 💡 읽기 요령: `배열.map(...)`을 만나면 "아, 배열을 **다른 모양 배열로** 바꾸는구나", `filter`는 "골라내는구나", `find`는 "한 놈 찾는구나" — 이 세 단어 감각만 있으면 배열 코드의 80%가 읽힙니다. 체이닝(`filter(...).map(...)`)은 "골라낸 다음 변환"처럼 왼쪽부터 순서대로.

## 직접 해보기 (10분) — 가짜 파일 목록으로 실전 연습

<kbd>F12</kbd> 콘솔에 붙여넣기:

```js
const files = [
  { id: 1, name: '경제노트.md', size: 300, tags: ['경제'] },
  { id: 2, name: '배포가이드.md', size: 900, tags: ['IT'] },
  { id: 3, name: '회의록.md', size: 100, tags: ['경제', 'IT'] },
];
```

1. `files.map((f) => f.name)` → 이름만 뽑은 새 배열
2. `files.filter((f) => f.tags.includes('경제'))` → 경제 태그만 — docvault 태그 필터가 하는 그 일
3. `files.find((f) => f.id === 2)` → 하나만. `files.find((f) => f.id === 99)` → undefined
4. `[...files].sort((a, b) => b.size - a.size)` → 큰 파일부터
5. 참조의 함정 체험: `const copy = files` → `copy.push({ id: 4, name: '침입자.md' })` → `files.length` → **4가 됐다!** 이어서 `const real = [...files]` → `real.push(...)` 해도 files는 무사 — 스프레드가 필요한 이유를 몸으로
6. 구조 분해: `const { name, ...rest } = files[0]` → `name` → `rest`

## 자주 하는 실수

- **원본을 그대로 sort/push** 해놓고 "화면이 안 바뀌어요" 또는 "다른 데가 같이 바뀌어요" — 참조 공유가 원인. 새 그릇(`[...]`, `{...}`)부터 의심 확인.
- `find`가 undefined를 돌려줄 수 있음을 잊고 바로 점찍기 → 즉사. `?.`나 if 문지기로 받기.
- map 안에서 return 빼먹기(중괄호 열었을 때) → undefined 배열이 그려짐.

# 2-4. 흐름과 에러 — 프로그램이 무너지지 않게 설계하기

## 이 장을 끝내면 알게 되는 것

- [ ] if/else의 전체 문법과, 중첩 대신 **early return**으로 펴는 법
- [ ] 반복문(for...of)과, 우리 코드에 반복문이 드문 이유
- [ ] **throw** — 에러는 "위로 던져지고, 잡힐 때까지 올라간다"
- [ ] **try/catch** — 에러를 받아내는 그물
- [ ] "에러를 값으로 바꾸는" 실전 패턴 (`.catch(() => null)`)

---

## 2-4-1. 갈림길의 전체 문법

개관에서 `if (조건) 행동` 한 줄짜리를 봤습니다. 전체 문법은:

```ts
if (조건A) {
  // A일 때
} else if (조건B) {
  // A는 아니고 B일 때
} else {
  // 둘 다 아닐 때
}
```

**위에서부터 검사해서 처음 참이 되는 곳 하나만** 실행됩니다. 그런데 우리 코드를 보면 else가 의외로 드뭅니다. 이유는 **early return**(문지기) 스타일 때문입니다. 같은 로직 두 가지 모양:

```ts
// 중첩 스타일 — 오른쪽으로 파고든다
function getContent(user, file) {
  if (user) {
    if (canReadFile(user, file)) {
      return 본문;
    } else {
      return 권한없음에러;
    }
  } else {
    return 로그인에러;
  }
}

// 문지기 스타일 — 우리 서버의 실제 구조
function getContent(user, file) {
  if (!user) return 로그인에러;              // 자격 미달은 즉시 퇴장
  if (!canReadFile(user, file)) return 권한없음에러;
  return 본문;                               // 여기 도달 = 모든 검사 통과
}
```

아래쪽이 압도적으로 읽기 쉽습니다 — **"실패 조건들을 위에서 걷어내고, 본론은 평평하게"**. 핸들러가 30줄을 넘으면 분리하라는 CLAUDE.md 규칙도 이 스타일이라 지킬 수 있는 겁니다. 코드를 읽을 때도 똑같이: 라우트 함수를 열면 위쪽 문지기들을 훑어 "무엇이 거부되는가"부터 파악하고, 마지막 블록에서 "본론이 무엇인가"를 읽으세요.

`switch`(값 하나를 여러 경우와 대조)라는 문법도 있지만 우리 코드에선 거의 안 씁니다 — 같은 일을 객체 딕셔너리(`PANEL_TITLE[panel]` — 실물!)나 삼항으로 처리하는 게 요즘 스타일입니다.

## 2-4-2. 반복 — 그런데 왜 for가 안 보일까

전통 반복문은 이렇게 생겼습니다:

```ts
for (const f of files) {   // files의 각 요소 f에 대해
  console.log(f.name);
}
```

`for...of`는 알아둬야 합니다(남의 코드에 나오니까). 하지만 우리 코드에서 반복의 대부분은 이미 배운 **map/filter/find**입니다. 이유는 목적이 드러나기 때문 — `for`는 "돈다"는 것만 말하지만 `filter`는 "골라낸다", `map`은 "변환한다"고 **이름부터 말합니다**. 읽는 사람이 루프 속을 해석할 필요가 없죠.

for가 남는 자리는 "배열을 만드는 게 목적이 아닐 때" — 예: 순회하다 중간에 멈추고 싶을 때(`break`), 횟수만큼 반복할 때. 드뭅니다.

## 2-4-3. 에러 — 던지고, 올라가고, 잡힌다

지금까지의 흐름 제어는 "정상 경로의 갈림길"이었습니다. 에러는 **제3의 흐름**입니다: `throw`(던지기)를 만나면 함수는 즉시 중단되고, 에러가 **호출한 쪽으로, 또 그걸 호출한 쪽으로** 계속 올라갑니다 — 누군가 잡을 때까지. 아무도 안 잡으면 프로그램이 죽습니다(콘솔의 빨간 글씨).

우리 코드의 실물 (`client/src/lib/api.ts`):

```ts
if (!res.ok) {
  ...
  throw new ApiError(res.status, code, message);
}
```

"응답이 실패면 ApiError를 **던져라**." `new ApiError(...)`는 에러 정보(상태·코드·메시지)를 담은 객체를 만드는 것이고, throw가 그걸 위로 쏘아 올립니다. 이 함수를 호출한 화면 코드 어딘가가 받게 됩니다.

받는 그물이 **try/catch**입니다:

```ts
try {
  body = JSON.parse(xhr.responseText);   // 시도해 보고
} catch {
  // 응답이 JSON이 아니면 상태 코드로만 처리   ← 실제 우리 주석
}
```

"try 블록을 실행하다 **뭐든 던져지면**, 즉시 catch로 점프해라." 위 실물의 포인트: JSON.parse는 망가진 글자를 받으면 던지는 함수인데, 우리는 "파싱 실패도 예상된 상황"이라 조용히 받아넘기고 다음 줄로 진행합니다. **에러 = 프로그램의 실패가 아니라, 예상하고 설계하는 또 하나의 경로**라는 감각이 중요합니다.

## 2-4-4. 에러를 값으로 바꾸는 패턴

try/catch 말고 한 가지 방식이 더 있습니다. 우리 코드에 자주 나오는 실물 (`Workspace.tsx`):

```ts
const t = await api<Tree>('/tree').catch(() => null);
if (t) { ... }
```

"api가 던지면 → **null이라는 값으로 바꿔라**." 이러면 에러라는 특수 흐름이 사라지고, "t가 있냐 없냐"라는 **평범한 값 검사**(2-1의 truthy!)로 돌아옵니다. 트리 로딩쯤은 실패해도 앱이 죽을 일이 아니니, 에러를 조용한 null로 강등시킨 것이죠.

두 방식의 사용처를 정리하면:

| 패턴 | 언제 |
|---|---|
| `throw` 위로 올려보내기 | 여기서 처리할 수 없는 문제 — 위에서 알아서 (api()가 던지는 이유) |
| `try/catch` 받기 | 실패가 예상되고, 여기서 대안이 있을 때 |
| `.catch(() => 대체값)` | 실패해도 그만 — 값으로 강등해 흐름 단순화 |

에러 설계는 "누가 책임질 것인가"의 설계입니다. 읽을 때는 throw를 보면 "**여긴 책임 안 지고 올려보내는구나**", catch를 보면 "**여기가 책임지는 곳이구나**"로 읽으면 됩니다.

<kbd>F12</kbd> 콘솔에서:

1. 던져지는 것 구경: `JSON.parse('{망가짐')` → 빨간 에러. 방금 에러가 던져졌고 아무도 안 잡아서 콘솔까지 올라온 겁니다
2. 그물로 받기:
   ```js
   try { JSON.parse('{망가짐') } catch (e) { console.log('받았다:', e.message) }
   ```
   → 빨간 글씨 대신 우리가 정한 처리가 실행됨
3. 직접 던지기:
   ```js
   const requirePositive = (n) => { if (n <= 0) throw new Error('양수만!'); return n; };
   ```
   → `requirePositive(5)` → 5. `requirePositive(-1)` → 던져짐. try/catch로 감싸서 받아보기
4. 값으로 강등: 우리 사이트 콘솔에서
   ```js
   await fetch('/api/v1/files/999999/content').then(r => r.json()).catch(() => null)
   ```
   → 에러 대신 값이 돌아오는 흐름 체험

## 자주 하는 실수

- **catch에서 아무것도 안 하기** — 에러를 삼켜버리면 "왜 안 되는데 조용하지?"라는 최악의 디버깅 상황이 됩니다. 조용히 넘길 거면 우리 코드처럼 **주석으로 왜 괜찮은지** 남기세요.
- 문지기 없이 본론부터 쓰기 — 실패 케이스가 본론에 섞여 스파게티가 됩니다. 실패부터 걷어내는 습관.
- for 반복문 안에서 배열을 만들고 push — 대부분 map 한 줄로 대체됩니다.

## 2-5-1. 문제: 기다리는 동안 멈출 수 없다

서버에 요청을 보내면 응답까지 0.1~1초쯤 걸립니다. 사람에겐 찰나지만, 초당 수십억 번 연산하는 컴퓨터에겐 **영겁**입니다. 그동안 코드가 "응답 올 때까지 정지"해 버리면? 브라우저에서 코드와 화면은 한 줄에서 돌아가므로 — **화면 전체가 얼어붙습니다.** 스크롤도 클릭도 안 되는 상태.

그래서 JavaScript의 전략은: **"기다리지 말고 예약증을 받아라. 준비되면 부를게."** 식당에서 진동벨 받고 딴 일 보는 것과 같습니다.

## 2-5-2. Promise — 예약증

시간이 걸리는 함수(네트워크, 파일 등)는 결과 대신 **Promise**라는 예약증 객체를 **즉시** 돌려줍니다. 예약증의 상태는 셋 중 하나:

- **대기 중** — 아직 결과 없음
- **이행됨** — 값이 준비됨 (resolve)
- **거부됨** — 실패함 (reject → 2-4에서 배운 "던져짐"으로 이어짐)

예약증에는 "준비되면 이걸 해줘"라고 콜백을 붙일 수 있습니다 — `.then()`:

```ts
// Workspace.tsx 실물 — 새 버전 확인
api<{ version: string }>('/health')
  .then(({ version }) => {
    if (version !== __APP_VERSION__) setNewVersionReady(true);
  })
  .catch(() => {});
```

읽는 법: "health를 요청해 두고(예약증 받고), **응답이 오면** 버전을 비교해라. **실패하면** 조용히 무시해라." 요청을 걸어둔 뒤 코드는 멈추지 않고 다음 일로 넘어갑니다.

## 2-5-3. async/await — 같은 것의 편한 문법

`.then()` 사슬은 단계가 많아지면 읽기 힘들어서, "동기 코드처럼 생겼지만 실제론 예약"인 문법이 나왔습니다. 우리 코드 실물 (`Workspace.tsx`의 loadTree):

```ts
const loadTree = useCallback(async (): Promise<Tree | null> => {
  const t = await api<Tree>('/tree').catch(() => null);
  if (t) {
    setTree(t);
    ...
  }
  return t;
}, []);
```

독법 두 줄이면 됩니다:

- **`async`** — "이 함수는 예약증(Promise)을 돌려주는 함수다"라는 표시. await를 쓰려면 함수에 이게 붙어 있어야 합니다.
- **`await`** — "예약증이 값이 될 때까지 **이 함수 안에서만** 멈춰라." 함수 바깥세상(화면!)은 멀쩡히 돌아갑니다. 값이 오면 그 줄부터 재개.

그러니 위 코드는 "트리를 요청하고, 올 때까지 (이 함수만) 기다렸다가, 실패면 null로 강등(2-4 패턴!), 있으면 화면 상태에 반영"입니다. `.then()` 사슬과 **완전히 같은 일**을 순차 문장처럼 쓴 것뿐입니다. 우리 코드는 흐름이 길면 await, 한두 단계짜리 곁가지면 then을 씁니다 — 읽을 때 둘을 같은 것으로 취급하세요.

### void — "발사만 하고 안 기다림"

우리 코드 곳곳의 `void`:

```ts
onSelect={(f) => void selectFile(f)}
```

selectFile은 async 함수라 예약증을 돌려주는데, 클릭 처리에선 그 결과를 기다릴 필요가 없습니다. `void`는 "**이 예약증은 일부러 안 기다린다**"는 선언 — 깜빡한 게 아니라 의도임을 표시하는 우리 프로젝트의 규칙입니다. 읽을 때는 "발사!" 정도로 넘기면 됩니다.

### Promise.all — 동시에 쏘기

```ts
await Promise.all([loadTree(), loadTags()]);   // Workspace.tsx 실물 — 첫 화면 로딩
```

트리 로딩과 태그 로딩은 서로를 기다릴 이유가 없습니다. 하나씩 await하면 0.2초+0.2초=0.4초지만, **둘 다 발사해 두고 둘 다 도착하면 진행**하면 0.2초면 끝납니다. `Promise.all([...])`은 "예약증 묶음이 전부 이행되면"이라는 뜻입니다.

## 2-5-4. api() 완전 해부 — 배운 것 총집합

우리 클라이언트의 모든 요청이 지나가는 함수를 처음부터 끝까지 읽어봅시다 (`client/src/lib/api.ts`). 1장(HTTP), 2-1(??), 2-3(스프레드), 2-4(throw)가 전부 등장합니다:

```ts
export async function api<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(`/api/v1${path}`, {   // ① 요청 발사, 응답 기다림
    ...init,                                    // ② 호출자가 준 옵션을 펼쳐 담고
    headers: { ...jsonHeaders, ...init?.headers },
  });

  if (!res.ok) {                                // ③ 문지기: 실패 응답(4xx/5xx)이면
    let code = 'UNKNOWN';
    let message = `HTTP ${res.status}`;
    try {
      const body = await res.json();            // ④ 에러 본문을 읽어보되
      code = body.code ?? code;                 //    있으면 쓰고 없으면 기본값 (??)
      message = body.message ?? message;
    } catch {
      // 에러 응답이 JSON이 아니면 상태 코드만으로 처리
    }
    throw new ApiError(res.status, code, message);  // ⑤ 위로 던진다 — 처리는 호출자 몫
  }

  return res.json() as Promise<T>;              // ⑥ 성공이면 JSON 본문을 돌려준다
}
```

- `fetch`는 브라우저 내장 "HTTP 요청 기계"입니다. 1장에서 개발자 도구로 훔쳐본 그 요청들이 전부 이 fetch가 쏜 것.
- 이 함수 덕분에 화면 코드는 `api<Tree>('/tree')` 한 줄이면 됩니다 — 주소 조립, 헤더, 에러 규격화가 다 여기 모여 있으니까. **"반복되는 절차를 함수 하나로 모은다"**는 모듈화 원칙의 교과서적 실물입니다.
- `<T>` 꺾쇠의 정체는 2-7(TypeScript)에서 밝힙니다.

docvault 사이트를 연 탭에서 <kbd>F12</kbd> 콘솔:

1. 예약증 관찰: `const p = fetch('/api/v1/health')` → `p` 입력 → `Promise {<pending>}` — 결과가 아니라 **예약증**이 온 것. 몇 초 뒤 다시 `p` → `fulfilled`로 변해 있음
2. await로 값 꺼내기: `const res = await fetch('/api/v1/health')` → `await res.json()` → JSON이 값으로. (콘솔은 특별히 최상위 await를 허용해 줍니다)
3. 순서 체감 — 붙여넣기:
   ```js
   console.log('1 발사 전');
   fetch('/api/v1/health').then(() => console.log('3 응답 도착'));
   console.log('2 발사 직후');
   ```
   → 출력 순서가 1, 2, 3. **기다리지 않고 지나갔다가 나중에 돌아온다**는 게 눈에 보입니다
4. 실패 강등: `await fetch('/api/v1/없는주소').then(r => r.status)` → 404 — 상태 코드가 값으로 옴. fetch는 4xx여도 안 던지기 때문에 우리 api()가 ③에서 **직접 검사해 던지는** 겁니다 (해부에서 본 그 문지기)

## 자주 하는 실수

- **await 빼먹기** — `const t = api('/tree')` 하면 t는 값이 아니라 예약증. `t.files`는 undefined. "Promise가 찍혀요"는 100% 이 실수입니다.
- async 아닌 함수 안에서 await 사용 → 문법 에러. 함수에 async부터.
- 순차 await 남발 — 서로 무관한 요청을 한 줄씩 기다리면 그만큼 느려집니다. 무관하면 Promise.all.
- fetch가 404에서 안 던진다는 걸 모르고 catch만 믿기 — 네트워크 단절만 던지고, 4xx/5xx는 `res.ok` 검사가 필요합니다.

## 2-6-1. 왜 파일을 나누나

기술적으로는 앱 전체를 파일 하나에 쓸 수도 있습니다. 하지만 수천 줄짜리 단일 파일은 **찾을 수도, 고칠 수도, 두 사람이 같이 만질 수도** 없습니다. 그래서 코드를 역할별 파일(**모듈**)로 나누고, 필요한 것만 서로 빌려 씁니다. CLAUDE.md의 "파일 하나 = 역할 하나" 규칙이 이 원칙의 우리 버전입니다.

빌려주고 빌리는 문법이 **export**(내보내기)와 **import**(들여오기)입니다.

## 2-6-2. export — 이 파일의 공개 목록

파일 안의 것들은 기본적으로 **비공개**입니다(2-2 스코프의 파일 버전). 밖에서 쓰게 하려면 export를 붙입니다. 방식이 둘:

```ts
// named export — 이름 붙여 여러 개 (api.ts 실물)
export class ApiError extends Error { ... }
export type User = { ... };
export async function api<T>(...) { ... }

// default export — "이 파일의 대표 상품" 딱 하나 (MarkdownRenderer.tsx 실물)
export default function MarkdownRenderer({ ... }) { ... }
```

우리 프로젝트의 관례: **화면 부품(컴포넌트) 파일은 default 하나**(파일 = 부품이니까), **연장통 파일(lib 등)은 named 여러 개**(도구 모음이니까). 파일을 열면 export부터 훑으세요 — **그 파일의 공개 API(목차)**가 바로 보입니다.

## 2-6-3. import — 들여오는 쪽의 문법 전부

우리 `MarkdownRenderer.tsx` 첫머리가 import의 표본실입니다:

```ts
import ReactMarkdown from 'react-markdown';        // ① default 들여오기 (남의 부품)
import remarkGfm from 'remark-gfm';                // ①
import type { ViewerTheme } from '../lib/api';     // ② named + 타입만 들여오기 (우리 파일)
import Mermaid from './Mermaid';                   // ③ default 들여오기 (우리 파일)
import 'highlight.js/styles/github-dark.css';      // ④ 값 없이 "실어 오기만" (CSS)
```

문법 대응 규칙:

- `import 이름 from ...` — 그 파일의 **default**를 받아온다. 이름은 받는 쪽 마음대로 (default는 원래 이름이 없으므로)
- `import { 이름 } from ...` — **named** 중에서 골라온다. 중괄호 안 이름은 **내보낸 이름과 정확히 일치**해야 함 (구조 분해처럼 생겼지만 문법상 별개)
- `import type { ... }` — 타입만 가져온다는 표시 (빌드 시 어차피 사라지므로 — 2-7)
- `import '경로'` — 가져올 값은 없고, 그 파일을 **실행/포함만** 해라 (CSS 파일이 대표)

### 경로 규칙 — 출처 판별법

**시작이 `./`나 `../`면 우리 프로젝트 파일**입니다 (0장의 상대 경로 — `./`는 같은 폴더, `../`는 한 칸 위). **경로 없이 이름만이면 `node_modules`의 남의 부품**입니다:

```ts
import { useState } from 'react';       // → node_modules/react — 남의 부품
import { api } from '../lib/api';       // → 우리 client/src/lib/api.ts
```

이 한 가지 규칙으로, 어떤 파일을 열든 첫 10줄에서 "**이 파일이 남의 부품 무엇과 우리 파일 무엇에 기대고 있는지**"를 파악할 수 있습니다. 코드 읽기는 항상 여기서 시작합니다.

## 2-6-4. 재수출 허브와 지연 로드

폴더의 대표 창구로 `index.ts`를 두는 관례가 있습니다. 우리 실물 (`client/src/renderers/index.ts`):

```ts
// react-markdown + highlight.js가 무거워서 md 렌더러는 지연 로드한다
export const MarkdownRenderer = lazy(() => import('./MarkdownRenderer'));
```

두 가지가 보입니다:

- **허브**: 쓰는 쪽은 `from '../renderers'`라고만 쓰면 됩니다(폴더를 지목하면 index가 응답). 렌더러가 늘어나도 창구는 하나.
- **지연 로드**: `import(...)`를 괄호로 호출하는 형태는 "**필요해질 때** 가서 실어 와라"입니다. 마크다운 렌더러는 무거워서, md 파일을 처음 열 때에야 내려받게 한 것 — 첫 화면이 빨라지는 실전 최적화입니다.

## 2-6-5. 구조 독법 — client/src 지도

모듈 문법을 알았으니 폴더 구조가 "설계 의도"로 읽힙니다:

| 폴더 | 역할 | 규칙 |
|---|---|---|
| `screens/` | 화면 단위 (Workspace, Viewer, Login...) | 화면 ID(SCR-xxx)당 파일 하나 |
| `components/` | 여러 화면이 쓰는 부품 (FileTree, ContextMenu...) | 두 곳 이상에서 쓰면 여기로 |
| `lib/` | 화면 아닌 연장통 (api, dialog, toast) | 로직만, 그리기 없음 |
| `renderers/` | 파일 형식별 뷰어 (md, html, 이미지...) | 형식 추가 = 파일 추가 |

의존 방향도 정해져 있습니다: **screens → components → lib** 순서로만 내려갑니다. lib이 화면을 import하는 역방향이 생기면 구조가 꼬였다는 신호. 서버도 같은 원리입니다 — `routes/`(창구) → `lib/`(로직) → `db/`(저장).

> 💡 새 코드베이스를 읽는 순서(평생 쓰는 요령): ① 폴더 이름으로 지도 그리기 → ② 진입점(main.tsx, index.ts)에서 시작 → ③ import를 타고 관심 있는 곳까지 내려가기. 절대 파일을 위에서부터 다 읽지 않습니다.

# 2-7. TypeScript 마스터 — 라벨의 체계, 그리고 라벨이 못 지키는 곳

## 이 장을 끝내면 알게 되는 것

- [ ] **타입은 빌드 때 사라진다** → 외부 입력은 zod로 지킨다 (실무의 핵심 구분)

## 2-7-1. 타입 표기 전체 문법

지금까지 흩어져 나온 표기를 한 표로 모읍니다. 전부 우리 코드 실물입니다:

| 표기 | 뜻 | 실물 (api.ts 등) |
|---|---|---|
| `: string` `: number` `: boolean` | 기본형 | `path: string` |
| `: number[]` | ~의 배열 | `tags: number[]` |
| `: { id: number; name: string }` | 이 모양의 객체 | Tree 타입들 |
| `: number \| null` | 유니온 — 이것 아니면 저것 | `folderId: number \| null` |
| `?:` | 옵셔널 — 없어도 됨 | `onProgress?: (pct: number) => void` |
| `: (pct: number) => void` | 함수 타입 — "숫자 받고 반환 없음" | 위와 동일 |

마지막 줄을 읽어봅시다: `onProgress?: (pct: number) => void` — "onProgress는 **없어도 되고**, 있다면 **숫자 하나를 받고 아무것도 안 돌려주는 함수**여야 한다." (`void`는 "반환값 없음". 2-5의 `void 발사` 접두사와 철자만 같은 다른 문법입니다.) 타입 표기만 읽고도 "진행률 콜백을 선택적으로 받는구나"를 알 수 있죠 — **타입은 문서**입니다.

## 2-7-2. type 별칭 — 모양에 이름 붙이기

같은 객체 모양을 여기저기 다시 쓰려면 이름을 붙입니다. 우리 실물 (`client/src/lib/api.ts`):

```ts
export type User = {
  id: number;
  username: string;
  displayName: string | null;
  role: 'user' | 'admin';
};
```

이제 `user: User`라고만 쓰면 이 모양 전체를 약속한 것입니다. 그런데 `role`을 보세요 — `string`이 아니라 `'user' | 'admin'`입니다. **특정 문자열 값 자체를 타입으로** 쓴 것 (리터럴 유니온). 효과:

```ts
if (user.role === 'amdin') ...   // ❌ 저장하는 순간 빨간 줄 — 'amdin'은 존재할 수 없는 값
```

일반 string이었다면 이 오타는 "조용히 항상 거짓인 조건"이 되어 영원히 숨었을 겁니다. 우리 코드는 이 패턴 천지입니다 — `ViewerTheme = 'light' | 'dark' | 'sepia'`, `fileType: 'md' | 'html' | 'code' | 'text' | 'image' | 'pdf'`, 정렬 기준, 패널 이름까지. **"가능한 값이 유한하면 전부 나열한다"** — TypeScript 설계의 제1습관입니다.

> 💡 비슷한 물건으로 `interface`가 있습니다 — 객체 모양 전용의 다른 문법. 우리 프로젝트는 type으로 통일했으니 "남의 코드에서 interface를 보면 type과 거의 같은 것"으로 읽으면 됩니다.
>
> 💡 파생 문법 하나: `TreeFile['fileType']` — "TreeFile 타입의 fileType 칸의 타입" (실물: SharedFile이 이렇게 재사용). 원본이 바뀌면 자동으로 따라가는 참조입니다.

## 2-7-3. 좁히기 — 문지기를 지나면 타입이 바뀐다

`number | null` 같은 유니온은 "그대로는 못 쓰는" 타입입니다 — null일지도 모르니까. TypeScript의 답이 우아합니다: **검사를 통과한 코드 구간에서는 타입이 자동으로 좁아집니다.**

```ts
const id = parseId(c.req.param('id'));          // id: number | null
if (id === null) return fail(c, 400, ...);      // 문지기
// ↓ 여기서 id는 그냥 number — null 가능성은 위에서 제거됐음을 TS가 압니다
```

2-4의 early return 문지기 스타일이 TypeScript와 찰떡인 이유가 이것입니다: **문지기 하나 = 타입 하나 좁히기.** `if (t) {...}` (truthy 검사), `?.` 뒤, `typeof x === 'string'` 뒤에서도 같은 일이 일어납니다. "빨간 줄이 떴는데 분명 값이 있을 텐데?" 싶으면 대부분 **좁히기 문지기를 안 세운 것**입니다.

이 원칙의 끝판이 CLAUDE.md 규칙 "**any 금지, 불가피하면 unknown + 좁히기**"입니다: `any`는 "검사 다 꺼"라서 금지. `unknown`은 반대로 "**뭔지 모르니 좁히기 전엔 아무것도 못 함**" — 모르는 값을 안전하게 받는 정식 통로입니다.

## 2-7-4. 제네릭 — 타입의 빈칸

드디어 꺾쇠입니다. 우리 api 함수의 정의와 호출:

```ts
export async function api<T>(path: string, init?: RequestInit): Promise<T> { ... }

const t = await api<Tree>('/tree');        // t의 타입은 Tree
const u = await api<User>('/auth/me');     // u의 타입은 User
```

api는 어떤 주소를 부르냐에 따라 돌아오는 모양이 다릅니다. 그래서 정의할 때 **타입 자리를 빈칸(`T`)으로** 뚫어두고, **호출자가 꺾쇠로 빈칸을 채웁니다**. 이게 **제네릭** 전부입니다 — "타입 매개변수". 함수의 매개변수가 값의 빈칸이듯, 제네릭은 타입의 빈칸입니다.

읽는 법: `api<Tree>('/tree')`를 보면 "**아, 이 호출의 결과는 Tree 모양이구나**". `useState<Panel>('files')`도 이제 읽힙니다 — "이 상태에는 Panel에 나열된 값만 들어간다". 남의 코드의 `Promise<T>`, `Array<string>` 같은 것도 전부 같은 원리: **꺾쇠 = 빈칸 채우기**.

## 2-7-5. 실무의 핵심 — 타입은 빌드 때 사라진다

이 장에서 하나만 가져간다면 이것입니다. `npm run build`가 타입 검사 후 라벨을 **전부 떼고** 순수 JavaScript를 만든다고 했죠(2부 개관). 그 말은 — **실행 중에는 타입이 존재하지 않습니다.** 그래서:

```ts
const t = await api<Tree>('/tree');
```

이 꺾쇠는 사실 **약속이지 검사가 아닙니다**. 서버가 엉뚱한 모양을 보내도 실행 중엔 아무도 안 잡습니다. 우리 코드처럼 클라이언트·서버를 둘 다 우리가 만들면 약속이 지켜지지만, **바깥에서 들어오는 입력은 다릅니다** — 사용자가 보낸 요청 본문은 조작이 가능하니까요 (1장: "클라이언트는 믿지 않는다").

그래서 서버는 실행 중에 검사하는 도구 **zod**를 씁니다. 실물 (`server/src/routes/files.ts`):

```ts
const saveContentSchema = z.object({
  content: z.string(),
  baseUpdatedAt: z.number().int(),
});
```

"본문은 content(문자열)와 baseUpdatedAt(정수)여야 한다"를 **실행 중에** 대조하고, 어긋나면 400 VALIDATION_ERROR로 거절합니다. 정리하면:

| | TypeScript | zod |
|---|---|---|
| 언제 검사 | 빌드할 때 (설계도 단계) | 실행 중 (현장 검문) |
| 무엇을 지킴 | 우리 코드끼리의 약속 | **경계를 넘어오는 입력** |

CLAUDE.md의 "모든 API 입력은 zod로 검증한다"가 바로 이 구분에서 나온 규칙입니다. **경계(네트워크·파일·환경변수)에서는 런타임 검증, 내부에서는 타입** — 실무 TypeScript의 핵심 문장입니다.

# 2-8. React — "상태가 바뀌면 다시 그린다"

2부의 종착역입니다. React는 언어가 아니라 **화면 라이브러리**지만, 우리 `client/` 코드의 절반이 React 어법이라 여기서 마스터합니다. 좋은 소식: 필요한 재료(함수·클로저·구조 분해·map·타입)는 **전부 이미 배웠습니다.**

## 이 장을 끝내면 알게 되는 것

- [ ] React의 단 하나의 사상: **화면 = 함수(상태)**
- [ ] **JSX** — HTML처럼 생긴 JavaScript의 규칙
- [ ] **props**(부품에 재료 주기)와 **state**(useState — 바뀌면 다시 그림)
- [ ] 조건부 렌더링(`&&`, 삼항)과 목록 렌더링(map + key)
- [ ] **useEffect** — "그린 다음 할 일"과 청소
- [ ] 우리가 만든 **사이드바 접기 기능을 처음부터 끝까지** 추적

---

## 2-8-1. 문제와 사상 — 왜 React인가

React 없이 화면을 바꾸려면 명령의 연속입니다: "그 버튼을 찾아서 색을 바꾸고, 저 패널을 찾아서 숨기고, 목록을 찾아서 줄을 지우고..." 화면이 복잡해지면 **어딘가 하나를 빼먹는 게 필연**이고, 화면과 데이터가 어긋난 채 굴러갑니다.

React의 답은 발상 전환입니다:

> **화면을 "데이터(상태)를 넣으면 화면이 나오는 함수"로 써라. 상태가 바뀌면, 함수를 다시 실행해서 화면을 통째로 다시 그린다.**

"바뀐 부분을 찾아 고치는" 명령 대신, "**현재 상태면 화면은 이래야 한다**"는 선언만 씁니다. 다시 그리기의 낭비는 React가 알아서 최소화합니다(실제 화면엔 달라진 부분만 반영). 이 사상 하나만 잡으면 React의 모든 것이 따라옵니다.

## 2-8-2. 컴포넌트와 JSX

**컴포넌트**는 "화면 조각을 돌려주는 함수"입니다. 이름이 대문자로 시작합니다 (개관의 작명 규칙 회수 — 대문자 = 화면 부품):

```tsx
export default function Login() {
  return <h1 className="text-2xl font-bold">docvault</h1>;
}
```

return 자리의 HTML 닮은 문법이 **JSX**입니다. 규칙은 몇 개뿐:

- **중괄호 `{}` = JavaScript 구멍.** 값이든 식이든 끼워 넣을 수 있음: `<h1>{user.username}</h1>`
- `class` 대신 `className` (class가 JS 예약어라서)
- 태그는 반드시 닫는다: `<input />` 처럼 자기 닫힘도 가능
- 소문자 태그(`<div>`)는 HTML 요소, **대문자 태그(`<FileTree />`)는 우리가 만든 컴포넌트**

JSX는 브라우저가 모르는 문법이라 빌드 때 함수 호출로 변환됩니다 — `.tsx` 확장자의 x가 "JSX 포함"이라는 표시입니다.

## 2-8-3. props — 부품에 재료 주기

컴포넌트는 함수니까 인자를 받습니다. React에선 그걸 **props**라 부르고, 태그의 속성처럼 씁니다. 우리 실물 — 뷰어가 마크다운 렌더러를 쓰는 곳:

```tsx
<MarkdownRenderer content={draft} theme={settings.viewerTheme} />
```

받는 쪽은 객체 구조 분해(2-3!)로 풀어 받습니다:

```tsx
function MarkdownRenderer({ content, theme = 'dark' }: { content: string; theme?: ViewerTheme }) {
```

props의 두 가지 성질만 기억하면 됩니다: **① 위에서 아래로만 흐른다** (부모가 자식에게 재료를 줌 — 역류 없음), **② 자식은 props를 바꿀 수 없다** (읽기 전용 — 바꾸고 싶으면 부모가 준 함수를 호출해 "요청"함. `onSelect={...}` 같은 콜백 props가 그 통로).

## 2-8-4. state — 이 장의 심장

props는 부모가 주는 재료지만, 컴포넌트 **스스로 기억하고 바꾸는 값**이 필요합니다 — 그게 **state**이고, 도구가 `useState`입니다. 우리가 직접 만든 기능의 실물로 처음부터 끝까지 추적해 봅시다 — **사이드바 접기** (`Workspace.tsx`):

**① 상태 선언:**

```tsx
const [panelCollapsed, setPanelCollapsed] = useState(false);
```

2-3에서 밝힌 배열 구조 분해입니다: 현재값 `panelCollapsed`(처음엔 false), 그걸 바꾸는 함수 `setPanelCollapsed`.

**② 상태를 화면에 반영 (선언):**

```tsx
<aside className={`... ${panelCollapsed ? 'pc:hidden' : ''}`}>
```

"접혀 있**으면** 숨김 클래스를 붙인다" — 명령이 아니라 **현재 상태의 묘사**입니다.

**③ 이벤트에서 상태 변경 (요청):**

```tsx
onClick={() => {
  if (panel === target) setPanelCollapsed((v) => !v);   // 활성 버튼 재클릭 → 뒤집기
  else { setPanel(target); setPanelCollapsed(false); }
}}
```

**④ 순환 완성:** setPanelCollapsed가 호출되면 → React가 "상태 바뀜"을 감지 → **Workspace 함수를 다시 실행** → ②의 삼항이 이번엔 반대쪽 값으로 평가 → 패널이 사라짐/나타남.

이게 React의 전부입니다: **상태 선언 → 화면은 상태의 함수 → 이벤트는 상태 변경만 요청 → 다시 그리기.** 클릭 핸들러 어디에도 "패널을 숨겨라"는 명령이 없다는 걸 음미하세요 — 상태만 바꾸면 화면은 따라옵니다.

세 가지 규칙:

- **직접 대입 금지** — `panelCollapsed = true`는 React가 모릅니다(다시 안 그림). 반드시 set 함수로.
- **이전 값 기반이면 함수형** — `setPanelCollapsed((v) => !v)`처럼 "이전 값 v를 받아 새 값을 계산"하는 꼴이 안전합니다 (연속 클릭에도 정확).
- **원본 불변** — 배열/객체 상태는 그릇째 새로 만들어 set합니다 (2-3의 스프레드가 여기서 필수가 되는 것: React는 **그릇이 바뀌었는지**로 변경을 감지하므로, 같은 그릇에 push하면 눈치 못 챕니다).

## 2-8-5. 조건과 목록 — 이미 배운 문법의 재활용

**조건부 렌더링** — 2-1의 단락 평가 그대로:

```tsx
{panel === 'files' && ( <파일패널 /> )}           // files 패널일 때만 그림 (실물)
{selected ? <Viewer file={selected} ... /> : <빈안내 />}   // 삼항 — 둘 중 하나 (실물)
```

**목록 렌더링** — 2-3의 map 그대로:

```tsx
{tags.map((tag) => (
  <button key={tag.id} onClick={() => setTagFilter(tag.id)}>...</button>
))}
```

새로 등장한 건 `key={tag.id}` 하나입니다. 다시 그릴 때 React가 "이전 목록의 어느 줄과 같은 항목인지" 알아보는 **이름표**입니다. 항목의 고유 id를 주면 되고, 빼먹으면 콘솔 경고 + 목록이 바뀔 때 상태가 엉뚱한 줄에 붙는 버그가 납니다.

## 2-8-6. useEffect — 그린 다음 할 일, 그리고 청소

그리기 밖의 일(타이머 걸기, 키보드 단축키 등록, 첫 데이터 로딩)은 **useEffect**에 둡니다. 우리 실물 — Ctrl+K 단축키 (`Workspace.tsx`):

```tsx
useEffect(() => {
  const handler = (e: KeyboardEvent) => {
    if ((e.ctrlKey || e.metaKey) && e.key.toLowerCase() === 'k') {
      e.preventDefault();
      setPaletteOpen((open) => !open);
    }
  };
  window.addEventListener('keydown', handler);
  return () => window.removeEventListener('keydown', handler);
}, []);
```

독법: "**그린 뒤에** 이 함수를 실행해라(키 감지기 등록). **돌려주는 함수는 청소용** — 이 컴포넌트가 화면에서 사라질 때 실행해라(감지기 해제)." 끝의 `[]`는 의존성 목록 — "이 값들이 바뀌면 다시 실행"이고, 빈 배열이면 "처음 한 번만". 청소를 빼먹으면 감지기가 누적되는 누수가 생깁니다 — 등록에는 해제, 타이머에는 clear가 짝입니다.

비슷한 훅 하나 더, 이름만 알아두면 됩니다 — **useMemo**: "재료가 안 바뀌었으면 계산 재사용". 실물이 정렬·필터를 적용한 `visibleFiles`입니다 (파일 수천 개를 매 렌더마다 재정렬하지 않게).
